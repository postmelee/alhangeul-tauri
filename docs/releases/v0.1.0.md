### 첫 공개 파일 계약 초안

rhwp v0.8.4는 이미 수용한 기준선을 첫 공개에 유지하고 새 pin 반영은 별도 Task로 분리한다.
최종 main SHA·두 run ID·archive ID/digest·실제 파일 크기/hash는 후속 게시 작업에서 채운다.
아래 예상 이름은 과거 산출물·현재 target 계약 기준이며 실제 inventory와 대조하기 전에는 업로드하지 않는다.

| 대상 | 예상 installer basename | 가져올 경로 | updater |
|---|---|---|---|
| Windows x64 NSIS | `Alhangeul_0.1.0_x64-setup.exe` | 단일 비게시 updater run | 동일 NSIS |
| Windows x64 MSI | `Alhangeul_0.1.0_x64_en-US.msi` | 위와 같은 updater run | 동일 MSI |
| Linux x64 AppImage | `Alhangeul_0.1.0_amd64.AppImage` | 위와 같은 updater run | 쓰기 자격 충족 시 |
| Linux x64 DEB | `Alhangeul_0.1.0_amd64.deb` | 같은 exact SHA의 지정 일반 run | 수동 |
| Linux x64 RPM | `Alhangeul-0.1.0-1.x86_64.rpm` | 위와 같은 일반 run | 수동 |
| Linux arm64 DEB | `Alhangeul_0.1.0_arm64.deb` | 위와 같은 일반 run | 수동 |

명시할 입력 목록은 위 installer 6개, 첫 세 installer basename에 `.sig`를 붙인 서명 3개,
`alhangeul-updater-release-inventory.json` 1개다. SHA256SUMS는 이 10개 basename의 hash를 담는다.
SHA256SUMS 자체 hash는 별도 기록하므로 GitHub asset은 총 **11개**다. 다른 SHA·실패 run 또는
일반 MSI/NSIS/AppImage로 교체하지 않는다. updater inventory schema는 세 target 그대로 두고
수동 패키지의 provenance·hash는 이 기록에 연결한다. Pages도 세 target schema를 유지하며
DEB/RPM·arm64는 기존 GitHub Releases 안내를 사용한다.

게시안: 최종 main에서 비게시 후보 확보 → 실제 파일 확인 → owner의 tag/파일/공개 승인 →
유지관리자 CLI로 exact tag·draft 11개 업로드 → 원격 bytes 재검증 → stable 공개·재조회 →
별도 release data PR·Pages/manifest 승인. 현재 `publish_release=true`는 재빌드하므로 사용하지 않는다.
2026-09-04 CLI 인증 주체는 `postmelee`, repository admin/push 권한을 조회했다. 권한 보유가
실행 승인은 아니며 CLI에 Actions environment 승인이 자동 적용되지 않는다. 경로 허용 결정은 아래에 남긴다.

## 준비 Go/No-Go 판단

2026-09-06 Stage 5는 **Task #9 준비 변경의 devel PR 진입을 Go**로 판정한다. Stage 4.8에서
6종 설치 파일·3종 updater·11개 공개 asset과 동일 bytes 게시 절차, Windows 미서명 및
보호 경계를 결정했고, Stage 4.9에서 공개 상태 3종과 제품 경계 회귀를 통과했다. 기준
`12190e0` 이후 앱·crate·pin·lock·workflow·site 공개 데이터도 바뀌지 않았다.

실제 `v0.1.0` 공개는 **No-Go**다. 이는 준비 실패가 아니라 단계 분리다. 아래 조건을 모두
충족하고 별도 공개 승인을 받기 전에는 빌드·tag·draft/public Release·Pages·manifest를 실행하지 않는다.

| 판단 대상 | 결론 | 근거 | 다음 진입 조건 |
|---|---|---|---|
| Task #9 devel PR | **Go** | Stage 4.8 결정 승인, Stage 4.9 95개 집중 테스트와 Pages·경계 검사 통과 | Stage 5 보고 승인 후 최종 보고·PR 절차 |
| 첫 공개 선행 결함 | **No-Go** | #19 OPEN, 첫 공개 전 수정 결정 | 별도 Task에서 #19 수용 기준·Windows/Linux 회귀 완료 |
| 최종 candidate·파일 | **No-Go** | final main SHA·두 비게시 run·11개 실제 asset이 없음 | release PR과 exact SHA 승인, 새 파일 설치·서명·hash·inventory 수용 |
| GitHub Release | **No-Go** | Release `[]`, `v0.1.0*` tag 없음; 공개 실행 승인 없음 | 동일 bytes draft read-back 뒤 tag·파일·공개 Go 재승인 |
| Pages·production manifest | **No-Go** | `site/release.json` unreleased, production manifest 없음 | Release 공개·원격 bytes 검증 후 별도 release data PR과 배포 승인 |

#28은 OPEN으로 유지하되 Stage 4.8 owner 결정에 따라 첫 공개 차단 조건으로 새로 추가하지 않는다.
현재 자동 보호 부재는 승인된 main SHA·명시 파일·CLI 실행자 기록으로 통제하고, 기술적 보호
구현은 별도 Task에서 다룬다.

현재 마지막 일반 native 수용 SHA는 위 근거 목록의 `50e9124…`다. #54 merge 후의 후보까지
runtime/config/pin/검사 도구 diff를 다시 판정한다. 문서-only라면 기존 source 수용을 재사용할
수 있지만 새 installer hash·서명·설치 기본 확인을 대신하지는 못한다. 열린 모든 Issue를
릴리즈 선행 조건으로 삼지 않고 위 결정과 실제 변경 영향에 필요한 항목만 선택한다.

각 Gate는 [실행 가이드](../operations/PUBLIC_RELEASE_RUNBOOK.md)를 따르고 결과는 이 기록의
identity·검증·공개 gate·한계 항목에 갱신한다. 아직 실행하지 않은 항목은 미실행으로 남긴다.

### 첫 공개 이후 순서

1. #9 준비 변경을 devel에 병합하고, 위 위험의 owner 결정에 따른 선행 작업을 완료한다.
2. 후속 게시 Issue에서 최종 main SHA·파일·공개 Go를 승인받아 v0.1.0 stable을 공개한다.
   rhwp v0.8.4·썸네일·Pages·MSI/NSIS/AppImage updater 기본안과 세 형식 기준선 보존을 인계한다.
3. [macOS sync PR #491](https://github.com/postmelee/alhangeul-macos/pull/491)은 참고만 한다.
   2026-09-04 기준 OPEN이며 Tauri PR이 아니다. 별도 Tauri Task에서 rhwp v0.8.6 Stable tag·
   resolved commit·core·Studio·WASM 정합성과 영향 검증을 수행한다.
4. 다음 앱 version은 별도 승인한다(`0.1.1`은 제안값). 새 공개 후 세 설치 형식의 실제
   production 업그레이드·재실행을 확인하고 이 기록과 다음 버전 기록을 연결한다.

첫 공개 전에 필요한 기본 설치·문서 기능 확인을 다음 버전의 updater 시험으로 미루지 않는다.
이번 단계에는 서명·workflow dispatch·release/tag·Pages 배포·Secret 설정 변경이 없다.
