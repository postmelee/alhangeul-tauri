# Task #110 수행계획서 — 완료된 릴리즈 운영·웹 변경의 main 정렬

상태: 수행계획서 승인 대기
작성일: 2026-10-05 (Asia/Seoul)

## 목적

공개 기본 브랜치 main에 #97의 업데이트 검증 도구·공개 기록, #102의 릴리즈 작성 규격, #108의 웹 다운로드 개선을 반영한다. 이미 공개된 v0.1.1 제품을 다시 배포하는 작업이 아니라, 완료된 운영·웹 변경과 저장소의 공개 상태를 정렬하는 작업이다.

main의 v0.1.1 안내와 양쪽 Git 이력을 보존하며, 일반 task PR과 main 정렬 PR을 분리한다. 각 PR의 정확한 기준 SHA·검증 근거·병합 결과를 기록한다.

## 배경

- 작업지시자는 같은 스레드에서 main 정렬 이슈 초안과 이슈 등록을 승인했고, 등록한 #110의 task-start 진입도 “진행해줘.”로 승인했다. 구현·단계 진행·PR 게시·병합은 각 승인 시점에 이어간다.
- 시작 devel: `1d3817c7133658c9e4251f65f5202baafd0624f4` (PR #109 병합).
- 시작 main: `7bab9062b7d231faad53465536aff407d535f52d` (PR #107 병합).
- 공통 조상: `96e89e900415ee9e1e942b5c01c833dea3415e86` (v0.1.1 제품 source).
- devel 전용 40개, main 전용 2개 커밋이 있으며 직접 tree 비교에서 103개 파일이 다르다. 앱·crate·제품 자산·rhwp lock·pnpm lock·submodule 설정은 동일하다.
- merge-tree 조사에서 README.md 내용 충돌 1개를 확인했다. main은 v0.1.1 공개 웹 안내를, devel은 버전별 릴리즈 기록을 가리킨다. 안정 버전·업데이트 검증 문구는 양쪽이 같다.
- 기존 main cwd에는 사용자 변경이 있고 다른 worktree가 devel을 사용한다. 별도 managed worktree의 local/task110을 최신 origin/devel에서 만들었으며 기존 checkout은 변경하지 않는다.
- docs/operations/DESKTOP_RELEASE.md의 “공개 기본 브랜치와 운영 대상”은 공개 이후 devel → main 정렬과 기존 제품 tag·asset 보존을 명시한다. #87의 이전 정렬 사례도 참고한다.

## 설계 방향

1. **양쪽 이력 보존**: Stage 2에서 최신 승인된 main을 작업 브랜치에 일반 merge한다. reset·rebase·cherry-pick으로 main 전용 이력을 대체하지 않는다. 예상 외 변경이나 추가 충돌이 생기면 범위와 검증을 다시 판단한다.
2. **README 최소 통합**: 기존 v0.1.1 안정 버전, 업데이트 검증, 알려진 제한을 유지한다. 마지막 안내는 v0.1.1 공개 릴리즈 안내와 버전별 릴리즈 기록 두 링크를 자연스럽게 연결하는 짧은 문구로 정리한다.
3. **두 PR의 책임**: task PR은 충돌 해결·계획·검증 기록을 devel에 통합한다. main 정렬 PR은 그 완료된 devel을 main으로 반영한다. 일반 merge commit을 유지하고 devel은 삭제하지 않는다.
4. **완료 시점**: 첫 devel PR은 `Refs #110`으로 추적하며 이슈를 자동 종료하지 않는다. main PR 병합·read-back까지 완료한 뒤 이슈를 종료한다. 첫 PR merge 후에도 필요한 local/task110/worktree는 유지하고 전체 작업 완료 시 정리한다.
5. **배포와 source 분리**: 이번 main SHA를 기존 installer의 source로 기록하지 않는다. v0.1.1 tag source, Release asset, Pages 배포 source는 각 원래 기준을 유지한다.
6. **원격 상태 변화**: PR마다 최신 head/base와 진행 중 작업을 다시 확인한다. devel 또는 main이 이동하면 기존 검사와의 tree/소유 경계 일치를 재검토하고 필요한 범위만 검증한다.
7. **규모 관리**: 새 제품 함수나 큰 소스 파일을 만들지 않는다. 기존 300 LOC 초과 문서는 병합으로 반영하는 완료 작업의 산출물이며 이번 task에서 확대하지 않는다.

## 잠정 단계

구현계획서 작성·승인 이후 다음 단계를 각각 진행하고 완료 보고·커밋 후 다음 단계 승인을 받는다.

- **Stage 1 — 기준선과 수용 근거 확정**
  - 최신 main/devel/source pin, 103개 경로 분류, README 충돌, 기존 성공 CI/업데이트/Pages 근거와 Release·공개 데이터 기준선을 기록한다.
  - 기존 실행의 실제 SHA·job/step 상태·선택 범위·제한을 대조하고 통합 검증 범위를 확정한다.
- **Stage 2 — 이력 통합과 README 충돌 해결**
  - 승인된 main을 local/task110에 일반 merge하고 README 공개 안내 두 링크를 함께 유지한다.
  - main이 작업 브랜치의 조상인지, devel 대비 새 변경이 README와 task 기록으로 제한되는지 검사한다.
  - 제품 version·native source·lock·gitlink, 웹 source·catalog·feed의 동일성을 검사한다.
- **Stage 3 — 통합 계약 검증과 PR 준비**
  - 플랫폼 중립 계약·Studio·Pages 검증을 실행하고 누적 변경/현재 변경의 증거를 구분한다.
  - main 승격 tree와 이미 수용된 소유 경계의 일치 및 첫 PR의 정확한 head/base 검증 전략을 확정한다.
  - 최종 보고·PR 게시 승인을 받을 수 있는 산출물을 준비한다. PR 게시 이후 원격 CI 결과와 main PR 병합은 그 실제 실행 시점에 추가 기록하며 미리 완료 처리하지 않는다.

단계 완료 후 task-final-report 절차로 devel PR을 게시한다. 원격 CI·리뷰·merge 승인을 받은 뒤 첫 PR을 병합한다. 이어 승인된 devel → main PR을 검토·병합하고 실제 main read-back과 정리를 완료한다. 각 전환 시점의 결과와 승인 요청을 같은 스레드에 보고한다.

### CI 범위와 기존 증거 재사용

- docs/operations/CI_VALIDATION.md의 자동 profile은 main 대비 workflow 누적 변경이나 통합 후보에 full을 선택할 수 있다. 이를 fast 전체 수용으로 바꾸어 해석하지 않는다.
- 이번 task의 새 변경 기준은 이미 수용된 devel SHA다. 해당 기준 대비 README·task 기록만 바뀌고 앱·workflow·검증 도구·lock이 동일하면 **이번 추가 변경은 fast 범위**로 검증한다. 누적 workflow/도구/제품의 수용은 각각의 기존 exact source·run·결과를 분리해 재사용한다.
- 첫 devel PR은 자동 PR acceptance의 Linux Node/Studio와 Windows PowerShell fast 및 `Alhangeul PR required` 전체 성공을 확인한다. synthetic merge candidate SHA·PR head/base를 기록한다.
- main PR에는 자동 PR acceptance가 실행되지 않는다. main이 최종 devel의 조상이고 main 병합 후보 tree가 수용된 devel tree와 완전히 같으면 첫 PR CI 후보와의 tree 동일성·상태를 근거로 재사용한다. source나 workflow가 달라지면 재사용하지 않는다.
- tree 재사용 조건을 만족하지 않지만 제품 변경이 없는 경우 정확한 main 승격 source에 승인된 `ci.yml profile=fast` 검증을 실행한다. workflow ref/checkout SHA·선택 범위와 실제 job/step 결과를 기록한다.
- 예상 밖 제품·lock·workflow 구현 변경으로 full/native/package가 필요하면 수행계획을 보정하고 별도 승인을 받는다. 이 수행계획은 새 installer 생성·서명·배포를 허용하지 않는다.
- fast/로컬 성공을 native 설치·GUI·실제 업그레이드의 신규 수용으로 보고하지 않는다. 이전 부분 성공·실패 run·미검증 Linux/Windows 환경의 한계를 유지한다.

### 통합 검증

- PR 준비 전 git status --short가 비어 있고 git diff --check가 통과한다.
- 최종 main에 승인된 변경이 반영되고 기존 main/devel 이력을 ancestry로 보존한다.
- 기존 v0.1.1 tag source·Release ID·11개 asset 목록/식별자/크기/digest와 updater feed·공개 데이터 hash를 기준선과 대조한다. 변동을 발견하면 원인을 조사하며 동일성을 임의로 선언하지 않는다.
- 공개 사이트/다운로드·업데이트·릴리즈 기록 링크가 유효하고 main의 공개 안내가 최신 상태와 맞는다.
- main 병합 후 이슈 종료·이번 publish/task110/local/task110 정리·managed worktree 보관을 확인한다. 다른 작업자의 devel을 이동하지 않고 종료 worktree는 origin/devel 기준으로 돌아간다.

## 리스크

- **README 충돌의 의미 손실**: 공개 웹 안내와 버전별 기록을 함께 연결하고 기존 안정 버전·업데이트 제한을 보존한다.
