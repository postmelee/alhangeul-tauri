## 목적

업데이트 페이지의 ‘최신 버전 다운로드’를 누르면 페이지 안에 설치 파일 선택 영역이 펼쳐지게 한다. Windows/Linux 선택과 전체 공개 설치 파일 6종, 설치 형식별 용도·업데이트 방식을 안내한다. 릴리즈 목록·상세 제목의 과도한 굵기를 낮추고 최신 버전 표시를 분리한다.

## 배경

작업지시자는 Linux 패키지 누락과 릴리즈 제목의 과도한 볼드를 지적했고, 페이지 안 펼침·OS 선택·전체 형식 표시 제안에 “그렇게 진행해줘”로 동의했다. 신규 이슈 초안 승인 후 #108을 M010/enhancement로 등록했으며, 이어 “진행해줘”로 브랜치·오늘할일·수행계획서 준비를 승인했다. 현재 승인은 이 시작 단계까지이며 구현계획서·제품 소스 변경은 아직 하지 않는다.

현재 site/updates/index.html의 드롭다운과 site/release.json.downloads는 NSIS/MSI/AppImage 3종이다. scripts/pages/release-data.mjs는 동일 3종 exact key와 updater inventory 정합성을 강제한다. 이를 일반 패키지 목록으로 바로 확장하면 자동 업데이트 계약에 영향이 생긴다. 반면 docs/releases/v0.1.1.notes.json.metadata.assets에는 검증된 설치 파일 6종이 이미 있다.

홈의 site/script.js는 같은 형식 목록을 일부 사용하지만 DEB/RPM을 하나로 묶고 arm64와 함께 일반 GitHub Releases로 연결한다. 릴리즈 목록은 부모 font-weight 600과 strong을 함께 사용하고, 섹션 제목은 브라우저 기본 굵기를 따른다. 기존 Pages 생성·검사와 릴리즈 안내 생성기를 유지하면서 필요한 부분을 연결한다.

## 설계 방향

### 사용자 흐름

버튼 아래에 선택 영역을 페이지 흐름 안에서 펼친다. 이후 내용은 아래로 내려가고 가리지 않는다. Windows/Linux 선택은 홈페이지와 같은 시각 표현을 재사용한다. 지원 OS를 판별하면 기본 선택하되 두 선택은 항상 노출해 사용자가 바꿀 수 있게 한다. 판별할 수 없는 환경에서는 Windows를 초기 선택하고 둘 다 제공하며, 지원 범위를 추가로 암시하지 않는다.

Windows는 2개, Linux는 4개 항목을 개별 표시하고 아키텍처를 구분한다. AppImage를 여러 배포판의 공통 선택지로 안내하되 모든 배포판 검증 완료로 표현하지 않는다. 배포판명 추천은 기존 공개 설치 안내 범위만 사용한다. DEB/RPM/arm64에는 수동 업데이트를 표시한다. 다운로드 버튼의 접근 가능한 이름에는 OS·아키텍처·형식·버전을 포함한다.

열기/닫기 상태와 제어 영역 관계를 제공한다. OS 선택에는 기존 radio/fieldset 패턴을 우선 재사용하고 키보드 전환을 확인한다. 닫거나 OS를 바꿨을 때 숨겨진 요소에 초점이 남지 않게 한다. 데이터 조회 실패나 JavaScript 비활성 상태에는 GitHub Release로 가는 안내를 유지하며 잘못된 직접 다운로드를 활성화하지 않는다.

### 데이터 경계

site/release.json과 updater/stable.json의 기존 3종 계약은 유지한다. 일반 다운로드 6종은 공개 release notes 원문의 metadata.assets와 version/tag/status를 검증해 별도의 웹용 목록으로 생성한다. 잠정 출력은 `_site/downloads.json`이며 source에 버전 URL을 수동 복제하지 않는다.

Pages build에서 최신 공개 원문과 release.json의 버전·tag·제품 source 정합성을 확인한 뒤 목록을 결정적으로 생성한다. 같은 metadata의 기존 updater 3종과 URL이 같은지 확인한다. 미공개 상태에서는 다운로드를 비활성화한다. 새로운 published 원문이 없거나 버전/자산이 불일치하면 빌드에서 거부한다. 브라우저에서도 release.json과 목록의 status/version/tag가 맞을 때만 링크를 활성화해 배포 캐시 혼합을 처리한다. 이전 릴리즈 상세는 고정된 해당 버전의 6종 다운로드를 유지한다.

홈과 업데이트 페이지는 동일한 OS/아키텍처/형식/설명/업데이트 방식 정의를 사용한다. 새 모듈이 필요하면 site/package-downloads.js와 scripts/pages/package-downloads.mjs로 데이터·UI/운영 경계를 나눈다. schema/API 상세는 승인 후 구현계획서에서 확정한다.

### 시각 표현과 파일 규모

공유 CSS를 보정하되 업데이트 목록/상세에 선택자를 한정해 문의 페이지의 제목 굵기를 바꾸지 않는다. 제목 굵기를 명시하고 항목의 strong 중첩을 없앤다. 최신 배지는 제목과 분리하며 작은 화면에서 설명·버튼·배지가 겹치지 않게 한다. 수정한 CSS/JS의 캐시 키는 HTML 원문과 릴리즈 안내 템플릿·생성 파일에 함께 반영하고 생성 drift를 검사한다.

신규 모듈·테스트는 300 LOC, 함수 50 LOC, 매개변수 5개·복잡도 10 권장 상한 안에서 분리한다. 기존 큰 테스트에 반복 코드를 추가하기보다 책임별 테스트와 기존 fixture helper를 재사용한다. 이번 계획은 신규 상한 예외를 요구하지 않는다.

## 검증 계획

### 단계별 검증

- Stage 1: 6종 공개 목록·release notes와 site/release.json 정합성·미공개/실패·생성 drift·updater bytes 보존 계약. `pnpm run build:pages`, `pnpm run check:pages`, `pnpm run check:release-notes`.
- Stage 2: 변경된 Pages UI 계약·브라우저 펼침/닫힘·OS 전환·키보드·데스크톱/390/320px·형식별 안내·글꼴 굵기·최신 배지·공개 링크 접근 가능한 이름. `pnpm run build:pages`, `pnpm run check:pages`, 생성 drift·whitespace 검사.
- Stage 3: `pnpm run test:automation`, `pnpm run check:product-boundary`, `pnpm run test:upstream`, `pnpm run test:studio`, `pnpm run build:studio`, Pages build/check·release-notes·`git diff --check` 및 PR required.

### 통합 검증

- 공개 목록의 각 URL을 해당 최신 release notes metadata 및 GitHub의 공개 6종 asset과 대조한다. 라이브 다운로드의 HTTP 확인은 HEAD 또는 필요한 최소 메타데이터 조회로 하며 설치 파일 재다운로드/재설치를 반복하지 않는다.
- 기준 site/release.json와 생성된 updater/stable.json을 hash 및 필드 대조한다. source·키·서명·URL·대상·notes·제품 assets의 변경이 없어야 한다.
- Mac 호스트에서는 Node/TypeScript/Pages/Studio의 중립 검사와 사이트 브라우저 검증만 수행한다. 이 사이트 확인은 Mac desktop 제품 검증이 아니다.
- PR 자동 Windows/Linux fast·Alhangeul PR required의 전체 job/필수 step 성공을 확인한다. 같은 source·artifact 결과는 CI_VALIDATION의 exact 재사용 기준에 따라 기록하며 부분 성공을 전체 수용으로 표시하지 않는다. native/package/full profile은 선택하지 않는다.
- PR 준비 전 모든 변경·보고를 커밋하고 `git status --short`가 빈 출력인지 확인한다.
- 공개 단계는 최종 승인 후 exact merge source로 Pages를 게시하고 실제 HTTP와 OS별 6종 메뉴·버전/링크·모바일 배치를 다시 확인한다.

## 리스크

- **공개 데이터/캐시 불일치**: 다른 버전의 목록과 release.json을 섞어 다운로드하지 않도록 생성 및 브라우저에서 일치를 요구한다.
- **updater 경계 변경**: 일반 패키지를 기존 signed target map에 추가하지 않는다. 기존 manifest bytes를 그대로 대조한다.
- **기존 공개 원문이 없는 신규 릴리즈**: 수동 링크 조립으로 숨기지 않고 빌드 검증에서 누락을 알린다. 다음 공개 절차에 원문 생성 순서를 기록한다.
- **작은 화면·접근성**: 패널을 문서 흐름에 배치하고 OS 선택·숨김·키보드 초점·길어지는 설명/배지를 실제 브라우저로 확인한다.
- **공유 CSS와 생성 drift**: 업데이트 페이지 선택자와 공식 템플릿/캐시 키를 함께 보정하고 문의·홈 회귀를 확인한다.
- **배포 승인**: 수행/구현/단계 승인을 Pages 게시 권한으로 확대하지 않는다. 공개 후보와 검증 결과를 제시한 뒤 병합·게시 승인받는다.
- **기존 작업 간섭**: 사용자 local/task69와 다른 devel worktree를 보존하고 새 분리 worktree만 사용한다.

## 승인 요청 사항

- 위 포함/제외 범위와 3단계 진행, 일반 웹 목록 6종·기존 updater 3종의 분리 방향.
- 기존 공식 site/·중앙 website_release_note.html 템플릿·docs/operations/PUBLIC_RELEASE_RUNBOOK.md를 사용하는 문서 위치 판단.
- 중립 로컬 검사·Windows/Linux PR fast·실제 사이트 브라우저·최소 공개 URL 확인 범위.
- 이 수행계획 승인 후 구현계획서 작성까지 진행. 소스 구현은 구현계획 승인 뒤, 병합·Pages 공개는 최종 후보 승인 뒤 수행.
