## 단계와 검증

1. #146 head/base를 다시 고정해 변경 파일과 생성 자산을 검토한다. full 세 플랫폼 빌드·core/설치 계약과 원시 결과를 확인한다. 성공 producer의 exact SHA/run/ID/digest로 Windows PDF 및 Linux GUI full을 실행한다. 실제 설치·실행, 대표 HWP/HWPX 열기·편집·저장·재열기, 직접 PDF, 적용되는 시스템 인쇄 항목을 구분한다.
2. Windows Explorer는 기존 Windows 10/11 KVM guest와 표준 사용자 NSIS/관리자 설치 MSI를 사용한다. 원시 bitmap과 실제 Explorer 화면을 함께 본다. signed candidate path가 필요한 소비자는 검증된 서명 파일을 확보한 뒤 실행한다. 기존 지원 정책과 MSI 3010 관측을 기록한다.
3. 버전과 원문을 준비하고 보호 검사·리뷰를 확인한다. devel→main의 최종 SHA로 일반 all/full/test 및 production updater 비게시 후보를 만들고 환경 리뷰를 받는다. NSIS·MSI·AppImage 서명과 수동 DEB x64/ARM64·RPM provenance를 검증한다.
4. 게시할 각 파일에서 native 설치/실행과 대표 문서 수용을 검증한다. Linux x64 GUI 및 ARM64 runner·Fedora VM을 활용한다. 정확한 설치 파일의 구성과 오픈소스/글꼴 고지 원문을 점검한다. 현재 명시적 bundled 고지는 FONTS.md와 Noto 2개 원문이므로 나머지 WOFF2·JS/Rust 고지의 존재/의무를 확인한다. 미해결 배포 요건은 게시 전 owner에게 보고한다. Authenticode/Smart App Control과 updater Minisign은 별도 판정한다.
5. v0.1.3의 현행 공개 파일을 플랫폼별 기준선으로 고정한다. 기존 생산 테스트의 0.1.2→0.1.3 입력을 재사용해 거짓 통과시키지 않도록 0.1.3→0.1.4 exact 입력과 피드 검증 계획을 준비한다. 사전 격리 검증과 실제 production feed에서의 사후 업그레이드 결과를 분리한다.
6. 필수 gate와 승인 확인 후 runbook의 검증된 exact 파일 승격 경로로 새 tag와 Release를 공개한다. 파일 10개와 SHA256SUMS를 draft/public에서 대조하고 Pages output·다운로드 6종·피드 3종·실제 업그레이드를 재확인한다. 실패 시 단계별 runbook을 적용하고 최종 근거를 보고한다.
