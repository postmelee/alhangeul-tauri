## 목적

Windows/Linux Alhangeul을 처음 공개하고 이후 버전도 반복 배포할 수 있도록 정책, 실행
walkthrough, 체크리스트와 버전별 기록을 분리한다. 새 작업자는 저장소만 읽고 현재 후보,
필수 입력, 승인 지점, 기대 결과와 실패 후 재개 위치를 파악할 수 있어야 한다.

이미 확보한 검증 증거를 보존하면서 변경 영향에 따른 최소 확인과 재사용 기준을 명시한다.
문서화가 끝났다는 사실을 제품 수용, 공개 승인 또는 updater 활성화로 취급하지 않는다.

## 배경

- PR #53과 Task #16이 병합되어 MSI·NSIS·AppImage updater의 구현, 시험용 실제 업데이트와
  실패 안전성 수용을 마쳤다. Windows/Linux 썸네일도 구현됐으나 플랫폼별 수용 범위는 다르다.
- `docs/operations/DESKTOP_RELEASE.md`는 565줄이며 반복 절차와 Task별 과거 증거가 섞여 있다.
  README에는 일부 과거 승인 경계를 현재 미완료 상태처럼 설명하는 문구가 남아 있다.
- macOS 저장소는 반복 runbook, 정책·체크리스트와 `mydocs/release/v<version>.md`를 분리한다.
  문서의 역할과 운영 완성도를 참고하되 DMG·Sparkle·Homebrew나 macOS 명령은 이식하지 않는다.
- 이 저장소의 공식 제품 문서는 `docs/`, 사용자 웹사이트는 `site/`다. 프레임워크용
  `mydocs/manual/release_update_protocol.md`는 Alhangeul 제품 배포 지침이 아니다.
- 작업지시자는 문서화 후 첫 릴리즈, upstream v0.8.6 수용, 다음 릴리즈와 앱의 실제 updater
  확인을 원한다. 이번 #54는 이 순서의 문서와 인계 기준만 소유한다.
- #9는 첫 공개 후보 Go/No-Go, #19는 PDF 일관성 문제, #28은 branch protection을 소유한다.
  `local/task9` 등 다른 작업 브랜치와 기존 계획·결과는 임의로 변경하지 않는다.

## 범위

### 포함

- 반복 정책·실행 순서·검증 선택표·버전 기록·템플릿의 책임과 진입점을 정비한다.
- 릴리즈 식별자, 후보 SHA, 이전 릴리즈, upstream pin, 패키지·서명·inventory와 게시 순서를
  실제 source에 대조한다. 첫 공개의 이전 릴리즈는 `없음`으로 기록한다.
- 썸네일과 updater를 포함하는 현재 제품 범위를 설명하되 구현·자동 수용·실기기 수용·공개
  완료를 구분한다. AppImage에 DEB/RPM의 파일 관리자 등록 기능이 있다고 쓰지 않는다.
- Windows MSI·NSIS, Linux x64 AppImage의 updater 대상과 Linux DEB/RPM·arm64 수동 배포
  대상을 분리한다. updater 서명과 Windows Authenticode도 구분한다.
- 과거 증거의 SHA·run·digest·제약을 보존하고 반복 정책 문서에는 필요한 요약과 링크만 둔다.
- 입력 수집부터 후보 검증, 공개, Pages·manifest, 실제 설치본 확인, 실패 재개·복구와 종료
  기록까지 명령·기대 결과·승인·중단 조건을 담은 walkthrough를 작성한다.
- 코드가 제공하지 않는 draft 승격, 수동 패키지 게시, 채널·권한 등의 차이는 후속 승인
  항목으로 표시한다. 문서만으로 해당 기능을 구현하거나 공개 정책을 승인하지 않는다.
- README·문서 인덱스·개발 문서의 관련 안내를 증거에 맞게 최소 보정한다.
- v0.1.0 준비 기록과 다음 릴리즈에 재사용할 양식을 작성하고 #9로 인계할 결정을 정리한다.

### 제외

- 앱·썸네일·updater source, tests, scripts, workflow, package·lock·빌드 설정 변경
- 새 자동화 도구나 skill 구현, CI 확장, branch protection·환경·Secret 변경
- 실제 native build·GUI acceptance·서명·원격 workflow 실행
- 앱 버전 변경, release PR·tag·GitHub Release 생성, Pages 배포와 updater 활성화
- `site/` 파일 변경, 공개 다운로드 URL·manifest 데이터의 게시 상태 전환
- upstream pin 갱신, macOS PR #491 직접 병합·cherry-pick, 다른 저장소 변경
- #9의 최종 Go/No-Go, #19 수정 또는 위험 수용, #28 정책 구현을 대신 수행
- 기존 타스크 계획·단계·최종 보고서의 결과 재작성 또는 다른 작업 브랜치 변경

## 설계 방향

### 문서 책임과 진실 원천

- `DESKTOP_RELEASE.md`: 반복되는 제품 배포 정책, 지원 matrix, 문서 읽는 순서의 진입점.
- `PUBLIC_RELEASE_RUNBOOK.md`: 실제 작업 순서. 각 단계는 입력·명령·기대 결과·증거 위치와
  승인·중단·재개 조건을 가진다. 공개 권한이 있는 명령은 읽기 전용 확인과 명확히 분리한다.
- `RELEASE_CHECKLIST.md`: 매번 필요한 기본 체크와 변경 영역별 추가 체크. 명령은 runbook을
  참조하고 버전별 실행 결과는 여기에 누적하지 않는다.
- `docs/releases/`: 공식 제품 릴리즈의 준비·공개 상태, 결정과 검증 출처. Task #54의
  최종 보고서는 별도로 `mydocs/report/`에 둔다.
- `release_record.md`: 실제 기록 위치, 작성 시점, 한국어 작성, 필수·선택 섹션과 검증 기준을
  명시하는 템플릿. 실행 결과와 승인 완료를 미리 채우지 않는다.
- README는 현재 기능과 공개 상태, 다음 문서로 가는 링크를 소유한다. 긴 run·digest 목록은
  버전 기록을 참조한다. `docs/DEVELOPMENT.md`의 제품 소유 경계는 바꾸지 않는다.

### 과거 기록 보존

1. 기존 release 문서의 절별로 반복 정책과 과거 결과를 분류한다.
2. Task별 원본 보고서가 있으면 버전 기록의 증거 목록에서 직접 연결한다.
3. 현 문서에만 있는 고유 값·수용 한계는 누락 없이 버전 기록으로 이전하거나 시작 기준
   commit의 원문에 고정 링크한다. 단순히 삭제하고 "과거 기록"이라고 쓰지 않는다.
4. 이전 위치와 새 위치의 대응표를 Stage 1 보고서에 남긴다. 기존 문서 경로는 유지하고
   저장소 내 링크·앵커의 사용처를 확인한다. 필요하면 호환용 진입 앵커를 남긴다.

### 첫 공개와 후속 공개

- `v0.1.0` 문서는 현재 source version의 준비 기록이며 공개 채널·최종 candidate·게시 시각은
  미확정으로 둔다. #9의 prerelease 계획과 현재 stable-only 구현은 결정 대기 차이로 적는다.
- 첫 공개 설치본에는 production 공개키와 canonical endpoint가 있어야 하며, 같은 버전의
  feed에서 업데이트 없음 확인과 실제 `N → N+1` 설치 성공을 구분한다.
- 실제 다음 릴리즈 전에 MSI·NSIS 설치본을 각각 격리한 Windows 환경과 쓰기 가능한 Linux
  AppImage 기준선을 보존한다. 새 버전 공개 뒤 각자 같은 형식으로 업데이트한다.
- macOS PR #491은 같은 upstream을 참고하는 증거일 뿐 Tauri 갱신 PR이 아니다. 별도 갱신
  Task에서 Stable tag·resolved commit과 native core·Studio·WASM을 함께 맞춘다.
- 첫 버전 `0.1.0`, 다음 버전 `0.1.1` 및 `rhwp v0.8.4 → v0.8.6` 순서는 제안 시나리오다.
  실제 source·version·채널·기존 pin 유지 예외·공개 승인 값은 각 릴리즈에서 확정한다.
- 공개 전 필요한 설치·문서 기능 확인을 다음 버전의 사후 updater 시험으로 대체하지 않는다.

### 검증 비용과 미구현 경계

- 필수 확인은 release identity, 산출물 무결성·서명, 실제 설치본의 기본 기능과 public
  read-back으로 분류한다. 영향을 받지 않는 과거 검증은 source/config diff와 근거를 기록해
  재사용할 수 있다. 자동화 성공과 미실행 GUI 확인을 같은 것으로 취급하지 않는다.
- upstream, updater/target, installer·썸네일 등록, Pages, 문서-only 변경을 구분해 추가 확인을
  선택한다. 단순 merge·문서 변경이라는 이유로 전체 native·negative suite를 재실행하지 않는다.
- 새로운 공개 installer 생성은 검증 재실행과 구분한다. 재빌드한 바이너리에는 과거 파일의
  digest나 서명·설치 성공을 승계하지 않는다.
- 원인 변경 없는 실패 job 재실행을 금지하고 실패 단계, immutable 입력과 재개 조건을 기록한다.
- #54에서 발견한 자동화 부족은 문서의 승인 대기 항목으로 남긴다. tag 이동, asset 덮어쓰기,
  채널 정책 우회와 사용자가 승인하지 않은 명령 실행으로 메우지 않는다.
- 신규·정비 문서는 역할별 300 LOC 이내를 목표로 한다. 보존 때문에 상한을 넘길 필요가 있으면
  구현계획 승인 또는 보정 승인에서 경로·이유를 먼저 확정하며 임의 분할하지 않는다.

## 잠정 단계

- **Stage 1 — 정책과 기록 구조 정비**
  - 기존 source·workflow와 문서를 대조하고 반복 정책·과거 증거·미확정 결정으로 분류한다.
  - `DESKTOP_RELEASE.md`, release 인덱스·준비 기록의 골격과 기록 템플릿을 정비한다.
  - 과거 절·고유 증거의 대응표와 변경 파일 경계를 검증한다.
- **Stage 2 — 실행 runbook과 최소 체크리스트**
  - 현재 가능한 명령, 단계별 승인·중단·재개, 기본/변경 영향별 검증을 문서화한다.
  - 첫 공개와 두 버전 updater 확인 절차를 연결하되 미구현 기능·미승인 정책은 구분한다.
  - 명령·input·permission·산출물과 source의 대응을 읽기 전용 검증한다.
- **Stage 3 — 진입점 정렬과 walkthrough 검증**
  - README·docs 인덱스·개발 안내·템플릿 안내를 정렬하고 준비 기록의 인계를 완성한다.

## 검증 계획

### 단계별 검증

- Stage 1
  - `git diff --check`; 문서 위치·역할·과거 증거 이전 대응표 검토.
  - 새 릴리즈 기록이 미공개 준비 상태이며 실제 공개 성공이나 자동 Go 판정을 담지 않는지 확인.
- Stage 2
  - workflow `workflow_dispatch` input, job 권한, build/publish 분기와 각 문서 명령의 대조.
  - `package.json`, release data validator, inventory·manifest 생성 경계를 읽기 전용 확인.
  - 지원·수동 설치 matrix, 키/서명 구분과 source SHA·파일 digest 재사용 조건 검토.
- Stage 3
  - 변경 문서의 상대 링크·앵커·예제 경로·참조 파일 존재 여부 확인.
  - 첫 공개(이전 버전 없음), 다음 공개(이전 설치본 있음), signing 실패, Release 이후 Pages
    실패, manifest 게시 이후 결함의 tabletop walkthrough. 명령을 실행하지 않고 경로를 대조.
  - 문서-only diff와 기록 템플릿의 필수 섹션·비밀 제외 기준 검토.

### 통합 검증

- 역할 분리가 사용자 승인 범위와 일치하고, 문서만 읽어 입력·실행·중단·인계를 찾을 수 있다.
- 반복 가이드에는 최신 정책만 두고 과거 결과·고유 SHA·한계는 출처를 잃지 않는다.
- 실제 명령이 없는 기능, 미실행 GUI, 미공개 Release를 완료로 표시하지 않는다.
- 변경 경로는 승인된 문서·템플릿·작업 기록뿐이다. source·workflow·Secret·upstream pin과
  `site/release.json`·manifest·원격 공개 상태는 바꾸지 않는다.
- `git diff --check`가 통과하고 최종 커밋 후 `git status --short`가 빈 출력이다.
- native build·Studio build·전체 test suite·원격 Actions를 실행하지 않는다. 이미 통과한
  검증을 문서화 작업 검증으로 재실행하거나 새 수용 결과로 기록하지 않는다.
