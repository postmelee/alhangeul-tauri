# Task #122 수행계획서 — rhwp v0.9.0 반영 및 Alhangeul v0.1.3 릴리즈 후보 준비

GitHub Issue [#122](https://github.com/postmelee/alhangeul-tauri/issues/122) · M010 · 2026-11-09 · 수행계획 승인 대기

## 목적

rhwp v0.9.0의 Rust core와 Studio를 동일한 커밋에서 통합한다. Alhangeul의 기존 데스크톱 기능을 Windows와 Linux에서 검증한 뒤, v0.1.3 후보의 설치 파일 6종과 릴리즈 노트를 공개 판단에 사용할 수 있도록 준비한다.

## 배경

- 기준 브랜치는 `devel`의 `4a68111194f2102370eabf5a323ea4fa107a2da4`이다. 직전 공개 제품 v0.1.2는 rhwp v0.8.7 커밋 `1a76570e833917d15817415a53c09ad61ab3203f`를 사용한다. [직전 릴리즈 작업 #113](https://github.com/postmelee/alhangeul-tauri/issues/113)
- 11월 8일 공개된 Stable 태그 v0.9.0은 `c9095c5f67632e6721e800ccc7fb43ea49d26682`를 가리킨다. upstream은 JS·WASM·Worker를 같은 버전으로 배포하도록 안내한다. Alhangeul이 실제로 번들에 넣는 진입점과 자원 경로를 확인해야 한다. [rhwp v0.9.0](https://github.com/edwardkim/rhwp/releases/tag/v0.9.0)
- 이슈 등록 직전 열린 자동 후보 PR은 없었다. 기존 동기화 workflow는 매일 실행되므로 실제 시작 시 동일 대상 후보의 유무를 다시 확인한다.

## 범위

### 포함

- Stable 태그와 커밋 확인, 기존 자동 후보 생성 또는 재사용, source gitlink·native lock·WASM·Studio·Worker 출처 확인.
- 변경된 upstream API와 충돌하는 앱 adapter의 보정, 데스크톱 파일 작업·로컬 글꼴·PDF·인쇄·썸네일 회귀 확인.
- 제품 버전 0.1.3 정합화, 릴리즈 노트 초안, 기존 Windows/Linux 설치 파일 6종의 수용 결과 인계.

### 제외

- upstream 소스 직접 수정, upstream 신기능의 별도 앱 기능화, 지원 플랫폼·설치 형식 추가.
- 이번 후보 준비 이후의 production 서명, 태그 생성, GitHub Release 게시, Pages·updater 피드 전환. 별도 승인 후 동일 커밋 및 최종 게시 파일의 검증 절차를 따른다.

## 설계 방향

1. 기존 `rhwp-upstream-sync.yml`에 명시적인 `target_tag=v0.9.0`을 사용한다. 기존 후보가 있으면 태그·커밋·base를 확인해 재사용한다. 생성기 실패 시 실패 단계와 입력을 확인하고, 보정 범위를 기록한다.
2. Rust 의존성과 WASM binding을 하나의 pin으로 관리한다. Studio의 실제 entry와 Worker 로딩은 빌드 결과 및 설치본에서 확인한다. 변경된 API는 제품 소유 adapter에서 대응하며 core와 Studio 코드를 복제하지 않는다.
3. 6종 후보 각각에 제품 커밋, 빌드 run과 artifact ID, 파일명·크기·SHA-256, 설치 환경 및 결과를 연결한다. 후보 검증 후 서명이나 재빌드로 파일이 달라지면 해당 파일의 검증을 다시 선택한다.

## 검증 계획

### 단계별 검증

- 1단계에서는 GitHub release/tag, submodule SHA, `rhwp-core.lock`과 생성물 해시를 대조하고 `pnpm run check:rhwp-pin`과 `pnpm run test:upstream`을 실행한다. 자동화가 같은 후보를 중복 생성하지 않는지 확인한다.
- 2단계에서는 `pnpm run check:product-boundary`, `pnpm run check:product-version`, `pnpm run test:studio`, `pnpm run build:studio`를 실행한다. Worker와 WASM 자원의 번들 경로를 확인하고 변경된 adapter의 회귀 사례를 실행한다.
- 3단계에서는 Windows x64 NSIS·MSI, Linux x64 AppImage·DEB·RPM 및 Linux arm64 DEB의 빌드·설치(또는 AppImage 실행)를 각각 확인한다. Windows와 Linux의 대표 설치본에서 HWP/HWPX 열기·편집·저장·재열기, 로컬 글꼴, PDF의 페이지 수·한글 텍스트, 시스템 인쇄의 페이지 출력·취소 후 복귀를 확인한다. Explorer와 Linux 파일 관리자의 첫 페이지 썸네일은 등록을 제공하는 설치 형식에서 검증한다.
- 4단계에서는 노트에 실린 동작을 앱에서 확인한 근거와 대조하고, 후보별 해시·수용 결과와 미실행 범위를 기록한다.

### 통합 검증

`docs/operations/CI_VALIDATION.md`, `RELEASE_CHECKLIST.md`, `PUBLIC_RELEASE_RUNBOOK.md`를 적용한다. 새 pin이 영향을 미치는 문서 렌더링 및 새 설치 파일에는 해당 커밋·파일의 결과를 사용한다. 재사용하는 결과에는 원래 SHA와 변경 영향 판단을 기록한다. Rust desktop 검증과 Tauri 패키징은 Windows/Linux에서 수행한다. 각 단계에서 `git diff --check`와 커밋 후 작업 트리 상태를 확인한다.

## 리스크

- Studio 진입점, Worker 경로 또는 WASM binding 변경은 개발 빌드가 통과해도 설치본의 문서 열기에 영향을 줄 수 있다. 새 설치본의 로딩과 대표 문서 편집·재열기로 확인한다.
- 렌더러 변경은 화면, 직접 PDF, 시스템 인쇄, 썸네일에 다르게 나타날 수 있다. 경로별 결과와 사용한 문서를 기록하며 미실행 환경을 표시한다.
- 정기 동기화나 base 변경이 겹치면 기존 PR과 대상 SHA를 다시 대조하고, 최종 수용 대상이 달라진 검사를 재선정한다.
