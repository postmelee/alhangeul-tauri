# Task #16 수행계획서 — Tauri updater 기반 Windows/Linux 자동 업데이트 경로

GitHub Issue: [#16](https://github.com/postmelee/alhangeul-tauri/issues/16)
마일스톤: M010

## 목적

첫 공개 Alhangeul 설치본부터 서명 검증되는 후속 업데이트 경로를 제공한다. 자동 업데이트
지원 형식은 Windows x64 MSI·NSIS와 Linux x64 AppImage로 한정하고, 각 설치본은 자기
형식과 architecture에 해당하는 updater artifact만 선택해야 한다.

업데이트 상태와 native 판별·다운로드·설치·재시작 경계는 Rust가 소유한다. TypeScript에는
상태 조회, 수동 확인, 명시적 다운로드·설치 요청과 사용자 표시를 위한 좁은 계약만 노출한다.
시작 시 확인은 새 버전 알림까지만 수행하고, 사용자 동작 없이 artifact를 내려받거나 설치하지
않는다. 하나라도 저장하지 않은 문서가 있으면 다운로드 전과 설치 직전에 다시 차단한다.

GitHub Release의 installer·서명과 GitHub Pages의 정적 updater manifest를 하나의 검증된
release inventory에서 만들고, immutable release artifact가 먼저 게시·검증된 경우에만
manifest를 공개한다. 세 지원 형식의 실제 `N → N+1` 수용을 통과하기 전에는 updater를
공개 배포 입력으로 사용하지 않는다.

## 배경

- Alhangeul 독립화 과정에서 HOP updater와 release endpoint를 제거했고 현재 제품에는 자동
  업데이트 경로가 없다. updater 없는 첫 공개 설치본은 후속 버전에서 수동 재설치를 요구한다.
- Task #24가 `rhwp v0.8.4`의 native·bundled Studio 기준선을 확정했고, Task #45와 PR #48이
  세 installer의 사용자 다운로드 target 및
  `https://postmelee.github.io/alhangeul-tauri/updater/stable.json` 예약 endpoint를 확정했다.
- 현재 `scripts/check-release-metadata.mjs`, Pages build와 checker는 updater dependency,
  설정과 manifest를 의도적으로 거부한다. 이번 task는 이 임시 차단을 서명·순서 검증 gate로
  대체해야 한다.
- 현재 desktop artifact workflow는 일반 검증 build이다. updater artifact 생성을 그대로
  켜면 모든 `tauri build`가 private key를 요구하므로 일반 build와 승인된 release build를
  분리해야 한다.
- 현재 Rust `DocumentSessionManager::has_dirty_sessions`는 release 전용 close guard에 한정돼
  있다. updater는 여러 창의 전체 세션을 native 진실 원천으로 재검사할 수 있어야 한다.
- 공식 기준은 [Tauri 2 updater 문서](https://v2.tauri.app/plugin/updater/)와
  [공식 updater plugin 구현](https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/updater)이다.
  Tauri 2 updater는 signature를 필수 검증하며, 새 제품에는 legacy 호환 archive 대신
  `bundle.createUpdaterArtifacts: true`의 v2 artifact 계약을 사용한다.

## 설계 방향

- **Rust native 소유**: webview는 공식 updater guest API를 직접 호출하지 않는다. Rust service가
  platform 자격, target, state transition, update resource, progress, dirty guard와 install을
  소유하고 직렬화된 상태 snapshot과 제한된 custom command만 UI에 제공한다.
- **명시적 상태 기계**: `idle`을 포함한 단방향 상태 전이와 operation id를 두어 오래된 event와
  동시 요청을 무시한다. background·manual check는 같은 native service를 사용하되 background
  오류는 편집을 방해하는 modal로 승격하지 않는다.
- **두 번의 데이터 보호 gate**: 다운로드 요청을 수락하기 직전과 다운로드가 끝난 뒤 설치를
  시작하기 직전에 `AppState`의 모든 문서 세션을 다시 확인한다. UI dirty 표시는 안내용이며
  허용 여부의 진실 원천으로 사용하지 않는다.
- **target은 native 증거로 결정**: Windows는 current executable의 canonical install path와
  승인된 uninstall registry record가 같은 설치를 가리킬 때만 MSI/NSIS target을 확정한다.
  Linux는 x64 AppImage 실행 증거와 교체 가능한 경로가 확인될 때만 AppImage target을 허용한다.
  UI, user-agent, 파일명 하나만으로 추정하지 않으며 충돌·누락은 수동 다운로드로 닫는다.
- **일반 build와 release build 분리**: 일반 `tauri dev`, CI와 desktop artifact build는 updater
  private key와 updater artifact 생성을 요구하지 않는다. 공개 endpoint·공개키는 binary에
  내장하되 `createUpdaterArtifacts: true`는 별도 release config에서만 병합한다. 기본 브랜치에
  이미 존재하는 `alhangeul-desktop.yml`에 명시적인 updater mode를 추가해 task branch에서도
  같은 workflow identity로 exact-SHA 검증하고, 그 mode에서만 signing secret을 공급한다.
- **Tauri 2 artifact 원형 유지**: 신규 v2 제품이므로 `v1Compatible` archive를 만들지 않는다.
  AppImage, MSI와 NSIS installer 자체 및 Tauri가 생성한 `.sig`를 inventory로 수집하고 파일을
  다시 포장하거나 signature와 artifact의 바이트 대응을 깨지 않는다.
- **단일 release inventory**: version·tag·source SHA·target·URL·hash·서명을 schema로 고정한다.
  사용자 다운로드와 updater manifest가 함께 검증하며 mutable URL을 허용하지 않는다.
- **artifact 우선 게시**: release job은 artifact와 `.sig` 업로드 및 원격 read-back 검증까지
  완료한다. 그 뒤 별도 승인된 Pages exact-SHA 배포가 `stable.json`을 한 번에 교체한다.
  일부 target만 존재하거나 signature·version이 불일치하면 기존 manifest를 유지한다.
- **UI 최소 확장**: 기존 About dialog와 desktop message/event 기반에 수동 확인 진입점과
  update 상태 dialog를 연결한다. 새 버전 알림은 문서 편집을 가리지 않고, 설치 버튼은 version,
  target과 재시작 영향을 명확히 보여 준 뒤 사용자가 직접 누르게 한다. unsupported 실행은
  Task #45 업데이트 페이지의 수동 다운로드로 연결한다.
- **key는 비밀 경계 밖으로 나오지 않음**: public key만 source/config에 남긴다. private key와
  password는 생성 순간부터 저장소 작업 디렉터리와 artifact에 쓰지 않고, 승인된 보관·백업과
  GitHub Secret 등록 절차를 별도 checkpoint로 실행한다. 유실 시 기존 binary의 신뢰 사슬을
  복구할 수 없다는 점과 rotation 시 복수 release 전환 절차를 운영 문서에 기록한다.
- **승인 checkpoint**: 실제 key pair 생성·백업·Secret 등록, 시험 release/tag 생성, release
  workflow 실행, Pages manifest 게시·updater 활성화는 각각 실행 직전에 범위·대상·복구 방법을
  제시하고 작업지시자의 명시 승인을 다시 받는다.
- **지원 host 준수**: macOS에서는 platform-neutral 검증만 수행한다. desktop Rust test·clippy,
  Tauri build와 설치 수용은 Windows/Linux runner 또는 승인된 실제 환경에서만 실행한다.

## 잠정 단계

- **Stage 1 — updater 신뢰·target·상태 계약**
  - Rust/TypeScript 직렬화 계약, 상태 전이, 세 custom target과 Windows/Linux fail-closed 판별을
    구현하고 fixture 기반 unit test로 고정한다.
  - 실제 key 생성 없이 공개키/개인키 경계, config 분리와 release inventory schema를 확정한다.
- **Stage 2 — Rust updater service와 문서 보호 UI**
  - 공식 updater plugin, native check/download/install service, 진행 event, 동시성 제어와 두 번의
    dirty-session gate를 구현한다.
  - 시작 알림, 수동 확인, 명시적 다운로드·설치, 오류·수동 fallback UI와 TypeScript test를 만든다.
- **Stage 3 — 서명 artifact·manifest·Pages 자동 gate**
  - release-only updater config, 세 artifact·`.sig` inventory와 manifest 생성·검증 도구를 만든다.
  - 기존의 updater 전면 금지 검사를 artifact-first·manifest fail-closed 계약으로 대체하고
    workflow·Pages automation test를 통과시킨다. 실제 Secret과 원격 release는 사용하지 않는다.
- **Stage 4 — key·release 운영 계약과 source 통합 검증**
  - 별도 명시 승인 후 production updater key pair의 안전한 생성·백업·Secret 등록과 public key
    내장을 수행한다. 승인이 없으면 source-only 검증까지만 진행하고 task 완료로 간주하지 않는다.
  - architecture·release·사용자 문서를 정렬하고 platform-neutral 전체 gate 및 Windows/Linux
    native build gate를 exact source SHA에서 통과시킨다.
- **Stage 5 — 세 형식 실제 `N → N+1` 수용과 게시 handoff**
  - 별도 명시 승인된 비공개/시험 release 범위에서 MSI, NSIS와 AppImage clean install 업데이트,
    cross-format·변조·network·dirty·파일 연결·read-only negative 시나리오를 검증한다.
  - 시험 부산물을 승인된 방식으로 정리하고, 최종 공개 release/tag 자체를 만들지 않은 채 검증된
    release artifact → Pages manifest 순서와 첫 공개 릴리스 입력을 최종 보고서로 넘긴다.

  - key fingerprint·public key 내장 확인과 tracked/untracked secret 누출 검사
  - `pnpm run check:product-boundary`
  - `pnpm run check:product-version`
  - `pnpm run check:release-metadata`
  - `pnpm run test:automation`
  - `pnpm run test:upstream`
  - `pnpm run test:studio`
  - `pnpm run build:studio`
  - Windows/Linux exact-SHA Rust test·clippy와 private key 없는 일반 Tauri build
- Stage 5
  - Windows x64 MSI clean install `N → N+1`, target, uninstall registry와 HWP/HWPX 연결 확인
  - Windows x64 NSIS clean install `N → N+1`, target, uninstall registry와 HWP/HWPX 연결 확인
  - MSI↔NSIS cross-format artifact 선택 거부
  - Linux x64 AppImage `N → N+1`, 재시작, writable/read-only와 비-AppImage 실행 확인
  - 다중 창 dirty, 다운로드 후 dirty 전환, 변조 signature, timeout·HTTP 오류·no-update 확인
  - remote Release asset read-back 완료 뒤에만 Pages manifest가 생성·게시되는 순서 확인

### 통합 검증

- 승인된 첫 공개 candidate binary에 HTTPS endpoint와 production public key가 포함된다.
- private key 또는 password가 저장소, build artifact, cache와 log에 노출되지 않는다.
- 개발 build와 일반 검증 build는 private key 없이 실행·검증할 수 있다.
- MSI, NSIS와 AppImage가 정확히 자기 custom target만 요청하며 불명확한 실행은 수동 fallback한다.
- background 확인과 사용자 수동 확인이 구분되고 다운로드·설치는 명시 동작으로만 시작한다.
- 여러 창 중 하나라도 dirty이면 다운로드·설치가 차단되고 다운로드 뒤 변경도 설치 직전 걸러진다.
- manifest와 Task #45 다운로드 링크가 동일 immutable GitHub Release artifact를 가리킨다.
- 변조·부분 release·signature 불일치에서는 새 manifest가 게시되지 않는다.
- 세 지원 형식에서 실제 `N → N+1`이 각각 한 번 이상 성공한다.
- Windows 업데이트 뒤 파일 연결이 보존되고 Linux read-only AppImage는 안전하게 실패한다.
- 최종 공개 release/tag, `devel → main` 병합과 updater 활성화는 이 task 결과를 입력으로 별도 승인한다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **잘못된 installer target 선택**: filename이나 UI 추정 대신 install path와 registry/AppImage
  runtime evidence를 교차 확인하고 모호한 경우 자동 설치를 거부한다.
- **편집 중 데이터 손실**: Rust 전체 세션을 다운로드 전·설치 전 두 번 확인하고 Windows installer
  실행 종료 및 Linux 재시작보다 guard가 항상 앞서도록 상태 전이를 test한다.
- **private key 유출·유실**: 저장소 밖 생성·백업, 최소 권한 Secret, log masking과 누출 검사를
  두고 fingerprint만 기록한다. 복구되지 않는 유실·무단 rotation은 release 차단 사유로 둔다.
- **일반 CI가 signing secret에 결합**: updater artifact 생성 설정을 release overlay로 분리해
  기존 dev/CI build가 secret 없이 유지되는 것을 automation test로 고정한다.
- **artifact보다 manifest가 먼저 공개**: 완전한 remote inventory와 signature read-back을 Pages
  입력 조건으로 두고 partial 실패에서는 기존 stable manifest를 보존한다.
- **실제 수용 검증 비용과 반복 실행**: final candidate exact SHA와 시나리오를 먼저 고정하고 원인
  변경 없는 rerun을 금지한다. 실패는 artifact, install, target, signature, endpoint로 분류한다.
- **시험 release가 공개 사용자에게 노출**: exact tag namespace, 공개 범위, 삭제/보존 방식을 실행
  전에 별도 승인받고 stable endpoint에는 수용 완료 전 연결하지 않는다.
- **Tauri plugin API 변화**: 현재 공식 v2 문서와 pin된 dependency API를 구현계획서에서 다시
  확인하고 plugin version·lockfile drift를 검증한다.

## 승인 요청 사항

- updater 지원 형식을 Windows x64 MSI·NSIS와 Linux x64 AppImage 세 가지로 고정한다.
- updater를 Rust native service로 소유하고 TypeScript에는 좁은 상태·명령 계약만 제공한다.
- background 확인은 알림까지만, 다운로드·설치는 사용자 명시 동작으로만 수행한다.
- native target 판별이 불명확하거나 지원 package가 아니면 자동 설치하지 않고 Task #45 Pages로
  수동 fallback한다.
- 일반 build와 release-only updater artifact build를 분리하고 Tauri 2 v2 artifact만 사용한다.
- GitHub Release artifact·signature 검증 완료 후에만 Pages stable manifest를 게시한다.
- 공식 문서는 `docs/architecture/UPDATER.md`, `docs/operations/DESKTOP_RELEASE.md`와
  `site/updates/`에 배치한다.
- 5개 Stage와 현재 macOS host/Windows·Linux native 검증 경계를 승인한다.
- 이 승인에는 key 생성·Secret 등록·시험 release·workflow 실행·manifest 게시 권한이 포함되지
  않으며, 각 외부 상태 변경 직전에 다시 명시 승인한다.

승인되면 `task_m010_16_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지와 각 승인
checkpoint를 구체화한다.
