# Task #35 수행계획서 — Windows GUI E2E exact-SHA acceptance 자동화

GitHub Issue: [#35](https://github.com/postmelee/alhangeul-tauri/issues/35)
마일스톤: M010

## 목적

표준 GitHub-hosted `windows-2025` runner에서 Alhangeul의 exact-SHA Windows x64 bundle을 MSI와 NSIS 각각의 깨끗한 환경에 설치하고, WebView 문서 UX와 Windows 네이티브 대화상자를 반복 검증하는 GUI acceptance gate를 구축한다.

Issue #34의 공통 Tauri WebDriver fixture·assertion·evidence·artifact handoff를 복제하지 않고 계승한다. WebView 내부는 외부 `tauri-driver`와 WebdriverIO로, Open/Save As·system print·Microsoft Print to PDF 같은 네이티브 UI는 Microsoft WinApp CLI의 UI Automation(UIA) 명령으로 제어한다. 일반 후보는 자동 증거로 대부분 판정하고 Windows 10/11 실기기 확인은 공개 릴리즈와 인쇄·글꼴·WebView upstream 변경 같은 위험 기반 gate로 축소한다.

## 배경

Issue #24 Stage 4에서는 exact SHA의 NSIS 전체 GUI를 VDI에서 수동 검증하고 MSI는 GitHub-hosted installer smoke로 보완했다. 현재 `.github/workflows/alhangeul-desktop.yml`의 `windows-installer-smoke`는 MSI·NSIS의 inventory, silent install, version, handler·shortcut, 제한 실행과 uninstall cleanup을 검증하지만 실제 WebView 문서 UX와 native file/print dialog는 수용하지 않는다. 후보마다 관리자 권한과 VDI session 상태에 의존해 같은 검증을 사람이 반복하는 방식은 재현성과 진단 증거가 부족하다.

Issue #34는 exact build SHA와 native run/artifact를 fail-closed로 결속하는 verifier, 공개 HWP/HWPX fixture, 플랫폼 중립 WebdriverIO helper와 evidence schema를 이미 제공한다. Tauri 공식 문서는 Windows에서 외부 `tauri-driver`를 지원하며 `@wdio/tauri-service`가 Edge WebDriver를 WebView2 runtime과 동기화할 수 있다고 설명한다. Microsoft WinApp CLI는 Win32를 포함한 Windows 앱과 표준 file dialog를 UIA로 검사·조작하고 GitHub Actions에서 실행하는 경로를 제공한다. 다만 mouse/keyboard 입력 주입 명령은 unlocked interactive desktop을 요구하므로, CI 기본 설계는 `inspect`, `invoke`, `set-value`, `wait-for`, `screenshot` 같은 UIA pattern 명령으로 한정하고 Stage 1 실제 runner probe에서 가용성을 확정한다.

## 설계 방향

- **별도 Windows GUI workflow**: `.github/workflows/alhangeul-windows-gui.yml`을 수동 `workflow_dispatch` gate로 두고 `build_ref`와 native `run_id`를 필수 입력받는다. native bundle을 재빌드하거나 이름이 같은 최신 artifact를 임의 선택하지 않는다.
- **installer별 격리**: MSI와 NSIS를 하나의 runner에서 순차 설치하지 않고 matrix의 서로 다른 새 runner에서 검증한다. 기존 installer smoke는 registry·handler·shortcut·uninstall 계약을 계속 소유하고, 새 workflow는 설치된 앱의 실제 GUI acceptance를 추가한다.
- **fail-closed handoff**: acceptance checkout SHA, 입력 build SHA, native workflow `head_sha`, exact artifact ID·digest와 내부 inventory/checksum 중 하나라도 다르면 설치 전에 실패한다. Issue #34 verifier와 artifact schema를 재사용한다.
- **공통/플랫폼 경계**: `tests/gui/wdio.shared.conf.ts`, fixture, WebView document UX helper와 evidence schema는 그대로 재사용한다. Windows WebDriver config와 WinApp CLI process/UIA selector·dialog lifecycle만 `tests/gui/windows/` 아래 platform adapter로 둔다.
- **production binary 우선**: 설치된 `Alhangeul.exe`를 외부 `tauri-driver`로 구동한다. Stage 1에서 production binary 또는 GitHub-hosted runner 연결이 불가능하면 embedded plugin이나 제품 runtime 변경으로 자동 전환하지 않고 계획 변경 승인을 요청한다.
- **semantic native UI**: AutomationId와 control pattern을 우선하고, HWND로 열린 dialog를 고정한 뒤 JSON 출력을 파싱한다. localization text나 runtime-dependent slug는 가능한 한 발견용으로만 사용한다. 좌표, 무제한 polling과 flaky retry는 사용하지 않는다.
- **UIA pattern 우선**: CI에서는 `inspect`, `search`, `get-property`, `set-value`, `invoke`, `wait-for`, `screenshot`을 우선한다. OS drag-in은 본질적으로 실제 shell drag가 필요하므로 Stage 1에서 interactive desktop과 source/target semantic bounds를 먼저 확인한 뒤 `winapp ui drag`를 허용하는 유일한 input-injection 예외로 둔다. 이 한정 경로도 성립하지 않으면 drag-in을 몰래 생략하지 않고 계획 변경 승인을 요청한다.
- **tool 공급망 고정**: Microsoft가 CI용으로 권장하는 `setup-WinAppCli` Action을 full immutable commit SHA로 고정하고 `version` 입력도 특정 release로 지정한다. Public Preview의 `latest`와 nightly artifact, winget 자동 갱신은 허용하지 않으며 update check를 CI에서 비활성화한다. `tauri-driver`와 Node/pnpm version을 고정하고 WebView2/Edge driver의 실제 resolved version을 증거에 남긴다. WinApp CLI를 cross-platform `pnpm-lock.yaml`에 추가하지 않는다.
- **증거 최소화**: 공개 fixture만 사용하며 UIA tree는 Alhangeul과 그 소유 dialog로 범위를 제한한다. 성공·실패 모두 screenshot, bounded log, 생성 PDF, 환경 version과 manifest를 보존하되 token, 개인 경로와 unrelated desktop/window 정보는 정규화하거나 수집하지 않는다.
- **비용과 잔여 gate**: 표준 GitHub-hosted runner만 사용하고 larger/self-hosted/유료 fallback은 두지 않는다. 공개 릴리즈 및 인쇄·글꼴·WebView upstream 변경 때 Windows 10/11 실기기 검증을 유지하며 일반 exact-SHA 후보는 자동 결과로 수용한다.
- **post-merge close gate**: 새 manual workflow는 default branch merge 전 실제 `workflow_dispatch`가 제한되므로 PR 전에는 정적·계약·중립 검증과 activation checklist를 완료한다. merge 후 MSI·NSIS 실제 canary와 evidence read-back까지 성공한 뒤 Issue #35를 닫는다.
- **merge 전 branch probe**: 새 workflow 자체는 default branch 반영 전 dispatch할 수 없으므로 Stage 1에서는 이미 default branch에 존재하는 `.github/workflows/alhangeul-desktop.yml`의 task branch 버전에 명시적 opt-in Windows GUI probe job을 잠정 추가하고 `--ref publish/task35`로 실제 runner를 측정한다. probe hook은 별도 acceptance workflow가 완성되면 제거하며, 중복 없는 장기 진단 가치가 확인되어 수행계획 변경 승인을 받은 경우에만 최종 변경으로 남긴다.

## 리스크

- **GitHub-hosted desktop 제약**: UIA pattern 명령은 CI 친화적이지만 일부 system dialog나 print path가 interactive desktop 또는 secure desktop을 요구할 수 있다. Stage 1에서 실제 `windows-2025` probe를 선행하고 OS drag-in 이외의 input injection이나 UAC 우회를 기본 해법으로 삼지 않는다.
- **WinApp CLI 변화 가능성**: Public Preview 도구와 문서가 빠르게 갱신될 수 있다. setup Action commit과 CLI release version을 이중 고정하고 JSON schema/parser 계약 test, 환경 version 증거와 update check 비활성화를 둔다.
- **WebView2/Edge driver 변동**: Evergreen runtime 갱신과 driver mismatch가 session을 깨뜨릴 수 있다. Tauri service의 동기화 경로를 사용하고 resolved runtime/driver version을 기록하며 무조건 재시도로 숨기지 않는다.
- **localized system dialog selector**: 표시 문자열은 runner 언어와 Windows build에 따라 달라질 수 있다. AutomationId, control type, owner HWND와 pattern을 우선하고 runtime slug/text 고정 의존을 최소화한다.
- **WebDriver와 native modal 경합**: WebDriver session이 열린 동안 native dialog가 focus를 가져가면 command가 block될 수 있다. trigger·UIA complete·WebView postcondition을 명시적 coordinator로 직렬화하고 timeout 시 양쪽 증거를 남긴다.
- **installer 권한 차이**: MSI와 NSIS의 install scope·권한·경로가 다르다. 별도 fresh runner job으로 격리하고 secure desktop 조작 없이 silent install한 뒤 non-elevated product UI를 검증한다.
- **민감 정보 과수집**: 전체 desktop UIA tree와 screenshot은 unrelated 정보가 섞일 수 있다. 공개 fixture와 app/owner dialog scope로 제한하고 path/token 정규화 후 artifact를 생성한다.
- **workflow 비용·시간**: MSI·NSIS 전체 GUI가 Windows runner 시간을 소비한다. manual gate, matrix fail-fast 비활성, bounded timeout과 최소 artifact를 사용하며 유료 runner로 우회하지 않는다.
