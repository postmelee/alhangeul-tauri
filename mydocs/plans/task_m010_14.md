# Task #14 수행계획서 — Windows Explorer HWP/HWPX 첫 페이지 썸네일

GitHub Issue: [#14](https://github.com/postmelee/alhangeul-tauri/issues/14)
마일스톤: M010

## 목적

Alhangeul로 한 번도 열거나 저장하지 않은 HWP/HWPX 문서도 Windows Explorer가 처음 표시할 때 문서 첫 페이지 기반 썸네일을 제공한다. Explorer의 격리된 Shell extension process에서 동작하는 Windows x64 COM Thumbnail Handler를 만들고, Tauri 앱·WebView·별도 사용자 UI를 시작하지 않은 채 `rhwp` 네이티브 렌더링 경로를 사용한다.

직접 첫 페이지 렌더링을 주 경로로 사용하고 실패할 때만 문서 내 `PrvImage`를 사용한다. 두 경로가 모두 실패하면 handler가 실패를 반환해 Explorer가 등록된 Alhangeul 문서 아이콘으로 안전하게 저하되도록 한다. 설치·업데이트·제거 과정에서는 기존 한컴 2020 등 다른 제품의 Thumbnail Handler와 파일 연결 상태를 보존한다.

## 배경

현재 `apps/desktop/src-tauri/src/commands.rs`의 `render_document_preview`는 파일을 읽고 `editable_core_from_bytes`와 `render_page_svg_native(0)`를 호출해 첫 페이지 SVG를 만들 수 있다. 그러나 이 경로는 Tauri command와 desktop session 모듈에 묶여 있어 Explorer가 직접 로드할 수 있는 독립 COM DLL의 재사용 경계가 아니다. `rhwp`에는 HWP `/PrvImage`와 HWPX `Preview/PrvImage.*` 추출 경로도 이미 있으므로 `third_party/rhwp`를 수정하지 않고 제품 소유 adapter에서 직접 렌더와 내장 preview fallback을 조합할 수 있다.

Task #11과 #13에서 MSI/NSIS의 HWP/HWPX `OpenWithProgids`, 기존 기본 연결 보존, 설치·제거 smoke가 정립됐지만 Thumbnail Handler CLSID·Shell extension 등록과 DLL artifact는 아직 없다. Task #13은 완료됐으며, 본 task의 exact-SHA 결과는 공개 후보 준비 Issue #9의 Windows Explorer 통합 입력이 된다. Windows ARM64는 Issue #10의 결과에 따라 별도로 판단한다.

Microsoft의 Thumbnail Handler 계약은 `IThumbnailProvider`와 초기화 인터페이스를 함께 구현하도록 하며 새 handler에는 `IInitializeWithStream`과 기본 process isolation 유지를 권장한다. Explorer는 파일 수정 시각을 기준으로 자체 thumbnail cache를 갱신하고, handler는 요청한 최대 크기 안에서 원래 종횡비를 유지한 비정사각 이미지를 반환해야 한다. 따라서 제품 자체 영구 cache, 정사각 padding, application overlay나 adornment는 도입하지 않는다.

## 설계 방향

- **소유 계층 분리**: 첫 페이지 SVG와 내장 preview 선택은 `rhwp`에 의존하되 Tauri·COM·Win32에 의존하지 않는 공유 Rust crate가 소유한다. Desktop의 `render_document_preview`는 이 crate의 얇은 adapter가 되고, Windows DLL은 stream·COM·bitmap 변환만 소유한다. 구체적인 crate 경로와 Cargo build topology는 Stage 1에서 기존 독립 `src-tauri` manifest·lock 계약을 보존하는 안으로 확정한다.
- **격리 COM 경계**: handler는 `IInitializeWithStream`을 첫 선택으로 구현하고 `DisableProcessIsolation`을 등록하지 않는다. Explorer가 제공한 stream만 읽으며 path 접근, Tauri runtime, WebView, window, dialog, child UI와 제품 store를 사용하지 않는다. COM apartment/threading model과 DLL unload 조건은 Windows SDK 계약에 맞춰 Stage 1에서 고정한다.
- **fallback 순서**: `직접 첫 페이지 SVG → 내장 preview image → HRESULT 실패` 순서를 고정한다. 직접 렌더가 성공하면 오래됐을 수 있는 내장 preview를 사용하지 않는다. 마지막 단계는 application icon을 bitmap에 합성하지 않고 실패를 반환해 Explorer가 기존 icon 경로를 사용하게 한다.
- **bitmap 계약**: `cx`를 두 축의 최대값으로 사용해 페이지 전체를 축소하고 종횡비를 유지한다. 정사각 padding, crop, application overlay와 drop shadow를 넣지 않는다. 0·비정상·과대 크기는 검증된 범위로 fail-closed 처리하며 BGRA row layout, alpha type과 `HBITMAP` ownership을 Windows 단위 test로 고정한다.
- **cache 소유권**: 문서별 영구 cache를 제품에 추가하지 않는다. 반복 요청과 수정 시각 기반 invalidation은 Explorer thumbnail cache가 소유하며, handler는 같은 stream·크기에서 결정적인 결과를 반환하는 stateless provider로 유지한다. cache 갱신 검증은 원본 수정 시각을 명시적으로 바꾼 Windows Explorer 시나리오로 수행한다.
- **resource budget**: 허용 파일 byte, stream read, SVG byte, decoded image dimension, 요청/출력 pixel, 단일 호출 시간과 동시 작업 수의 구체값은 Stage 1 fixture benchmark와 Windows surrogate 관찰로 정하고 구현계획서 승인 항목으로 올린다. 각 phase 전후 budget을 검사하고 초과·암호화·미지원·panic은 preview 또는 icon fallback으로 전환한다. Rust unwind가 COM ABI를 넘지 않게 모든 FFI entry를 방어한다.
- **등록 보존**: HWP/HWPX extension의 thumbnail Shell extension GUID와 Alhangeul COM CLSID 등록을 별도 계약으로 둔다. 설치 전 hive/view/value 종류와 부재 상태를 제품 전용 transaction record에 snapshot하고, 제거 때 현재 값이 여전히 Alhangeul 소유인 경우에만 원래 값을 복원한다. 설치 뒤 다른 제품이나 사용자가 바꾼 값은 제거 과정에서 덮어쓰지 않는다. MSI per-machine과 NSIS per-user의 merged HKCR precedence를 실제 registry view에서 각각 검증한다.
- **업데이트·rollback**: 동일 버전 재설치, 업그레이드, 설치 중단, 제거와 MSI rollback에서 DLL·CLSID·extension 등록·backup state가 서로 갈라지지 않게 한다. DLL이 사용 중일 때의 교체/제거와 Explorer cache·process refresh 절차를 installer test에 포함하되 Explorer나 전체 Shell process를 무차별 종료하지 않는다.
- **제품 독립성**: handler 차단·등록 실패·렌더 실패가 `Alhangeul.exe`, HWP/HWPX open/save, 기존 file association에 영향을 주지 않게 DLL과 앱 실행 경계를 분리한다. 로그에는 문서 path·내용·텍스트를 기록하지 않고 오류 범주와 제한 초과 여부만 test 진단에 남긴다.
- **플랫폼 경계**: 구현과 feature acceptance는 Windows x64에서 수행한다. 공유 Rust 경계로 인해 기존 desktop build에 회귀가 없는지는 승인된 Windows/Linux native matrix로 확인하지만 Linux용 thumbnail 기능은 만들지 않는다. 현재 macOS host에서는 Rust desktop/handler 성공이나 Tauri native build를 주장하지 않는다.

## 잠정 단계

- **Stage 1 — COM·공유 renderer·installer 계약 확정**
  - 현재 Tauri preview 경계, `rhwp` direct/preview API, Cargo build topology, COM ABI/threading, registry precedence와 MSI/NSIS transaction을 조사한다.
  - HWP/HWPX fixture matrix와 Windows benchmark로 resource budget 후보를 정하고 정확한 파일·의존성·검증·커밋 단위를 구현계획서에 고정한다.
- **Stage 2 — Tauri 비의존 첫 페이지 렌더 경계 분리**
  - bounded bytes에서 format을 판별하고 direct SVG와 embedded preview를 순서대로 제공하는 공유 Rust API를 만든다.
  - 기존 Tauri `render_document_preview`를 공유 API로 전환하고 HWP/HWPX·실패·원본 무수정 회귀를 검증한다.
- **Stage 3 — Windows COM Thumbnail Handler와 bitmap 변환**
  - `IInitializeWithStream`, `IThumbnailProvider`, class factory·DLL lifecycle과 SVG/preview → BGRA `HBITMAP` 변환을 구현한다.
  - panic·limit·손상·암호화·동시 요청 방어, 종횡비·alpha·ownership과 Tauri/WebView 미기동을 Windows native test로 검증한다.
- **Stage 4 — MSI/NSIS 등록·공존·rollback 통합**
  - handler DLL을 Windows x64 bundle에 포함하고 COM·HWP/HWPX Shell extension 등록과 기존 handler snapshot/조건부 복원을 구현한다.
  - MSI/NSIS clean install·update·reinstall·uninstall·rollback, 한컴 sentinel 공존과 artifact inventory를 자동 검증한다.
- **Stage 5 — 플랫폼 중립 회귀·공식 문서 정렬**
  - product/upstream/Studio/automation/build gate와 source contract를 통과시키고 실제 구현 경계를 공식 제품·아키텍처·개발·운영 문서에 반영한다.
  - Stage 6 수동 수용 matrix, 미서명/차단 정책과 Issue #9 handoff 조건을 확정한다.
- **Stage 6 — Windows x64 exact-SHA Explorer 수용**
  - exact SHA의 Windows x64 MSI/NSIS를 실제 Windows 환경에서 설치하고 Explorer 크기·DPI·cache·문서별 fallback·한컴 공존을 검증한다.
  - 기존 Windows/Linux native matrix 회귀, artifact inventory와 SHA-256을 확인하고 공개 후보 포함 가능 여부와 잔여 제한을 기록한다.

## 검증 계획

### 단계별 검증

- Stage 1
  - current `render_document_preview`와 `rhwp` native render/preview API inventory
  - Windows SDK의 `IThumbnailProvider`·`IInitializeWithStream`·process isolation·registration 계약 검토
  - HWP/HWPX 정상·preview 없음·stale preview·손상·대용량 fixture별 시간/peak memory benchmark

- Stage 2
  - 공유 Rust crate의 HWP/HWPX 첫 페이지 SVG·embedded preview·fallback 우선순위 test
  - file/stream byte 상한, unsupported/encrypted/corrupt input과 원본 byte·size·mtime 불변 test
  - desktop command가 공유 API만 호출하고 Tauri session/parser 구현을 복제하지 않는지 검증

  - Windows x64 DLL export와 CLSID/class factory activation test
  - memory `IStream` 초기화, 중복 초기화 거부, requested `cx`별 HBITMAP width/height/stride/alpha/종횡비 test
  - direct render 성공 시 stale preview 비사용, direct 실패 시 preview, 둘 다 실패 시 HRESULT fallback test
  - panic/oversize/invalid SVG/image/time budget·반복/동시 요청과 DLL unload test
  - handler 요청 중 `Alhangeul.exe`, WebView2 UI process, window/dialog와 network/file write가 발생하지 않는지 확인

## 리스크

- **COM ABI와 panic**: 잘못된 reference count, apartment model, export 또는 Rust unwind는 surrogate를 종료시킬 수 있다. 얇은 FFI 계층, `catch_unwind`, HRESULT 변환, activation/unload stress test로 방어한다.
- **비신뢰 문서 비용**: `rhwp` parse/layout은 입력에 따라 오래 걸리거나 큰 메모리를 사용할 수 있고 내부 호출 중간에 강제 취소하기 어렵다. 사전 byte/pixel 제한, phase budget과 Explorer process isolation을 함께 사용하고, hard deadline을 보장할 수 없는 경로는 Stage 1에서 별도 worker 필요성까지 비교해 구현계획서에 명시한다.
- **렌더 품질과 font**: DllHost의 font 환경과 SVG rasterizer가 앱/PDF와 다르면 한글 glyph·그림·비율이 달라질 수 있다. 제품 font 정책과 라이선스를 재사용하고 대표 fixture의 bitmap read-back을 수행한다.
- **embedded preview 안전성**: preview image가 손상되거나 과대 dimension을 선언할 수 있다. decode 전에 format/dimension/byte limit을 적용하고 실패하면 icon 경로로 저하한다.
- **registry precedence 충돌**: HKLM/HKCU merged HKCR와 한컴 installer가 같은 Shell extension value를 바꿀 수 있다. scope별 raw state를 기록하고 Alhangeul 값일 때만 복원해 제3자 변경을 보존한다.
- **installer rollback과 사용 중 DLL**: Explorer surrogate가 DLL을 로드한 상태에서 update/uninstall하면 파일·registry가 부분 상태로 남을 수 있다. MSI component/NSIS transaction 순서, 재부팅 필요 상태와 targeted Shell refresh를 실제 installer에서 검증한다.
- **cache 오판**: Explorer cache는 OS가 소유하므로 handler 호출 횟수만으로 cache 성공을 단정할 수 없다. mtime·화면 결과·필요 시 ETW/Process Monitor 증거를 함께 기록하고 제품 자체 cache를 추가하지 않는다.
- **미서명 차단**: 정책에 따라 DLL만 차단될 수 있다. handler 등록/로드 실패를 앱 설치·실행 실패와 분리하고 unsigned 제한을 운영 문서와 수용 결과에 명시한다.
- **artifact 크기와 build 복잡도**: desktop과 handler가 `rhwp`를 각각 link하면 installer 크기와 build 시간이 늘 수 있다. 공유 source 경계는 유지하되 binary 중복·LTO·Cargo lock topology를 Stage 1에서 측정하고 독립성보다 먼저 최적화하지 않는다.
- **Windows ARM64 분기**: x64 COM DLL을 ARM64 범위로 오인할 수 있다. package/PE architecture와 registry view를 x64로 고정하고 ARM64는 Issue #10 결과 전까지 생성·등록하지 않는다.
