# Task #19 수행계획서 — PDF snapshot과 stale job 회수 경계

GitHub Issue: [#19](https://github.com/postmelee/alhangeul-tauri/issues/19)
마일스톤: M010

## 목적

직접 PDF 내보내기가 시작 시점의 한 문서 상태만 사용하도록 고정해, 페이지 SVG를 순차 수집하는 동안 편집이 발생하더라도 서로 다른 문서 revision이 한 PDF에 섞이지 않게 한다.

WebView reload, 창 종료, timeout과 변환 실패로 정상 완료되지 못한 native PDF job과 OS 임시 SVG를 회수한다. 기존의 같은 target 잠금, searchable PDF와 outlined fallback, atomic target replace, source dirty/session/recent 불변 계약은 유지한다.

## 배경

현재 `DesktopPersistence.exportPdf()`는 active Studio handler에서 `pageCount()`를 얻은 뒤 각 `getPageSvg(page)`를 `await`하며 native job에 전달한다. 각 페이지 호출 사이에 편집이 들어오면 앞뒤 페이지가 다른 문서 상태에서 렌더될 수 있지만, native job은 owner·target·페이지 순서만 확인하므로 이를 식별하지 못한다.

native `PdfExportJobs`는 `TempDir`로 정상 abort·commit·window destroy 시 임시 파일을 회수하고 같은 target의 동시 작업을 막는다. 그러나 WebView reload는 native window를 파괴하지 않으므로 job record와 target 잠금이 프로세스 종료까지 남을 수 있고, 비정상 종료 뒤 OS temp의 `.alhangeul-pdf-*` 디렉터리를 다음 실행에서 정리하는 경계도 없다.

Task #19는 Issue #34의 Linux GUI 자동 수용과 병렬로 시작하며, Task #20의 dispatcher·embed handler lifecycle 정리도 별도 worktree에서 진행 중이다. 따라서 이번 task는 `command/dispatcher.ts`, `embed/desktop-runtime.ts`, `core/platform.ts`와 native `desktop_platform`을 수정하지 않는 경계를 우선한다. 해당 파일이 필요해지면 Task #20과의 통합 순서를 확인하고 수행계획 보정 승인을 받는다.

## 범위

### 포함

- 현재 문서 형식(HWP/HWPX)의 serializer bytes를 한 번 캡처하고 격리된 WASM 문서 인스턴스로 재로딩해 page count와 모든 SVG를 같은 immutable snapshot에서 생성하는 Studio 경계
- snapshot 생성·페이지 렌더·해제 lifecycle과 HWP/HWPX 대표 fixture의 원본 대비 쪽 수·본문·페이지 SVG 정합성 검증
- snapshot 식별자와 page count를 native PDF job에 결속하고 다른 snapshot, 중복·누락·역순 페이지를 fail-closed 처리하는 command 계약
- page count, 단일 SVG bytes, 누적 SVG bytes, job 수명과 동시 job 수에 대한 bounded limit
- 새 export 시작 시 같은 window owner의 중단 job 회수, window destroy 회수, TTL 기반 stale job 회수
- 애플리케이션 시작 시 충분히 오래된 `.alhangeul-pdf-*` orphan temp 디렉터리를 prefix·age·directory 검증 뒤 제한된 개수만 정리하는 경계
- 편집 중 export, WebView reload, timeout, append/변환 실패, 같은 target 경합과 비정상 종료 흔적의 focused test
- Windows x64와 Linux x64 exact-SHA에서 직접 PDF의 쪽 수, searchable 한글 text, source state 불변과 임시 파일 회수 검증

## 설계 방향

- PDF page surface의 진실 원천은 live editor가 아니라 export 시작 시 한 번 만든 immutable snapshot으로 둔다. active document를 현재 형식의 serializer bytes로 캡처하고 별도 WASM document에 로드한 뒤, 그 인스턴스에서 page count와 모든 page SVG를 생성한다.
- snapshot 캡처는 source save나 `notifySaved`를 호출하지 않고 active document의 file path, format, native revision, dirty, recent와 upstream recovery 상태를 바꾸지 않는다. snapshot 인스턴스는 성공·실패·취소 모두에서 명시적으로 해제한다.
- HWP/HWPX serializer round-trip 뒤의 page count와 대표 SVG 구조가 live document와 동등한지 Stage 1 fixture로 먼저 검증한다. 조판 손실 또는 허용할 수 없는 메모리 증가가 확인되면 mutation lock이나 revision guard로 임의 전환하지 않고 대안과 영향 범위를 문서화해 수행계획 보정 승인을 요청한다.
- native job은 `snapshotId`, 예상 page count, owner window, target path, 생성·최근 활동 시각과 누적 SVG bytes를 소유한다. 모든 append·commit에서 owner/snapshot/page order/limit/expiry를 함께 검증한다.
- 새 begin은 먼저 expired job을 회수하고 같은 window owner의 이전 미완료 job을 정리한다. target lock은 다른 window의 유효 job에 대해서만 유지한다. window destroy cleanup은 기존 경계를 보존한다.
- orphan temp cleanup은 OS temp 루트 바로 아래의 제품 prefix directory만 대상으로 하고, symlink·최근 항목·한도 초과 항목은 건드리지 않는다. 사용자 문서 경로나 target PDF를 재귀 정리 대상으로 사용하지 않는다.
- limit과 TTL의 구체값은 대표 6쪽 fixture와 긴 문서 focused test에서 page/SVG 크기와 실행 시간을 측정한 뒤 구현계획서에 고정한다. limit 초과는 target을 바꾸지 않은 채 명시적 오류와 cleanup으로 끝낸다.
- Task #20과 충돌을 피하기 위해 우선 예상 변경을 새 snapshot module, `DesktopPersistence`/`DesktopHost`, native PDF job·command에 한정한다. Task #20 또는 #34가 먼저 merge되면 승인 후 최신 `devel`을 통합하고 focused·전체 gate를 다시 실행한다.

## 잠정 단계

- **Stage 1 — immutable PDF snapshot 계약**
  - 현재 형식 serializer bytes로 격리 snapshot을 만들고 같은 snapshot의 page count·SVG만 반환하는 lifecycle을 구현한다.
  - HWP/HWPX round-trip 조판 정합성, export 중 live 편집과 source dirty/session 불변, snapshot 해제를 focused test로 검증한다.
- **Stage 2 — native job freshness와 resource limit**
  - snapshot 결속, owner/target/page order 검증, TTL·same-owner recovery, page/SVG/job limit과 orphan temp cleanup을 구현한다.
  - 만료·reload·실패·경합에서 target 보존과 temp/job 회수를 Rust test로 검증한다.
- **Stage 3 — Studio/native 통합과 공식 문서 정렬**
  - snapshot pipeline을 direct PDF command에 연결하고 cancel·timeout·fallback·동시 요청 회귀를 검증한다.
  - 공식 아키텍처와 release 운영 문서에 자동 gate와 잔여 수동 gate를 최소 반영한다.
- **Stage 4 — Windows/Linux exact-SHA 수용**
  - 최신 승인 `devel`을 통합한 exact SHA에서 플랫폼 중립 gate와 Windows/Linux native build·PDF 시나리오를 실행한다.
  - 편집 중 export 결과 일관성, searchable 한글 text, atomic replace, reload/재실행 cleanup과 검증 한계를 기록한다.

### 통합 검증

- 한 PDF의 page count와 모든 page SVG가 하나의 immutable snapshot ID에 결속된다.
- export 중 live editor를 수정해도 결과가 시작 snapshot으로 완성되거나 명시적으로 실패하며 혼합 revision PDF는 target에 commit되지 않는다.
- WebView reload, window destroy, timeout, limit 초과와 변환 실패 뒤 job·temp가 회수되고 기존 target과 source session 상태가 보존된다.
- searchable PDF, outlined fallback 경고, 같은 target 원자 교체와 `notifySaved` 미호출 계약이 유지된다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **serializer snapshot 조판 차이**: 현재 형식 round-trip이 live IR의 일부를 손실하면 PDF가 시작 화면과 달라질 수 있다. Stage 1에서 HWP/HWPX 대표·긴 문서를 비교하고 차이가 있으면 구현을 확대하지 않고 대안 승인으로 되돌린다.
- **메모리·응답 시간 증가**: serializer bytes, 격리 document와 SVG가 일시적으로 공존한다. page/SVG/누적 bytes와 job 시간 limit을 두고 snapshot·native temp를 단계적으로 해제한다.
- **orphan cleanup 오삭제**: OS temp scan이 넓으면 다른 프로세스나 사용자 파일을 건드릴 수 있다. 고정 prefix, 바로 아래 directory, age, symlink 거부, 회수 개수 상한을 모두 만족한 항목만 삭제한다.
- **Task #20 충돌**: dispatcher/embed lifecycle branch가 병렬 진행 중이다. 해당 파일을 수정하지 않는 방향을 우선하고, 실제 필요 시 두 task의 diff와 merge 순서를 승인받는다.
- **Task #34 exact-SHA 변동**: Linux GUI acceptance 보정이 아직 진행 중이다. 과거 성공 artifact를 재사용하지 않고 #34 correction merge 이후 최신 기준으로 Stage 4를 실행한다.
- **지원 환경 제한**: 현재 macOS host에서는 Rust desktop/Tauri 성공을 주장하지 않는다. Rust·Tauri와 실제 PDF 수용은 Windows/Linux native 환경에서만 완료 판정한다.

## 승인 요청 사항

- live editor의 순차 `getPageSvg` 대신 현재 형식 serializer bytes로 만든 격리 WASM immutable snapshot을 직접 PDF의 진실 원천으로 사용하는 방향
- snapshot round-trip 정합성 또는 자원 한계가 실패하면 mutation lock/revision guard로 자동 전환하지 않고 수행계획을 보정하는 gate
- native job에 snapshot·owner·target·page/bytes/time limit을 결속하고 same-owner begin, TTL, window destroy와 app startup orphan cleanup을 함께 소유하게 하는 범위
- 공식 문서는 기존 `docs/architecture/UPSTREAM.md`와 `docs/operations/DESKTOP_RELEASE.md`만 최소 보정하는 위치 판단
- Task #20의 dispatcher/embed lifecycle 파일을 피하고, #34·#20 선행 merge가 생기면 최신 `devel` 통합 후 재검증하는 병렬 작업 경계
- macOS에서는 플랫폼 중립 검증만 수행하고 Rust desktop/Tauri·실제 PDF 수용은 Windows/Linux exact-SHA 환경에서 완료하는 검증 범위

승인되면 `task_m010_19_impl.md`에서 단계별 산출물, 검증 명령, limit/TTL 값, 커밋 메시지와 Task #20·#34 통합 순서를 구체화한다.
