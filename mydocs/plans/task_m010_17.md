# Task #17 수행계획서 — Linux 파일 관리자 HWP/HWPX 첫 페이지 썸네일

GitHub Issue: [#17](https://github.com/postmelee/alhangeul-tauri/issues/17)
마일스톤: M010

## 목적

Alhangeul로 한 번도 열거나 저장하지 않은 로컬 HWP/HWPX 문서도 지원 대상 Linux 파일 관리자에서 첫 페이지 기반 썸네일을 표시한다. Tauri·WebView·별도 UI를 시작하지 않는 Linux x64·arm64 Rust thumbnailer와 Freedesktop `.thumbnailer` 등록을 만들고, DEB·RPM 설치·업데이트·제거 과정에서 Alhangeul 소유 파일만 관리한다.

Task #14에서 병합된 `crates/document-preview`의 native direct render, embedded preview 추출·raster, pinned NotoSansKR와 resource limit을 재사용한다. 직접 렌더가 성공하면 오래됐을 수 있는 내장 preview보다 우선하고, 직접 렌더 실패 시에만 유효한 preview를 사용한다. 두 경로가 모두 실패하면 부분 PNG를 남기지 않고 비정상 종료해 파일 관리자가 기존 MIME icon으로 안전하게 저하하도록 한다.

## 배경

Task #14/PR #46은 Windows Explorer용 COM handler를 구현하면서 Tauri 비의존 `crates/document-preview`, 독립 worker protocol, 64 MiB 입력·16 MiB SVG·최대 1024 px 출력, process-local font와 대표 raster 회귀를 정립했다. Windows 구현에서 얻은 핵심 교훈은 Shell/UI process 안에서 문서를 parse하지 않는 것, renderer 결과를 성공 코드만으로 판정하지 않는 것, cache와 최종 icon fallback을 OS에 맡기는 것, 설치·제거가 다른 프로그램의 연결을 변경하지 않는 것이다.

Linux에서는 파일 관리자가 `.thumbnailer`의 외부 명령을 시작하므로 COM handler를 복제할 필요가 없다. 대신 `%i`·`%o`·`%s` 인자, PNG와 임시 파일/atomic rename, XDG thumbnail cache의 URI·mtime 검증, GNOME Files와 Thunar/Tumbler의 discovery·failure 동작을 실제 환경에서 먼저 확인해야 한다. Freedesktop 표준의 normal/large/x-large/xx-large 크기 128/256/512/1024 px는 현재 공유 core의 최대 edge 1024 px와 정렬된다.

현재 native workflow는 Linux x64에서 Tauri 기본 bundle 전체를, Linux arm64에서 DEB를 생성한다. Tauri config에는 Linux custom files나 package lifecycle script가 아직 없다. Stage 1은 x64 DEB·RPM과 arm64 DEB를 1차 package matrix로 검증하고, arm64 RPM은 현재 workflow·실행 환경과 Issue 수용 범위를 대조해 구현계획서 승인 항목으로 확정한다.

## 설계 방향

- **공유 core 재사용**: HWP/HWPX parse, first-page SVG, embedded preview, NotoSansKR와 byte/pixel 상한은 `crates/document-preview`를 단일 진실 원천으로 유지한다. Linux adapter는 path·CLI·PNG·atomic output만 소유하며 기존 Windows protocol·BGRA 결과를 깨는 플랫폼 분기를 공유 core에 넣지 않는다.
- **Linux 실행 경계**: `.thumbnailer`는 절대 설치 경로의 binary를 `%i %o %s`로 호출한다. `%u` remote URI는 사용하지 않고 local regular file만 연다. Tauri app, WebView, window, dialog, product store와 network를 시작하지 않는다.
- **격리 방식은 계측 후 확정**: 외부 thumbnailer process 자체가 파일 관리자와 분리돼 있지만 blocking native render를 process 내부 thread만으로 안전하게 중단할 수 있는지는 별도 문제다. Stage 1에서 GNOME/Tumbler timeout, x64·arm64 cold render와 RSS를 계측하고, 단일 process watchdog·self worker·기존 worker protocol 재사용을 비교해 hard deadline과 memory cap 방식을 구현계획서에서 승인받는다.
- **fallback과 실패 소유권**: direct render 성공 결과만 최종 선택하고 실패할 때 preview를 사용한다. 둘 다 실패하면 app icon PNG를 임의 생성하지 않고 출력 부재와 명시적 exit code로 파일 관리자의 MIME icon/failure cache에 맡긴다.
- **PNG와 atomic output**: 요청 edge를 두 축 최대값으로 사용해 비율을 보존하고 alpha PNG를 만든다. 최종 `%o`를 직접 스트리밍하지 않고 sibling temporary file에 완성·decode 검증한 뒤 rename한다. 오류·panic·deadline에는 temporary와 final partial file을 남기지 않는다.
- **cache 소유권**: 제품 자체 persistent thumbnail cache를 만들지 않는다. XDG cache의 URI·mtime·size/failure 기록은 파일 관리자가 소유하며, Alhangeul은 결정적 output을 제공한다. 원본 수정 전후 UI와 cache metadata를 함께 관찰하되 전체 cache를 삭제해 성공을 만들지 않는다.
- **선언적 package 우선**: helper와 `.thumbnailer`는 DEB/RPM package manifest의 custom files로 설치·제거한다. discovery refresh가 실제로 필요하다고 Stage 1에서 확인한 경우에만 최소 lifecycle script를 도입하며, MIME default와 다른 프로그램 등록은 읽거나 변경하지 않는다.
- **지원 matrix**: 1차 제안은 x64에서 DEB·RPM과 GNOME Files·Thunar/Tumbler, arm64에서 native binary·DEB·MIME/thumbnail output이다. arm64 RPM과 GUI file-manager 수용 가능 여부는 runner/VDI 가용성을 Stage 1에서 확인해 구현계획서에 확정하고, 검증하지 않은 조합을 지원 완료로 표현하지 않는다.
- **회귀와 병렬 작업**: Task #20·#35·#45가 건드릴 수 있는 `package.json`, Tauri config, native workflow·운영 문서는 Stage 진입 전 최신 `devel`과 diff를 대조한다. 다른 task 변경을 되돌리지 않고 충돌 시 범위와 통합 순서를 작업지시자에게 보고한다.

## 잠정 단계

- **Stage 1 — Freedesktop·file manager·resource·package 계약 확정**
  - GNOME Files와 Thunar/Tumbler의 `.thumbnailer` discovery, `%i %o %s`, success/failure/cache 동작을 실제 Linux x64에서 probe한다.
  - 대표 HWP/HWPX의 x64·arm64 cold render 시간·peak RSS와 file-manager timeout을 계측하고 process/deadline/memory, binary 경로와 package matrix를 구현계획서에 확정한다.
- **Stage 2 — bounded Linux CLI와 atomic PNG 구현**
  - 공유 `document-preview`를 사용하는 local-file CLI, direct-first/preview fallback, PNG 변환과 sibling temp→rename을 구현한다.
  - 인자·크기·원본 불변·손상·preview 없음/오래됨·부분 output·Tauri/WebView/network 미기동을 Rust와 source test로 검증한다.
- **Stage 3 — GNOME Files·Thunar/Tumbler 통합과 cache 수용**
  - system-wide `.thumbnailer`를 연결하고 HWP/HWPX MIME discovery, 128/256/512/1024·임의 크기와 비율·alpha를 확인한다.
  - 미열람 문서, 반복 cache, 원본 mtime·내용 변경 뒤 invalidation, 실패 cache와 MIME icon fallback을 실제 UI에서 검증한다.
- **Stage 4 — DEB·RPM 설치·업데이트·제거 통합**
  - 승인된 x64/arm64 package matrix에 helper와 `.thumbnailer`를 declarative custom files로 포함한다.
  - clean install, same-version reinstall/update, 실패 rollback과 uninstall 뒤 제품 소유 파일 부재·다른 default app/thumbnailer 보존을 native smoke로 검증한다.
- **Stage 5 — 플랫폼 중립 회귀·공식 문서 정렬**
  - locked Cargo, product/upstream/Studio/automation/build와 artifact inventory를 통과시키고 구현된 Linux 지원·제외·운영 경계를 공식 문서에 반영한다.
  - final exact-SHA GUI/package matrix와 검증하지 못한 환경을 확정한다.
- **Stage 6 — Linux x64·arm64 exact-SHA native 수용**
  - exact SHA의 Linux x64 DEB/RPM과 arm64 승인 package를 clean native 환경에 설치해 helper·PNG·MIME·cache·GUI·제거를 수용한다.
  - artifact ID/digest, binary/package inventory와 원본 불변·resource evidence를 기록하고 KDE·AppImage·sandbox 미지원 경계를 유지한다.

### 통합 검증

- Alhangeul로 열거나 저장하지 않은 HWP/HWPX에서 지원 Linux file manager가 현재 첫 페이지 썸네일을 표시한다.
- direct render가 성공하면 embedded preview보다 우선하고 실패 시 preview 또는 파일 관리자의 MIME icon으로 안전하게 저하된다.
- 원본 문서 hash·size·mtime이 요청 전후 같고, final output 외 문서·인접 경로·제품 store 쓰기와 network가 없다.
- 128/256/512/1024와 임의 요청 크기에서 비율·alpha·대표 text/image/table이 유지되고 승인 resource limit을 넘지 않는다.
- 반복 요청은 file manager cache를 사용하며 원본 mtime·내용 변경 뒤 새 결과로 갱신된다.
- 대용량·손상·암호화·미지원 문서가 file manager/thumbnail service를 중단시키거나 partial PNG·orphan process를 남기지 않는다.
- 승인된 DEB/RPM 설치·업데이트·제거 뒤 Alhangeul 소유 helper/registration만 변경되고 기존 MIME default·제3자 thumbnailer는 보존된다.
- x64·arm64 중 실제 검증한 package/file-manager 조합만 지원 완료로 표시하고 KDE·AppImage·sandbox 범위는 제외한다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **blocking render와 hard deadline**: native render 중간 취소가 불가능하면 외부 process라는 사실만으로 1,500 ms 같은 hard deadline을 보장할 수 없다. Stage 1에서 file-manager timeout과 RSS를 실측하고 self worker 또는 process-level kill/resource cap을 비교한다.
- **Linux 배포판·파일 관리자 차이**: GNOME·Tumbler 버전, MIME database와 failure cache 정책이 다를 수 있다. 검증 배포판·버전을 exact evidence로 고정하고 다른 환경을 일반화하지 않는다.
- **PNG alpha·color 변환**: 공유 core는 premultiplied BGRA를 반환하므로 잘못된 unpremultiply/encode는 가장자리와 투명 배경을 손상시킬 수 있다. 대표 pixel·decode roundtrip과 시각 gate를 함께 둔다.
- **cache 오판**: cache hit·failure cache·mtime invalidation은 파일 관리자가 소유한다. 전체 cache 삭제로 통과시키지 않고 output 호출 횟수, metadata와 UI 결과를 결합해 판정한다.
- **package lifecycle**: Tauri DEB/RPM custom file 경로와 script 지원이 달라 과도한 install hook을 만들 수 있다. manifest 소유 삭제를 우선하고 실제로 필요한 refresh만 최소 script로 승인받는다.
- **arm64 검증 가용성**: 현재 workflow는 arm64 DEB만 명시한다. RPM/GUI 환경이 없으면 helper·package 경계까지만 증명하고 미검증 조합은 수용에서 제외한다.
- **병렬 task 충돌**: Task #20·#35·#45가 Tauri config, package script, workflow와 운영 문서를 변경할 수 있다. Stage 진입마다 최신 `devel` 차이를 확인하고 임의 rebase/overwrite 없이 통합 순서를 승인받는다.
- **fixture와 개인정보**: 실제 사용자 문서를 저장소·artifact·log에 넣지 않는다. 공개 fixture와 hash·resource/output 구조만 기록하고 문서 path·text를 로그로 남기지 않는다.

## 승인 요청 사항

- Task #14의 `crates/document-preview`를 재사용하고 Linux adapter가 CLI·PNG·atomic output만 소유하는 방향
- Stage 1 실측 뒤 hard deadline/memory 격리 방식을 구현계획서에서 확정하고 Windows COM 구조를 그대로 복제하지 않는 방향
- local `%i` 입력, `%o` sibling temp→atomic rename, `%s` 1~1024 px와 `direct → preview → nonzero/MIME icon` 계약
- 제품 persistent cache를 만들거나 전체 XDG cache를 삭제하지 않고 GNOME/Tumbler의 URI·mtime cache를 검증하는 방향
- helper와 `.thumbnailer`를 declarative package files로 우선 관리하고 필요성이 입증될 때만 lifecycle script를 추가하는 방향
- 1차 수용 matrix를 x64 DEB·RPM/GNOME Files·Thunar, arm64 native helper·DEB로 두고 arm64 RPM·GUI는 Stage 1 가용성 확인 뒤 확정하는 방향
- 신규 공식 아키텍처 문서를 `docs/architecture/LINUX_THUMBNAILS.md`에 두고 기존 개발·운영·index 문서를 최소 보정하는 위치 판단
- KDE, AppImage 등록, Flatpak/Snap, Preview Pane, 저장 시 PrvImage, Windows/macOS, release·배포를 제외하는 범위

승인되면 `task_m010_17_impl.md`에서 Stage 1 probe의 정확한 host, fixture, 명령, artifact와 이후 단계별 파일·검증·커밋 메시지를 구체화한다.
