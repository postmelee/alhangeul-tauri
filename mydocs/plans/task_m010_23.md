# Task #23 수행계획서 — rhwp Stable 감시와 전체 upstream 동기화 PR 자동화

GitHub Issue: [#23](https://github.com/postmelee/alhangeul-tauri/issues/23)
마일스톤: M010

## 목적

Alhangeul의 유일한 지속 upstream인 `edwardkim/rhwp`의 최신 Stable release를 자동으로
감시하고, 현재 pin과 차이가 있으면 Rust core와 전체 upstream Studio source를 동일한
release tag·resolved commit으로 갱신하는 reviewable draft PR 후보를 생성한다.

자동화는 release를 병합하거나 공개하지 않는다. tag provenance, 갱신 범위와 플랫폼 중립
검증을 기계적으로 제공하고, 별도 수용 task가 source diff와 Windows/Linux native gate를
판정할 수 있는 입력까지만 만든다.

## 배경

- 현재 pin은 `v0.8.2`, resolved commit
  `9b16aa9e23f476e2b335d7c029fc9f24a199d63c`이다.
- 2026-08-12 upstream `v0.8.4`는 draft/prerelease가 아닌 Stable release이며 annotated
  tag가 resolved commit `496333b27d21ddb9114ba9ae340bcb895870c9a7`을 가리킨다.
- `scripts/update-upstream.sh`는 승인된 tag·commit을 검증하고 source submodule, desktop
  Cargo lock, bundled WASM과 `rhwp-core.lock`을 원자적으로 갱신하지만 release 탐지와 PR
  생성을 소유하지 않는다.
- 전체 Studio source는 `third_party/rhwp/rhwp-studio`를 exact Vite root로 사용하므로
  submodule gitlink 갱신이 core와 Studio source를 함께 이동시킨다. 별도 local Studio
  복제본이나 prebuilt shadow bundle을 만들면 안 된다.
- Alhangeul-macOS에는 daily release check와 full sync PR workflow가 있으며 실제
  `v0.8.4` PR #463을 생성했다. 이를 설계 참고로만 사용하고 Tauri의 Windows/Linux,
  `pnpm`, submodule·WASM provenance 경계에 맞춰 구현한다.
- 현재 Tauri 저장소 Actions 기본 권한은 read이며 Actions의 PR 생성·승인 설정은 꺼져
  있다. 자동 PR용 repository variable·secret도 없다. macOS 저장소에만 기존 Alhangeul
  Automation GitHub App 설정이 있다.

## 설계 방향

### Stable release와 provenance 판정

- latest는 GitHub Releases API의 latest Stable 응답을 사용하고 `draft=false`,
  `prerelease=false`, exact `vX.Y.Z`를 다시 검증한다.
- 수동 target tag도 release-by-tag 응답을 조회해 같은 Stable 조건을 적용한다. 존재하는
  Git tag만으로 공개 Stable로 인정하지 않는다.
- release `target_commitish` 문자열을 resolved commit으로 신뢰하지 않는다.
  `git ls-remote`의 `refs/tags/<tag>`와 annotated tag의 `^{}` ref를 해석해 40자리 commit을
  얻고, 갱신 script가 fetch 뒤 같은 commit을 재검증한다.
- current 비교는 `rhwp-core.lock`의 tag·commit을 기준으로 하며, Studio source는 submodule
  gitlink가 그 commit과 일치하고 exact upstream entry 계약이 통과해야 current로 판정한다.

### helper와 파일 크기 경계

- 282 LOC인 `scripts/update-upstream.sh`와 300 LOC를 넘은 기존 test는 확대하지 않는다.
- release resolve/classify, 관리 참조 치환, PR body 생성은 역할별 Node helper와 별도 test로
  분리하고 파일 300 LOC, 함수 50 LOC 권장 상한을 지킨다.
- workflow는 orchestration만 소유하고 release parsing·본문 escaping·치환 규칙을 긴
  inline shell로 중복하지 않는다.
- current pin 문구는 경로·marker·예상 횟수가 모두 일치할 때만 바꾸며 전역 문자열 치환을
  금지한다. release별 known issue 설명은 자동으로 다른 version 이름으로 바꾸지 않는다.

### 자동 PR과 하이퍼-워터폴 경계

- release별 bot-owned branch와 draft PR을 최대 하나 유지한다. 동일 tag의 열린 PR이 있으면
  source history를 rewrite하지 않고 기존 URL을 보고한다.
- merged PR 뒤 남은 branch, 사람이 수정한 branch, branch만 있고 PR이 없는 상태는 자동
  삭제·덮어쓰지 않고 blocker로 보고한다.
- 자동 PR은 merge 가능한 최종 task PR이 아니라 기계 생성 candidate다. Issue #24는
  `local/task24`에서 candidate 변경을 검토·가져오고 계획·native 검증을 완료한 뒤
  `publish/task24` PR을 만든다. 사용한 자동 PR은 별도 승인으로 닫고 branch를 정리한다.
- PR 본문은 자동 검증 성공과 Windows/Linux native 수용 완료를 구분하며 Issue #24를
  자동 close하지 않는다.

### credential과 외부 상태 변경

- resolve·build는 `GITHUB_TOKEN`의 read-only scope로 수행한다. write 직전 job에서만
  `actions/create-github-app-token`으로 installation token을 발급하고 contents·pull request
  최소 권한을 명시한다.
- 기존 Alhangeul Automation GitHub App을 Tauri 저장소에 설치하고
  `ALHANGEUL_AUTOMATION_CLIENT_ID`, `ALHANGEUL_AUTOMATION_APP_PRIVATE_KEY`를 설정하는
  방식을 권장한다. 현재 두 값은 Tauri 저장소에 없으므로 실제 등록은 별도 승인 gate다.
- GitHub App을 쓸 수 없을 때만 `GITHUB_TOKEN` 대안을 다시 승인받는다. repository-wide
  Actions PR 생성·승인 설정을 계획 단계에서 임의로 켜지 않는다.
- workflow·helper merge 전에는 default branch의 schedule과 `workflow_dispatch`가 활성화되지
  않는다. task PR 전에는 helper의 local read-only dry-run과 workflow 계약 test로 no-write
  경로를 검증하고, 실제 draft PR 생성은 task PR merge와 credential 설정 뒤 별도 승인으로
  dispatch한다.

### trigger, concurrency와 실패 정책

- daily schedule은 macOS workflow와 겹치지 않는 UTC 시각으로 분산하고 수동 입력은
  `target_tag`, `dry_run`만 둔다.
- repository·target tag 단위 concurrency는 중복 writer를 직렬화하고 running job을
  취소하지 않는다.
- update/build/check가 하나라도 실패하면 commit·push·PR 생성 전에 중지한다. 실패 시
  자동 reset, branch 삭제, force push를 수행하지 않고 step summary에 실패 단계를 남긴다.
- workflow가 만든 임시 artifact는 provenance 진단용 최소 범위와 짧은 retention만 사용하며
  release asset으로 해석하지 않는다.

## 리스크

- **자동 PR과 task PR 혼동**: bot PR을 draft candidate로 표시하고 Issue #24가 정규 branch와
  계획·보고 절차로 변경을 수용하게 한다.
- **GitHub App 미설정**: read-only dry-run은 가능하지만 write gate는 실패한다. App 설치와
  variable·secret 등록을 별도 승인하고 preflight에서 명확히 중지한다.
- **과도한 workflow 권한**: read job과 write job을 분리하고 App token은 push 직전에만
  contents·pull request 권한으로 발급한다. Actions PR 승인 설정은 켜지 않는다.
- **release/tag spoofing**: Releases Stable metadata와 dereferenced Git tag commit을 모두
  검증하고 갱신 script가 fetch 뒤 재확인한다.
- **혼합 core·Studio release**: submodule, Cargo lock, WASM, pin과 exact Studio entry를
  한 commit에서 검사하고 일부만 성공한 변경은 push하지 않는다.
- **기계 치환의 문서 훼손**: allowlist, marker와 exact count를 사용하고 release별 known issue
  서술은 자동 치환하지 않는다.
- **bot branch 덮어쓰기**: 기존 branch·PR을 자동 삭제하거나 force-push하지 않고 사람이
  수정했거나 branch-only 상태면 blocker로 보고한다.
- **default branch 전용 dispatch**: task PR 전에는 helper local dry-run만 검증하고 실제
  scheduled/write 수용은 merge 뒤 Issue close gate로 남긴다. task PR은 Issue #23을 자동
  close하지 않는다.
- **GitHub API/네트워크 장애**: current로 오판하지 않고 workflow를 실패시키며 다음 schedule
  또는 수동 재실행으로 복구한다.

## Post-merge Stage 4.3 재개 계획 — clean-base automation gate 분리

### 재개 근거

- default branch dry-run `31668192739`는 `v0.8.4`와 resolved commit
  `496333b27d21ddb9114ba9ae340bcb895870c9a7`을 탐지하고 repository write 없이 성공했다.
- GitHub App 설치 범위와 repository variable·secret을 설정한 뒤 실행한 write run
  `31668495052`는 source·lock·WASM·provenance 갱신을 마쳤지만
  `Run platform-neutral gates`의 `pnpm run test:automation`에서 중지됐다.
- 실패한 integration test는 clean repository에서 current lock과 Git index gitlink가 같은지
  검사한다. candidate worktree에서는 submodule working tree와 lock이 이미 `v0.8.4`인 반면,
  아직 staging하지 않은 Git index gitlink가 기존 `v0.8.2`여서 실패했다.
- App token 발급, branch push와 PR 생성 전 실패했으며 candidate branch와 PR은 남지 않았다.
