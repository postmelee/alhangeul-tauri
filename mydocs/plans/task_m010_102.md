## 설계 방향

- `docs/releases/v<version>.notes.json`을 승인된 사용자 문구의 단일 원문으로 둔다. version·변경 요약·rhwp/앱 변화·한계·관련 PR/Issue를 구조화한다. 원문에 기술 검증 로그나 비밀을 넣지 않는다.
- 공개일·tag/source·패키지 URL·signature 등은 검증된 release metadata/inventory를 입력으로 받아 조합한다. 사실을 여러 템플릿에 수동 복제하지 않는다. schema에는 version과 metadata의 정합성을 검사할 기준을 둔다.
- GitHub 출력은 `이번 버전의 주요 변경 사항 → 다운로드 및 설치 → 알려진 제한 사항 → 이번 릴리즈 관련 PR과 Issue → 상세 기록` 순서다. 변경 요약·포함된 rhwp 변화·알한글 앱 변화를 별도 subsection으로 둔다.
- 웹 출력은 동일 원문의 사용자용 설명을 짧게 사용한다. 실제 공개일과 고정 tag 다운로드를 제공하고, 긴 provenance/PR 목록은 기록·Release 링크로 연결한다.
- updater notes는 별도의 짧은 요약 필드를 사용하며 기존 4000자 제한을 유지한다. 전체 GitHub 본문을 manifest에 복사하지 않는다.
- 필수 항목·버전·고정 HTTPS URL·pin·placeholder·PR/Issue 분류·출력 drift를 검사한다. 기계 검사는 구조·근거 필드의 정합성을 검사하며, 의미상 변경 분류와 해결 여부는 실제 PR/Issue를 조회한 리뷰로 확정한다.
- rhwp v0.8.6 유지 시 새 upstream 기능으로 소개하지 않는다. 단순 관련 이슈를 해결된 이슈로 표현하지 않는다. 아직 OPEN인 #97은 참고 이슈로 둔다.
- Windows NSIS/MSI와 Linux x64 AppImage는 앱 내 업데이트 확인·사용자 동의·dirty 보호를 안내한다. DEB/RPM/arm64는 수동 설치를 안내한다. 실제 upgrade 결과는 실행 후 기록한다.
- 최신 표시의 기준은 실제 공개 release data다. 가장 높은 파일명이나 source version으로 최신 공개 여부를 추측하지 않는다. 버전별 페이지 다운로드는 역사적으로 고정하며 최신 메뉴의 URL과 구분한다.
- #102 기반의 site/release.json은 0.1.0이다. v0.1.1 예제 생성에는 #97에서 read-back한 공개 metadata/inventory를 명시적인 별도 입력으로 사용한다. 사이트 feed를 임의로 0.1.1로 전환하지 않는다.
- 생성기·validator·renderer·CLI를 역할별 파일로 나누고 파일 300 LOC, 함수 50 LOC, 매개변수 5개를 목표로 한다. 초과 필요 시 구현계획에서 이유와 분리 대안을 먼저 승인받는다.

## 검증 계획

### 단계별 검증

- Stage 1: 필수 항목 누락, placeholder, version/tag/pin 불일치, 관련/해결 Issue 오류를 검사한다. 원문과 템플릿의 사용자 용어를 리뷰한다.
- Stage 2: `node --test tests/release-notes.test.mjs` 및 변경한 Pages/CI 계약. 동일 입력의 출력 재현, 원문 변경의 drift 감지, HTML escaping과 고정 tag URL을 확인한다.
- Stage 3: `pnpm run build:pages`, `pnpm run check:pages`; 데스크톱/모바일 브라우저에서 index와 v0.1.1 화면, 다운로드·링크·짧은 안내를 직접 확인한다. 아직 공개하지 않은 상태를 완료로 적지 않는다.
- Stage 4: `pnpm run check:product-boundary`, `pnpm run test:upstream`, `pnpm run test:studio`, `pnpm run build:studio`, 필요한 빠른 자동화 profile, `git diff --check`.

### 통합 검증

- GitHub 본문·웹 안내·updater notes가 같은 사용자 원문과 승인 metadata에서 생성되며 source drift 검사에 통과한다.
- 신규 v0.1.1 데이터는 공개 tag/source/실제 공개일/6개 설치 형식과 일치한다. 3개 updater target과 수동 패키지를 혼동하지 않는다.
- Windows/Linux runner의 빠른 Node/Studio/Windows 계약을 새 정확한 harness SHA로 확인한다. 검증 profile은 기존 `CI_VALIDATION.md`를 따르며 부분 성공을 전체 성공으로 보고하지 않는다.
- Mac 호스트에서는 플랫폼 중립 Node/TypeScript/Pages 계약과 브라우저 표시만 검증한다. native Rust/Tauri build·실행은 수행하지 않는다.
- binary/runtime/key/installer가 바뀌지 않으므로 #97에서 이미 수용한 exact 6종 공개 bytes의 설치 검증을 재사용한다. source diff와 SHA/run 링크를 보고서에 기록하고 재빌드하지 않는다.
- 실제 0.1.0 → 0.1.1 production updater 테스트는 #97 후속 범위다. 시험 endpoint·HTTP 성공·same-version 검사를 대신 기록하지 않는다.
- 최종 보고·커밋 뒤 PR 준비 전 작업 트리가 clean이고 `git diff --check`가 통과해야 한다.

## 리스크

- **미완료 공개 상태의 과장**: GitHub Release, Pages, production manifest, 실제 upgrade 결과를 각각 실제 근거로 표시한다.
- **데이터 중복·drift**: 사용자 문구의 단일 원문과 검증된 metadata를 분리하고 생성물과 일치 여부를 검사한다.
- **#97/#102 통합 충돌**: 공통 도구·예제는 #102, 게시 데이터 적용은 #97이다. #102 merge 후 #97에 merge 방식으로 반영하고 orders·기록 충돌은 양쪽 최신 결과를 보존한다. force/rebase는 수행하지 않는다.
- **계약 범위 초과**: metadata/pin 불일치를 임의 수정하지 않고 승인한 공개 자료를 고정한다. upstream 코드·설치본·환경 보호는 변경하지 않는다.
- **HTML/문구 안전성**: 구조화된 문구를 escaping하며 임의 HTML·script를 원문 입력으로 받지 않는다. 원본의 Mac 전용 설치 안내를 복사하지 않는다.
