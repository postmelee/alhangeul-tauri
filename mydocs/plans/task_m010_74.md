## 설계 방향

### 단일 상태와 최소 host 연결

- Alhangeul이 글꼴 사용 선택·목록 세대·공급 결과를 소유한다. upstream 분석/대체/renderer가 alias와 상대 import 어느 쪽으로 접근해도 동일 adapter 인스턴스를 읽도록 실제 resolved path 기준의 좁은 host resolver를 설계한다. Vite와 Vitest는 같은 연결 규칙을 사용한다.
- 상대 import를 전역 문자열 치환하지 않고 exact upstream 파일 경계로 제한한다. export 누락, 중복 모듈, 의도하지 않은 upstream 재진입을 실제 소비자 연결 테스트로 검출한다. renderer/entry/범용 dialog의 local 복제본은 만들지 않는다.
- 최초 선택 포착·수동 재감지·고정된 저장 성공 문구는 기존 leaf wrapper와 최소 host hook으로 연결한다. 불가피한 source transform은 upstream 파일을 쓰지 않는 빌드 시점의 특정 hook/문구에만 한정하고 marker 개수 불일치 시 실패시킨다. 정확한 hook·추가 alias 목록과 경계 테스트는 구현계획서 승인 전에 확정한다. 무조건 alias 개수 검사를 느슨하게 바꾸지 않는다.

### 선택 지속·복원 정책

- 선택은 `미선택 / 사용 / 미사용`으로 구분한다. “대체 글꼴로 보기”는 미사용 선택으로 지속하고 닫기/Escape는 영구 거절로 바꾸지 않는다. 취소 직후 같은 실행의 반복 안내는 억제하되 다음 실행에서 선택할 수 있게 한다.
- native Rust가 앱 데이터 위치의 작은 versioned 설정 파일을 소유한다. 저장 대상은 선택과 필요한 schema 정보이며 원본 font bytes와 전체 목록·개인 경로는 영속 저장하지 않는다. 저장 성공 이후에만 지속 설정 성공으로 안내한다. 새 의존성 도입보다 기존 native 파일 처리 패턴을 우선한다.
- 사용 상태는 새 프로세스 시작 때 native catalog를 재조회하고, 문서별 필요한 family/bytes만 공급한다. 한 실행의 요청은 합치고 완료된 목록은 재사용한다. 문서 변경 시 필요한 파일의 유효성 확인과 수동 재감지로 삭제/변경을 반영한다.
- 설정 저장은 원자적 교체와 동시 접근 직렬화를 고려한다. 새 창은 native의 최신 선택을 먼저 복원하고 기존 창에는 변경을 전달한다. 늦게 완료된 이전 감지/bytes 요청은 새 선택을 덮어쓰지 못한다.
- 저장 실패 시 해당 실행에서의 사용 여부와 지속 저장 실패를 분리해 알리고 “다음 실행에서도 재사용”을 주장하지 않는다. 손상/읽기 실패 시 허용으로 추정하지 않고 대체 표시와 수동 복구 경로를 제공한다.
- 미사용은 Alhangeul의 목록 감지와 직접 bytes 공급을 중단한다는 뜻이다. OS/WebView가 CSS family를 자체 해석하는 시스템 글꼴까지 차단한다고 안내하지 않는다.

### 실제 사용과 실패 처리

- `감지됨 / 읽기 가능 / 해당 renderer 등록 완료 / 대체됨`을 구분한다. 설정 저장 성공을 snapshot 영속 저장 또는 모든 글꼴 적용 성공으로 표현하지 않는다. 기존 `stored` 필드와 새 선택 상태의 의미는 구현계획서에서 명시한다.
- CSS/SVG/Canvas2D 계열은 실제 사용되는 경로부터 확인하고, file-backed FontFace 등록/해제와 화면 갱신을 검증한다. CanvasKit은 bytes 공급·typeface 등록·재렌더 결과를 별도 확인한다.
- 대표 양성 사례는 기존 지원 root에 설치한 공개 라이선스의 단일 face TTF/OTF로 선정한다. system-installed 목록에 있으나 bytes 허용 root 밖인 경우 CanvasKit fallback/제한을 명시한다. 목록에 존재한다는 이유로 적용 성공으로 표시하지 않는다.
- 재감지·미사용 전환·삭제·읽기 실패 시 adapter가 소유한 bytes/FontFace/renderer 캐시를 세대별로 무효화한다. 접근할 수 없는 파일을 오래된 정상 항목으로 남기지 않는다. 사용자 문서의 원래 글꼴 이름을 자동 치환해 저장하지 않는다.
- renderer 자체 수정 또는 보안 root 확대가 필요해지면 범위를 확대하지 않고 구현계획 보정 승인을 요청한다. 해당 경로 미검증·대체 사용은 다른 경로의 성공과 분리한다.
- 새 모듈은 역할별로 분리해 파일 300 LOC, 함수 50 LOC, 매개변수 5개, 복잡도 10 기준을 따른다. 이미 큰 native command/catalog 파일은 등록·연결만 최소 변경하고 새 상태 로직은 별도 모듈에 둔다.

## 잠정 단계

- **Stage 1 — 실제 소비자 연결과 상태 통합**: 분리 캐시 회귀를 고정하고 상대/alias import를 단일 adapter에 연결한다. upstream 분석·대체·실제 호출 export와 host build 경계를 검증한다.
- **Stage 2 — 선택 지속·자동 복원과 안내**: native 설정, 창 간 동기화, 최초 선택/취소/미사용, 수동 재감지, 저장 실패 안내를 연결한다. 새 창·새 프로세스와 동시 요청을 검증한다.
- **Stage 3 — 실제 공급·적용과 실패 회귀**: 지원 글꼴의 필요 bytes 공급, 캐시 무효화, renderer별 적용/대체와 삭제·읽기 실패를 검증한다. 기존 문서 글꼴명·저장 결과를 보존한다.
- **Stage 4 — Windows/Linux 통합 수용과 문서**: 승인한 exact 후보의 full 및 설치본 시나리오를 수행하고 경로별 결과·한계, 공식 문서, 최종 보고를 정리한다.

각 단계 완료 후 보고·커밋·승인을 거쳐 다음 단계로 진행한다. 이 수행계획 승인은 곧바로 모든 단계 실행 승인이 아니다.

## 검증 계획

### 단계별 검증

- Stage 1: 실제 pinned upstream `analyzeDocumentFonts`·font substitution과 Alhangeul adapter 연결로 감지 전후 상태를 검증한다. native IPC만 mock하고 분석 함수를 대체하지 않는다. build와 test의 resolver 차이·중복 모듈·누락 export를 검사한다.
- Stage 2: 사용/미사용/취소, empty catalog, 저장 실패·설정 손상·복원 실패, 여러 창 동시 변경·늦은 응답을 테스트한다. Rust 설정 test는 Windows/Linux에서만 실행하며 JS module reset 성공을 실제 프로세스 재실행 성공으로 기재하지 않는다.
- Stage 3: 지원 root의 공개 글꼴로 family/face/읽기/등록/화면 결과를 연계한다. 공급 실패·파일 삭제·재감지·미사용 전환 뒤 대체와 stale cache 해제를 검사한다. CSS 문자열, 목록, `document.fonts.check`만으로 화면 적용을 수용하지 않는다.
- Stage 4: Windows x64 설치본과 Linux x64 설치본에서 아래 matrix를 실행한다. Linux arm64는 full의 native/package 결과를 기록하며 GUI 미실행을 명시한다.

- 기본 플랫폼 중립 gate: `pnpm run check:product-boundary`, `pnpm run test:upstream`, `pnpm run test:studio`, `pnpm run build:studio`, `git diff --check`. 초기화되지 않은 submodule과 frozen pnpm 의존성은 승인 후 이 worktree에만 준비하고 pin을 바꾸지 않는다.
- 원인을 집중 회귀로 먼저 고정한 뒤 승인된 `ci.yml profile=fast`를 사용한다. 공유 제품 변경의 최종 후보는 `profile=full`로 세 target의 core/native/package와 Windows 설치, 최종 집계를 확인한다. native Rust/Tauri는 Windows/Linux에서만 실행한다.
- CI는 해당 단계에서 exact source/workflow SHA와 실행 범위를 확정·승인한 뒤 dispatch한다. `publish/task74`의 비게시 검증용 push도 그 승인에 포함해 확인하며 원격 `local/task74`는 만들지 않는다. 부모 task의 실행/릴리즈 승인을 재사용하지 않는다.
- 제품 bytes 변경 후 이전 installer 재검사를 새 source 수용으로 쓰지 않는다. 새 후보의 run/attempt/source/workflow SHA, artifact ID/digest, 설치 파일 hash, OS/renderer/fixture와 결과를 기록한다. 부분 성공·diagnostic 계약 통과·skipped·미실행을 구분한다.
- full 성공만으로 실제 GUI 적용을 수용하지 않는다. Windows는 사용자 보고 환경을 포함한 exact 후보 설치 확인, Linux는 지원 환경의 직접 GUI/기존 harness 관측을 별도 수행한다. 설치본을 사용할 수 없으면 해당 수용을 보류하고 완료로 기록하지 않는다.
- 공개 라이선스 글꼴/문서만 증거에 사용하며 proprietary bytes/path·개인 문서·native 오류의 민감 경로를 로그·artifact에 남기지 않는다.
- PR 준비 전 `git status --short`는 빈 출력이며 `git diff --check`는 경고 없이 통과해야 한다.

## 리스크

- **upstream 연결 범위**: 상대 import 교체는 font substitution까지 영향을 준다. exact pin·파일 경계와 실제 소비자 회귀로 고정하며 renderer 복제나 광범위 source patch로 확장하지 않는다.
- **고정 toast와 선택 콜백**: 상태 adapter만 고치면 거절 지속과 저장 안내가 남는다. 최소 UI/hook의 정확한 변경점을 구현계획서에서 승인받는다.
- **renderer/bytes 제한**: system 목록의 모든 폰트가 CanvasKit에 공급 가능한 것은 아니다. 지원 root의 양성 사례와 제한 사례를 각각 확인하며 root 확대는 하지 않는다.
- **캐시와 동시성**: 폰트 제거 후 등록된 face·bytes·CanvasKit 캐시나 늦은 감지가 남을 수 있다. 소유한 등록의 해제와 세대 검사, 재렌더를 함께 검증한다.
- **검증 환경**: 현재 호스트는 Windows/Linux desktop 실행 환경이 아니다. 플랫폼 중립 검사와 실제 Windows/Linux native·GUI 수용을 분리한다.
- **#69 병행 작업**: 같은 오늘할일이나 공식 문서가 이후 devel에서 바뀌면 diff를 확인하고 필요한 통합 순서를 승인받는다. 다른 checkout·후보·원격 실행을 변경하지 않는다.
