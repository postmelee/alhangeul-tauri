## 설계 방향

1. 기존 [runbook](../../docs/operations/PUBLIC_RELEASE_RUNBOOK.md)과
   [체크리스트](../../docs/operations/RELEASE_CHECKLIST.md)를 실행한다. 새 운영 체계를 만들지 않는다.
2. 공개 기본안은 기존 기록의 `0.1.0` / `v0.1.0` stable 및 6종 installer다.
   Windows x64 NSIS·MSI, Linux x64 AppImage·DEB·RPM, Linux arm64 DEB를 대상으로 검증 환경을
   확정한다. 환경 미확보 시 해당 파일을 조용히 생략하지 않고 범위 재승인을 받는다.
3. Windows NSIS·MSI와 AppImage는 같은 비게시 updater run, 수동 3종은 같은 exact SHA의 일반
   run에서 가져오는 기존 계약을 따른다. 6 installer + 3 서명 + inventory + SHA256SUMS의
   11 asset 기본안을 Stage 1에서 재확인한다. 일반 패키지로 updater 파일을 대체하지 않는다.
4. Windows Authenticode와 updater Minisign을 구분한다. 공개키 fingerprint·endpoint·환경
   승인자·허용 ref는 읽기 전용으로 확인하며 비밀 값은 출력·저장하지 않는다.
5. 기존 검증은 source/config/pin/harness diff가 맞을 때만 재사용한다. 새 bytes의 최소 설치·
   무결성·서명은 새로 확인한다. 제품을 바꾸지 않은 검사 보정은 적격 artifact를 재사용한다.
6. known NSIS 실패 패턴의 진단 계약 통과와 실제 bitmap 성공을 구분한다. MSI 재부팅 요구는
   재부팅 후 확인 전까지 미검증이다. 지원 한계와 위험 판단은 파일 공개 전에 승인받는다.
7. 실패하면 먼저 제품 결함·검사 결함·환경 한계·증거 누락을 분류한다. 실패 재현에 필요한
   가장 작은 검증부터 보정하며, 반복 실패를 이유로 자동화 고도화나 실험을 확대하지 않는다.
8. 준비/기록용 task PR, `devel → main` release PR, 공개 뒤 release data PR의 목적을 분리한다.
   각 PR·merge·공개 권한은 별도 승인한다. 중간 PR merge만으로 #69 전체를 완료/close하지 않는다.
   단계 기록의 통합 시점과 브랜치 운용은 구현계획에서 구체화하고, 최종 보고는 전체 수용 후 작성한다.
9. 공개는 기존 runbook의 동일 bytes CLI 경로를 사용한다. 재빌드하는
   `publish_release=true`는 사용하지 않는다. Pages 입력은 Release 원격 확인 전에 published로 바꾸지 않는다.

## 검증 계획

### 단계별 검증

- Stage 1: GitHub 이슈·PR·release/tag·환경 설정 읽기, 후보 diff 및 과거 근거 대조.
  `pnpm run check:product-version`, `pnpm run check:release-metadata`,
  `pnpm run check:rhwp-pin`을 적용한다. 없는 pin tag 확보는 기존 절차와 exact identity를 따른다.
  실제 Windows/Linux 환경표를 확정한다. NSIS VDI와 MSI 관리자 환경을 구분하며,
  Linux x64 DEB/AppImage·RPM 배포판·arm64의 설치/GUI 범위를 명시한다.
- Stage 2: 최종 통합은 기존 full 경로로 수행하고 ordinary workflow SHA = build_ref resolved SHA =
  checkout SHA를 확인한다. 같은 SHA의 비게시 updater run에서 production 서명 후보를 확보한다.
  full은 GUI/updater/공개 전체 성공이 아니며, 일반 run과 updater run을 구분한다.
- Stage 3: `check:desktop-artifacts`, `check:updater-artifacts`와 기존 runbook의 실제 파일 대조,
  대상 환경 설치·실행·문서 저장/재열기를 적용한다. updater 파일의 설치를 ordinary 파일의
  성공으로 대체하지 않는다. Windows 세 설치 계약의 raw 결과와 평가를 따로 읽는다.
- Stage 4: exact tag commit·파일명/크기/SHA-256·서명·notes·draft/stable 상태 확인.
  게시 파일을 다시 내려받아 승인한 로컬 값과 대조하며 asset 덮어쓰기는 하지 않는다.
- Stage 5: `pnpm run build:pages`, `pnpm run check:pages`, 관련 Pages/updater 회귀와
  실제 원격 링크·manifest 확인. 미공개 fail-closed 검사는 고정 fixture로 유지한다.
- Stage 6: 링크·gate 기록·인계 completeness, 보존 파일과 원격 identity 일치 확인.
  문서-only 정리에 native/full을 반복하지 않는다.

### 통합 검증

- [CI_VALIDATION.md](../../docs/operations/CI_VALIDATION.md)의 fast/installer/package/full 선택을 따른다.
  빠른 계약·PowerShell 보정은 fast, 동일 제품 bytes의 설치 검사 보정은 적격 producer의
  `product_sha`, `product_run_id`, `artifact_id`, `artifact_digest`를 모두 고정한다.
- Windows 제품 변경은 windows-package, Linux 제품 변경은 linux-package,
  공유 코드·lock·workflow 변경과 최종 통합은 full이다. 새 오류는 필요한 범위로 먼저 좁힌다.
- Rust/Tauri 빌드와 native 검사는 Windows/Linux에서만 수행한다. 현재 호스트는 문서·Node 검사에만 사용한다.
- 과거 `d36294a` full과 `29a25c4` VDI는 참고 근거이며 새 파일 검증이 아니다.
- 필수 검사 실패·누락·환경 미확보는 통과로 바꾸지 않는다. 파일별 결과와 위험 승인 뒤 공개한다.
- PR 준비 전 `git status --short`가 비어 있고, `git diff --check`가 경고 없이 통과한다.

## 리스크

- **검증 환경 부족**: 관리자 없는 VDI로 MSI 성공을 주장하지 않는다. 적합한 Windows 환경과
  Linux 배포판/architecture 실행 환경 확보 또는 공개 범위 재승인을 먼저 받는다.
- **계약 통과 오해**: NSIS 제한과 MSI 재부팅 후 미검증을 실제 기능 성공과 분리한다.
- **재빌드·ref 이동·artifact 만료**: exact identity를 다시 확인하며 bytes가 바뀌면 새 파일 검증으로 돌아간다.
- **서명/게시 권한**: Secret 값은 노출하지 않는다. CLI 게시도 승인된 입력·실행자 기록으로 통제한다.
- **범위 확대·반복 CI**: #58·#67은 후속으로 유지한다. 출시 차단 결함만 재승인하여 최소 보정하고,
  매 보정마다 무관한 전체 환경 실험을 반복하지 않는다.
- **운영 task의 여러 PR**: 준비 PR·release PR·데이터 PR은 역할이 다르다. 중간 merge가 #69의
  공개 수용 완료나 이슈 close를 뜻하지 않도록 구현계획에서 순서와 보고 시점을 명확히 한다.
