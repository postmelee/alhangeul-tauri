# Task #45 수행계획서 — Windows/Linux 릴리스·업데이트용 GitHub Pages 재구성

GitHub Issue: [#45](https://github.com/postmelee/alhangeul-tauri/issues/45)
마일스톤: M010

## 목적

현재 HOP 계열의 녹색 격자·상태 카드 중심 단일 화면인 `site/`를 Windows/Linux용
Alhangeul 공식 릴리스·업데이트 허브로 재구성한다. 참고 기준은
[`postmelee/alhangeul-macos` Pages](https://postmelee.github.io/alhangeul-macos/)의
정보 구조, 흰색·연회색 section 리듬, 파란 accent, 타이포그래피, 여백과 접근성 패턴이다.
macOS 전용 기능이나 자산을 복사하지 않고 실제 Windows/Linux 제품 기능과 설치 형식으로
내용을 치환한다.

첫 공개 릴리스 전에는 검증되지 않은 다운로드를 노출하지 않고, 공개 뒤에는 Windows x64
MSI·NSIS와 Linux x64 AppImage의 version과 immutable GitHub Release URL이 홈·업데이트
페이지에서 한 계약을 사용하도록 한다. 후속 Issue #16이 동일 artifact를 사용하는 updater
manifest를 안전하게 게시할 수 있도록 Pages 경로와 custom target handoff를 정의한다.

## 배경

- Task #24와 PR #37이 `rhwp v0.8.4` core·전체 Studio, Windows/Linux native 수용 기준선을
  `devel`에 병합했다.
- 현재 `site/index.html`은 공식 설치 파일이 없다는 개발 상태만 보여 주며 다운로드 선택,
  업데이트 안내, 문의/제보와 실제 제품 화면이 없다.
- 현재 `.github/workflows/pages.yml`은 수동 실행이지만 실행 ref를 exact SHA 입력으로 고정하지
  않고 정적 파일을 단순 복사·치환한다. release metadata나 링크 정합성 gate도 없다.
- Issue #16은 Windows x64 MSI·NSIS와 Linux x64 AppImage 세 custom target의 updater를
  구현하며 #45의 canonical Pages URL·수동 fallback 계약을 선행 입력으로 요구한다.
- Issue #14 Windows thumbnail, Issue #17 Linux thumbnail과 Task #35 Windows GUI 자동화는
  첫 릴리스 필수 범위에서 제외됐다. Pages에서도 Thumbnail을 제공한다고 표현하지 않는다.
- 참고 Pages는 반투명 상단 내비게이션, 중앙 hero, 제품 화면, 기능 showcase, FAQ,
  프로젝트 철학과 footer 순서를 사용한다. 이번 task는 그 계층과 시각 리듬을 Windows/Linux
  제품에 맞게 재해석한다.

## 설계 방향

- **참고 디자인의 구조적 재사용**: 상단 nav → 대형 hero → 제품 화면 → 기능 설명 →
  다운로드 선택 → FAQ → 철학 → footer 순서를 유지한다. 흰색과 연회색 section, blue accent,
  큰 한국어 제목, 넓은 여백과 얇은 경계·그림자 비율을 참고하되 CSS와 문구는 이 저장소에서
  새로 작성한다.
- **Windows/Linux 전용 내용**: Finder, Quick Look, Thumbnail, DMG와 Mac 공유 대신
  HWP/HWPX 열기·편집·저장, drag-in, PDF, system print와 MSI·NSIS·AppImage 선택을 전면에 둔다.
- **실제 제품 시각 자료**: 검증된 Windows/Linux 실행 화면만 사용하고 mockup이나 다른
  platform 이미지를 실제 제품 화면처럼 표시하지 않는다. screenshot의 source SHA와 환경을
  작업 보고서에 기록하며 문서 내용·개인 경로·credential이 보이는 evidence는 사용하지 않는다.
- **정적·결정적 build**: `site/`를 source로 유지하고 Node build/check script가 release
  metadata schema, 내부 경로와 immutable download URL을 검증한 뒤 `_site`를 생성한다.
  JavaScript가 실패해도 핵심 설명과 수동 지원 범위는 읽을 수 있어야 한다.
- **공개 전 fail-closed**: `unreleased` 상태에서는 download anchor를 만들지 않고 “공개
  준비 중”과 GitHub Releases 확인 경로만 제공한다. 공개 상태로 바꾸려면 exact semantic
  version, tag와 세 artifact URL이 모두 있어야 build가 성공한다.
- **immutable URL**: 일반 다운로드와 updater 모두
  `https://github.com/postmelee/alhangeul-tauri/releases/download/v{version}/{asset}` 형식을
  사용한다. `releases/latest/download` 같은 mutable URL은 canonical artifact 계약에 쓰지 않는다.
- **updater 분리**: #45는 `https://postmelee.github.io/alhangeul-tauri/updater/stable.json`
  public path, 세 custom target과 게시 순서를
  공식 문서에 고정하지만 파일을 생성하지 않는다. #16이 signature와 artifact를 검증한 뒤에만
  manifest를 release-aware Pages deployment에 포함한다.
- **공통 UI와 최소 script**: 홈·업데이트·문의 페이지가 같은 header/footer/token을 공유하고,
  FAQ는 native `<details>`를 사용한다. reveal/feature interaction은 콘텐츠 이해에 필수적이지
  않은 향상으로만 두며 reduced motion에서는 즉시 표시한다.
- **base path 안전성**: GitHub project Pages의 `/alhangeul-tauri/` base에서 홈·하위 페이지,
  asset과 metadata 경로가 모두 동작하도록 상대 URL을 사용하고 build 후 link checker로 검증한다.
- **exact-SHA 배포**: Pages workflow는 40자리 `deploy_ref`를 받아 checkout SHA를 재검증하고,
  build/check 성공 뒤에만 artifact를 배포한다. 원인 변경 없이 실패 run을 반복하지 않으며
  실제 deploy는 최종 Stage 승인 뒤 한 번만 수행한다.

## 리스크

- **참고 디자인과 플랫폼 혼동**: 시각 계층은 유사하게 유지하되 Mac 전용 문구·장치·기능을
  복사하지 않고 Windows/Linux 실제 지원 기능 allowlist와 금지 문구 검사를 둔다.
- **허위 다운로드·version**: 공개 전 fail-closed metadata와 negative test로 direct download를
  차단한다. 공개 상태 전환은 세 immutable artifact URL이 모두 검증된 후 별도 release 단계에서 한다.
- **updater 보안 경계 선행 노출**: #45는 endpoint와 target schema만 문서화하고 manifest 파일,
  signature와 key를 만들지 않는다. #16의 artifact 검증 뒤 publish 순서를 build gate로 연결한다.
- **Pages base path와 하위 페이지 drift**: source의 상대 URL과 build 후 link checker로 root와
  `/updates/`, `/feedback/` 경로를 함께 검증한다.
- **시각 자산 provenance·개인정보**: exact candidate의 공개 가능한 fixture 화면만 사용하고
  source SHA·환경을 보고서에 남긴다. 다른 platform 장치 이미지나 credential·개인 문서는 금지한다.
- **motion·접근성 회귀**: 애니메이션은 progressive enhancement로 제한하고 reduced motion,
  focus-visible과 keyboard-only 검증을 각 UI Stage의 차단 gate로 둔다.
- **배포가 검증보다 앞서는 위험**: workflow가 exact SHA와 build/check를 검증한 뒤에만 deploy하고,
  실제 dispatch는 Stage 4 별도 승인 후 한 번만 수행한다.

## 승인 요청 사항

- 참고 Pages의 정보 구조·시각 리듬을 최대한 유사하게 적용하되 Windows/Linux 실제 기능·자산으로
