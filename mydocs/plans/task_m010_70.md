# Task #70 수행계획서 — 첫 공개 전 updater 키 교체와 복구 검증

GitHub Issue: [#70](https://github.com/postmelee/alhangeul-tauri/issues/70)
마일스톤: M010

작성일: 2026-09-20. 상태: Stage 2 복구 검증 및 사용자 임시본 정리 확인 완료, Stage 3 승인 대기.
착수 기준: `cf0aac9de32451e55a686aa09677d1d00bd4648b` (`origin/devel`).

## 목적

첫 공개 전에 복구 가능한 새 updater 서명 키로 전환한다. 원본·백업·암호 보관을
확인하고, 복구된 키의 서명과 실제 Windows/Linux CI 산출물의 서명을 검증하여 #69에 인계한다.
이 계획 승인만으로 키 생성, Secret 교체, 원격 서명 또는 공개를 실행하지 않는다.

## 배경

- #16에서 기존 production key로 서명·검증한 기록은 있으나 현재 원본·백업 위치는 확인되지 않았다.
- 지정된 로컬 위치의 파일명 검색에서 후보를 찾지 못했다. 전역 유실이나 노출을 확정한 것은 아니다.
- 작업지시자는 공개 릴리즈 전 새 키 생성·백업·공개키 및 Secret 교체·재검증 방향을 승인했다.
- #69는 첫 공개 준비 중이다. 기존 키가 포함된 시험 설치본에는 새 키를 소급 적용할 수 없다.
- 기존 [운영 정책](../../docs/operations/DESKTOP_RELEASE.md)은 키 교체를 별도 승인 작업으로 둔다.

## 범위

### 포함

- 키 생성 환경·암호 입력 방식·원본 보관·독립 백업·암호 보관 책임의 사전 확정.
- 새 키 생성, 암호화 백업, 백업에서 복구한 키로 공개 테스트 자료 서명·검증.
- 앱 공개키와 검증 fingerprint 교체 및 관련 계약·현재 운영 문서의 최소 정합성 보완.
- GitHub `release` 환경의 두 signing Secret 교체와 승인된 미게시 서명 CI.
- 실제 MSI·NSIS·AppImage와 서명의 공개키 검증, hash·inventory 확인 및 #69 인계.

### 제외

- Release·tag·Pages 게시, updater 활성화, Authenticode, CI 구조 개편.
- 기존 키·자료 삭제, 과거 검증 기록의 fingerprint 소급 변경, 시험 설치본 자동 마이그레이션.
- 기존 #69 미커밋 변경의 이동·되돌리기, #58·#67 구현, upstream·lock 갱신.
- 비밀 자료를 저장소·채팅·로그·shell history·일반 artifact에 남기는 행위.

## 설계 방향

1. `local/task70`은 최신 `origin/devel`에서 만든 분리 worktree를 사용한다.
   원래 worktree의 #69 변경은 그대로 둔다. #70 통합 후 #69 재개 시 보드와 관련 문서를 병합한다.
2. 보관 책임자는 작업지시자다. 원본은 저장소 밖 접근 제한 위치에, 복구본은 독립적인
   암호화 저장소에 둔다. 같은 디스크의 다른 폴더만으로 독립 백업을 충족했다고 보지 않는다.
3. 암호는 별도 credential store에서 관리한다. 실제 경로·키·암호는 보고서에 쓰지 않고
   공개 fingerprint, 검증 결과와 보관 책임 확인만 남긴다. 보관 수단 미확보 시 생성 전에 멈춘다.
4. 2026-09-20 작업지시자 승인으로 키 관리만 Mac의 기존 Tauri CLI 2.10.1을 사용한다.
   제품 빌드·native 검증은 Windows/Linux에 유지한다. 비밀 출력과 디버그 tracing을 금지한다.
5. **백업 복구와 공개 자료 서명 검증 성공 후에만 Secret을 교체한다.**
   백업 생성 성공이나 파일 존재만으로 복구 성공을 대신하지 않는다.
6. Secret 원문 read-back은 하지 않는다. 기존 두 Secret 이름을 유지하고, 안전한 입력 경로로
   교체한다. 암호와 키의 두 번 쓰기는 원자적이지 않으므로 교체 중 signing run이 없음을 확인한다.
   교체 실패 시 게시·서명을 중단하고 새 키 쌍을 일관되게 등록한 후 검증한다.
7. 현재 공개키·fingerprint 소비 지점만 변경한다. 과거 보고서의 기존 키 검증 사실은 보존한다.
   이전 key의 시험 설치본은 새 후보를 재설치해야 하며, 공개 사용자 자동 업데이트 성공으로 주장하지 않는다.
8. CI는 기존 구조를 사용한다. 빠른 계약은 `fast`, 최종 통합은 `full`, 서명은 기존 updater
   build의 `publish_release=false`로 검증한다. full 성공이 서명 검증을 대신하지 않는다.
9. 같은 실패를 무작정 재실행하지 않는다. 원인을 계약·키 정합성·제품·환경으로 구분하고
   변경 범위에 맞는 최소 회귀를 먼저 수행한다. #69 최종 공개 SHA/bytes 수용은 별도다.
10. 단계별 승인과 별도로 키 생성/복구 실행, Secret 교체, exact-ref 원격 push·CI 실행은
    입력과 영향 범위를 제시하여 승인받는다. 비밀 자료는 명령 인자나 사용자 답변으로 요구하지 않는다.

## 검증 계획

### 단계별 검증

- Stage 1: 보관 수단/책임 확인, Secret 이름·권한·활성 signing run 조회(값 조회 없음), 도구 안전성 확인.
- Stage 2: 복구본의 공개키 일치, 복구 키 서명/검증 성공과 변조 자료 거부, 비밀 출력·추적 없음.
- Stage 3: `pnpm run check:release-metadata`, 관련 Node 회귀 및 `ci.yml profile=fast`.
  최종 통합 `profile=full`과 동일 후보 updater 미게시 CI, 새 공개키로 세 installer 서명·inventory 검증.
- Stage 4: run/attempt/source SHA와 artifact ID/digest 고정, 보관 확인과 잔여 한계 검토.

### 통합 검증

- 새 키 복구 가능성과 CI가 같은 공개키에 맞는 서명을 생성함을 모두 확인한다.
- [CI_VALIDATION.md](../../docs/operations/CI_VALIDATION.md)에 따라 ordinary workflow SHA와
  build_ref resolved SHA를 일치시킨다. 과거 bytes 재사용을 새 키 제품 검증으로 취급하지 않는다.
- 로컬에서는 허용된 Node/문서 검사만 수행하며 Windows/Linux native는 해당 환경에서 실행한다.
- `git diff --check` 통과, PR 준비 전 #70 worktree clean, #69 변경 보존.
- 공개 Release·tag·Pages·manifest는 이 task에서 생성하지 않는다.

## 리스크

- **보관 수단 미확정**: 사용자 확인이 필요하다. 자동으로 임의 credential store를 선택하지 않는다.
- **기존 키 복구 불가**: Secret 교체 후 기존 키로 되돌릴 수 있다고 가정하지 않는다.
- **전환 중 불일치**: 기존 ref의 signing run을 중지/회피하는 승인 절차와 새 후보 일치 확인이 필요하다.
- **비밀 노출**: tracing·CLI 자동출력·임시 파일·artifact 경계를 구현계획에서 점검한다.
- **시험본 호환성**: 기존 키를 신뢰하는 시험 설치본은 새 후보로 재설치한다.
- **#69와 문서 충돌**: 원래 worktree를 건드리지 않고 통합 시 양쪽 기록을 보존한다.
- **과도한 검증 확대**: 새 CI 체계·rotation 일반화 구현을 추가하지 않고 기존 도구로 최소 수용한다.
