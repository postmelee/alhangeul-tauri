# Task #11 수행계획서 — Windows x64 installer smoke 자동화와 MSI 설치 실패 진단

GitHub Issue: [#11](https://github.com/postmelee/alhangeul-tauri/issues/11)
마일스톤: M010

## 목적

Windows x64 MSI와 NSIS를 fresh GitHub-hosted Windows runner에서 실제로 설치하고, 제품 version·파일 연결 handler·제거 상태·사용자 fixture 보존을 같은 방식으로 반복 검증하는 package-level smoke를 만든다. MSI가 실패하면 verbose Windows Installer log와 최초 실패 지점을 보존하여 Windows 10 VDI에서 관찰한 `1602 (ERROR_INSTALL_USEREXIT)`가 installer 결함인지 GUI/VDI 제어 문제인지 분리한다.

이 task는 Issue #9의 공개 prerelease 준비를 다시 진행할 수 있게 만드는 선행 blocker다. 자동 smoke가 성공해도 실제 GUI에서 문서 편집·저장·PDF·인쇄까지 성공했다고 확대 해석하지 않으며, release PR·tag·GitHub Release·서명·게시를 수행하지 않는다.

## 배경

- Issue #9 Stage 3 candidate exact SHA `6e0adc941b9eedbd2d7cceab12bf31dddf184c3a`에서 Windows x64 MSI·NSIS build, artifact inventory와 SHA-256 검증은 성공했다.
- Windows 10 x64 VDI 수동 보고서에서 MSI는 두 번 모두 설치 마법사가 중단되고 Windows Installer status `1602`를 남겼다. 사용자는 취소하지 않았지만 verbose MSI log가 없어 실패 action은 확정하지 못했다.
- 같은 보고서에서 NSIS 설치·실행 파일 version·재설치·제거는 관찰했지만, 기존 설치 열거에 `-LiteralPath`와 wildcard를 함께 사용한 오류 때문에 clean-install 사전 조건은 확정하지 못했다.

- 현재 실제 Windows GUI 환경을 안정적으로 사용할 수 없으므로, 자동화 가능한 설치 경계를 먼저 통과시킨 뒤 물리 Windows GUI 검증은 Issue #9의 후속 gate로 남겨야 한다.

### PowerShell smoke 경계

- 독립 PowerShell script가 MSI·NSIS artifact root, 결과·log 디렉터리, 기대 제품명·version을 명시적 parameter로 받는다.
- script는 엄격한 오류 처리와 명시적 path를 사용한다. wildcard를 조회할 때 `-LiteralPath`를 사용하지 않으며, registry view와 HKLM/HKCU 경계를 명시한다.
- 설치 전에는 실행 process, 설치 경로, uninstall key와 Alhangeul handler가 없는지 검사한다. fresh runner 가정을 결과 대신 사용하지 않는다.
- 두 installer는 같은 runner에서 순차 검증하되 MSI uninstall과 잔여 상태 검사가 끝나기 전 NSIS를 설치하지 않는다. 한 installer의 상태가 다른 installer 결과를 오염시키면 전체 smoke를 실패시킨다.
- MSI는 `msiexec.exe`를 `/i`, silent/no-restart 옵션과 `/L*v` log로 실행하고 실제 process exit code를 보존한다. 실패 시에도 cleanup과 log upload 단계가 실행돼야 한다.
- NSIS는 지원되는 silent option으로 실행하고 installer exit code, 실제 설치 경로와 uninstaller를 기준으로 검증한다.
- 실행 파일의 ProductVersion과 FileVersion은 모두 `0.1.0`이어야 한다. process-level launch는 제한 시간 안에 process가 생성되고 즉시 비정상 종료하지 않는지만 확인한 뒤 안전하게 종료하며, 창 rendering이나 문서 기능 성공으로 기록하지 않는다.
- 비민감 fixture는 install path 밖 runner 임시 작업 디렉터리에 임의 marker로 만들고 설치 전후 SHA-256을 비교한다. 개인 문서나 외부 비공개 fixture를 사용하지 않는다.
- uninstall 뒤 process, 제품 설치 경로, uninstall 등록, Alhangeul ProgID/OpenWith handler와 제품 shortcut이 승인된 정리 상태인지 확인한다.

### 파일 연결 판정

- 설치 전 `.hwp`와 `.hwpx`의 사용자·시스템 기본 연결 값을 snapshot하고 uninstall까지 비교한다.
- 성공 기준은 Alhangeul handler가 Windows의 지원되는 등록 위치에서 발견되고 open command가 설치된 Alhangeul 실행 파일을 가리키는 것이다.
- 기존 기본 앱을 Alhangeul로 바꾸는 것은 성공 기준이 아니며, 기존 기본 연결을 강제로 변경하면 실패로 처리한다.
- MSI advertised ProgID와 NSIS 등록 방식이 다를 수 있으므로 Stage 1에서 생성된 installer와 Tauri의 실제 registry contract를 조사해 installer별 허용 위치를 고정한다. 단순히 `.hwp` 기본값만 읽어 handler 부재를 판정하지 않는다.
- uninstall cleanup은 설치 전 snapshot과 Alhangeul 소유 key를 구분한다. 기존 앱의 key나 사용자 문서를 삭제하지 않는다.

### Workflow와 증적

- 기존 `.github/workflows/alhangeul-desktop.yml`의 `contents: read`, `workflow_dispatch`, exact-ref checkout과 14일 build artifact 경계를 유지한다.
- Windows build artifact를 fresh `windows-2025` smoke job으로 전달해 build 성공과 install 성공을 분리한다.
- smoke 실패에도 원본 MSI verbose log, registry·path·version·exit-code 요약과 cleanup 결과를 별도 diagnostic artifact로 업로드한다.
- workflow는 release API, write permission, secret, signing, tag 또는 게시 단계를 추가하지 않는다.
- Node 자동화 test는 workflow job·runner·artifact 연결·항상 실행되는 진단 upload와 PowerShell script의 핵심 parameter/guard를 정적으로 보호한다. 실제 installer 결과는 Windows Actions run만 수용 증적으로 사용한다.
- log에는 token·secret·개인 문서 내용을 기록하지 않는다. GitHub-hosted runner의 표준 임시 path는 허용하되 환경 전체 dump나 계정 정보를 수집하지 않는다.

### 원인 판정과 packaging 수정 gate

1. 먼저 기존 bundle을 자동 smoke로 재현하고 verbose log·registry 증적을 수집한다.
2. MSI가 fresh runner에서도 실패하면 `Return value 3`와 관련 custom action·WiX component를 기준으로 source 원인을 특정한다.
3. custom WiX template 또는 Tauri bundle 설정의 결함이 확인된 경우에만 최소 수정한다. 추측만으로 installer template을 변경하지 않는다.
4. MSI가 성공하면 VDI의 interactive install/UI/session 문제로 분류하되, NSIS와 association 계약까지 모두 통과해야 Task #11은 성공이다.
5. 수정 뒤에는 새 exact SHA에서 MSI·NSIS 양쪽을 처음부터 다시 검증한다. 한 installer의 성공으로 다른 installer를 대체하지 않는다.

검증된 원인·해결이 이후 작업에서도 반복될 가능성이 있으면 `mydocs/troubleshootings/task_m010_11_windows_installer.md`에 재현 조건, 원인, 해결과 재발 방지를 기록한다. 원인을 확정하지 못하면 추측성 troubleshooting 문서는 만들지 않고 단계·최종 보고서에 검증 한계만 남긴다.

## 잠정 단계

- **Stage 1 — 실패 근거와 installer 상태 계약 확정**
  - Task #9 candidate·Windows 보고서·현재 WiX/NSIS 생성 설정을 대조한다.
  - clean-state, install, handler, launch, uninstall과 fixture 보존의 package별 관찰 위치를 확정한다.
  - Task #11 선병합 후 Task #9 새 candidate 재검증 순서를 단계 보고서에 고정한다.
- **Stage 2 — installer smoke script와 회귀 계약 구현**
  - MSI/NSIS 순차 검증, verbose log, registry snapshot, version, process, fixture와 cleanup 검사를 PowerShell script로 구현한다.
  - 실패 경로에서도 cleanup과 진단 자료가 보존되는 계약을 Node test로 보호한다.
- **Stage 3 — Windows workflow 연결과 원인 진단**
  - fresh `windows-2025` job에서 Windows artifact를 내려받아 smoke를 실행하고 진단 artifact를 항상 업로드한다.
  - exact SHA 최초 run으로 MSI `1602` 재현 여부와 file association 실제 등록 위치를 판정한다.
- **Stage 4 — 증거 기반 packaging 보정과 재검증**
  - 결함이 재현·특정된 경우에만 WiX/Tauri 설정을 최소 수정한다. 결함이 없으면 source를 바꾸지 않고 VDI 한계를 기록한다.

- **Stage 5 — 운영 문서 정렬과 Task #9 handoff**
  - 자동 package smoke가 보장하는 범위와 실제 GUI 검증이 남는 범위를 공식 운영 문서에 반영한다.
  - 전체 로컬·Actions 증적과 잔여 위험을 정리하고, Task #9이 최신 `devel`에서 새 candidate를 검증할 입력을 확정한다.

### 통합 검증

- fresh Windows runner에서 MSI와 NSIS가 각각 clean install·version·handler·bounded launch·uninstall·fixture 보존 검사를 통과한다.
- MSI 실패 시 원본 verbose log와 최초 실패 action을 식별할 수 있는 문맥이 보존된다.
- installer가 기존 `.hwp`/`.hwpx` 기본 앱을 강제로 변경하지 않는다.
- uninstall 뒤 제품 process·설치 경로·uninstall 등록·Alhangeul 소유 handler·shortcut이 승인된 상태로 정리된다.
- workflow failure에서도 진단 artifact가 업로드되고 release·tag·secret·write permission이 추가되지 않는다.
- exact-SHA Actions run의 event, head SHA, Windows jobs와 conclusion이 기록과 일치한다.
- 자동 smoke 결과를 실제 GUI 문서 시나리오 성공으로 표현하지 않는다.
- Issue #9은 열린 blocked 상태를 유지하며 이전 candidate artifact를 공개 asset으로 사용하지 않는다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **MSI `1602` 미재현**: fresh hosted runner에서 성공할 수 있다. 이 경우 source를 추측 수정하지 않고 VDI의 interactive/session 한계로 분류하며 자동 smoke를 회귀 gate로 남긴다.
- **권한·session 차이**: GitHub-hosted runner의 관리자 권한과 non-interactive session은 실제 사용자 PC와 다르다. package-level 결과만 주장하고 GUI·SmartScreen·UAC 체감 검증은 Issue #9에 남긴다.
- **registry view 차이**: MSI·NSIS, HKLM/HKCU와 32/64-bit view가 다를 수 있다. 모든 허용 위치를 명시적으로 검사하고 기존 기본값과 Alhangeul handler를 분리한다.
- **기존 앱 훼손**: file association cleanup이 기존 Hancom 등록을 건드릴 수 있다. fresh runner와 설치 전 snapshot을 사용하고 Alhangeul 소유 key만 판정·정리한다.
- **실패 cleanup 누락**: installer 중간 실패가 다음 검사를 오염시킬 수 있다. `finally` 성격의 cleanup·diagnostic 경로를 두고 잔여 상태가 있으면 성공으로 처리하지 않는다.
- **launch hang**: GUI process가 runner에서 종료되지 않을 수 있다. bounded timeout 뒤 대상 process만 명시적으로 종료하고 광범위한 process kill을 사용하지 않는다.
- **로그 노출**: verbose installer log에 path와 환경 정보가 포함될 수 있다. secret·환경 전체 dump·개인 문서를 넣지 않고 표준 runner 진단만 artifact로 보존한다.
- **Task #9 충돌**: 두 task가 workflow와 운영 문서를 모두 수정한다. Task #11을 먼저 병합하고 Task #9이 최신 `devel`에서 충돌을 해소한 새 SHA를 검증하며, 과거 candidate 성공을 승계하지 않는다.
- **자동화 범위 오인**: installer smoke는 문서 기능·PDF·인쇄·실제 파일 연결 UI 선택을 보장하지 않는다. 공식 문서와 보고서에 남은 수동 gate를 명시한다.

## 승인 요청 사항

- Task #11을 최신 `origin/devel`에서 독립 수행하고, Task #11 merge 뒤 Task #9이 최신 `devel`로 새 exact-SHA candidate를 만드는 통합 순서
