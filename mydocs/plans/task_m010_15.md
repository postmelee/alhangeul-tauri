# Task #15 수행계획서 — Tauri 인쇄를 upstream 전용 페이지 SVG surface로 교체

GitHub Issue: [#15](https://github.com/postmelee/alhangeul-tauri/issues/15)
마일스톤: M010

## 목적

Alhangeul-Tauri의 `인쇄`가 최상위 Studio WebView를 그대로 인쇄하지 않고, 고정된 rhwp v0.8.2가 제공하는 페이지별 `profile=print` SVG와 전용 인쇄 미리보기 surface를 사용하도록 보정한다. Tauri에는 전용 창 생성과 최종 native 인쇄처럼 host에 꼭 필요한 경계만 남긴다.

Windows WebView2 인쇄 미리보기에서 문서 대신 빈 앱 화면이 한 쪽으로 표시되는 회귀를 제거하고, Windows/Linux exact-SHA bundle에서 페이지 수·방향·한글·다중 페이지 결과를 검증한다. 검증 가능한 Windows 후보를 작업지시자가 내려받을 수 있는 상태까지 진행한다.

## 배경

Task #13 exact SHA `63a2703cebf3a79d11a010974203fdaf4ccd3e76`의 PDF 직접 저장은 최소 Linux와 Windows VDI에서 성공했고, Windows Edge에서 한글 검색·선택·복사도 확인됐다. 그러나 같은 후보의 `file:print`는 Tauri adapter가 upstream command를 `printCurrentWebview()`로 바꾼 뒤 Rust `WebviewWindow.print()`를 호출한다. Windows 미리보기에는 앱 제목과 날짜만 있는 빈 한 쪽이 나타나 문서 페이지가 인쇄 surface에 준비되지 않았음이 확인됐다.

rhwp v0.8.2 upstream은 `runPrintPreview()`에서 `renderPageSvgWithProfile(..., 'print')`로 모든 페이지를 준비하고 `print.html` same-origin 창에 배치한 뒤 그 전용 창만 인쇄한다. 따라서 PDF 변환·폰트 문제와 분리된 adapter 소유 경계 결함으로 다룬다.

Task #13은 아직 `devel`에 merge되지 않았고 본 결함 코드도 그 브랜치에만 존재한다. 작업지시자는 별도 Issue 등록과 다운로드 가능한 검증 후보까지의 연속 진행을 승인했다. 이에 `local/task15`는 일반적인 `origin/devel` 대신 Task #13 exact SHA에서 분기한다. Task #13의 변경을 복제하거나 재작성하지 않으며, #13 merge 전에는 #15의 `devel` 대상 PR을 만들지 않는다.

## 범위

### 포함

- upstream `file:print`, `runPrintPreview`, `print-surface.ts`, `print.html`과 Tauri adapter의 소유 경계를 고정한다.
- 최상위 Studio WebView 직접 인쇄 override를 제거하거나 전용 인쇄 surface의 최종 호출만 담당하도록 축소한다.
- Tauri에서 same-origin 전용 인쇄 창을 만들고 페이지별 print SVG를 준비할 수 있는 최소 bridge를 구현한다.
- upstream 페이지 준비 로직을 중복하지 않는 focused test와 drift guard를 추가한다.
- Windows WebView2에서 쪽 수·방향·한글·다중 페이지·Microsoft Print to PDF를 검증할 exact-SHA 후보를 만든다.
- Linux exact-SHA bundle에서 인쇄 surface와 기존 PDF/HWP/HWPX 기능의 회귀를 확인한다.

### 제외

- 검증을 통과한 `file:print-to-pdf` searchable PDF pipeline과 bundle font 정책 변경
- HWP/HWPX 저장·메뉴·drag-in·문서 중앙 배치의 재설계
- `third_party/rhwp` source 수정 또는 upstream pin 갱신
- macOS 지원·빌드·검증
- release, tag, 서명, updater, package repository 게시
- Task #13 또는 #15의 merge·close

## 설계 방향

- **upstream 페이지 surface 계승**: `file:print`의 문서 pagination, 페이지별 `profile=print` SVG, preview DOM/style은 upstream을 진실 원천으로 둔다.
- **얇은 Tauri host 경계**: Tauri가 브라우저 `window.open()`을 원하는 앱 창으로 제공하지 못하는 경우에만 전용 WebviewWindow 생성·ready handshake·최종 print 명령을 adapter로 보충한다. 페이지 SVG 조립을 Rust나 별도 local command에 복제하지 않는다.
- **명시적 대상 창**: native print는 현재 editor 창이 아니라 페이지 SVG가 완성된 전용 print surface에만 호출한다. 문서 준비 완료 전 인쇄 대화상자를 열지 않는다.
- **PDF 분리 유지**: `file:print-to-pdf`는 현재 Rust `svg2pdf` direct-save 계약을 유지하고 인쇄 surface 작업의 영향을 받지 않게 focused test로 고정한다.
- **의존 브랜치**: `local/task15`의 base `63a2703...`을 문서와 검증 증거에 기록한다. Task #13 merge 뒤에만 #15 게시 기준을 최신 `devel`과 정렬하며, 그 전에는 history rewrite나 중복 PR을 만들지 않는다.
- **플랫폼 경계**: 플랫폼 중립 TypeScript 검증은 현재 호스트에서 수행한다. Rust desktop build와 Tauri bundle 성공은 Windows/Linux workflow에서만 판정한다.

  - upstream window/surface lifecycle, Tauri popup·WebviewWindow 동작, 현재 override를 비교한다.

- **Stage 2 — 전용 페이지 SVG 인쇄 surface 구현**

  - 단일·다중 페이지, 준비 완료, 닫기, 반복 인쇄와 PDF 분리 회귀를 자동 검증한다.

  - 제품 경계, upstream, Studio test/build를 통과시키고 공식 소유 경계·release gate를 필요한 만큼 보정한다.
- **Stage 4 — exact-SHA Windows/Linux 후보와 수동 검증 handoff**
  - exact SHA로 Windows/Linux native CI·bundle을 만들고 artifact inventory를 확인한다.
  - 작업지시자가 내려받을 Windows x64 MSI·NSIS 후보와 검증 절차를 제공한다.

## 검증 계획

### 단계별 검증

- Stage 1
  - upstream/local print command·surface call graph 비교
  - Tauri v2 WebviewWindow 생성·same-origin asset·print command capability 검토
  - focused ownership/drift test
- Stage 2
  - `pnpm --filter @alhangeul/studio-host test`
  - print surface 단일·다중 페이지, ready·close·retry test
  - `file:print-to-pdf`와 save command 회귀 test
- Stage 3
  - `pnpm run check:product-boundary`
  - `pnpm run test:upstream`
  - `pnpm run test:studio`
  - `pnpm run build:studio`
  - `git diff --check`
- Stage 4
  - Windows/Linux native workflow와 artifact inventory
  - Windows x64 MSI·NSIS 또는 portable 후보의 인쇄 미리보기, Microsoft Print to PDF, 다중 페이지·세로/가로·한글 수동 검증
  - Linux 후보의 전용 surface 페이지 수·시각 결과와 direct PDF 회귀 검증

### 통합 검증

- `file:print`가 editor WebView 대신 upstream 페이지별 `profile=print` SVG를 전용 surface에 구성한다.
- Windows 인쇄 미리보기의 페이지 수·방향·본문이 원문과 일치하며 Studio chrome이나 빈 한 쪽이 출력되지 않는다.
- direct PDF의 페이지·한글 searchable 결과와 HWP/HWPX 저장이 회귀하지 않는다.
- `git status --short`가 후보 게시 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **Tauri popup 정책**: upstream `window.open()`이 일반 browser popup과 다른 WebView를 만들거나 차단될 수 있다. 먼저 실제 runtime 경계를 test로 고정하고, 필요하면 전용 WebviewWindow adapter만 추가한다.
- **서로 다른 JS realm**: editor와 print 창이 다른 Webview realm이면 DOM 객체를 직접 넘길 수 없다. 직렬화 가능한 페이지 payload와 ready handshake를 사용하되 upstream SVG 생성은 복제하지 않는다.
- **CSP와 asset origin**: `print.html`의 inline style이나 same-origin 판정이 Tauri CSP 변환과 충돌할 수 있다. external style/class와 실제 asset URL을 검증한다.
- **중복 인쇄·창 leak**: 반복 클릭, popup close, 준비 실패에서 orphan window나 중복 native dialog가 생길 수 있다. 단일 job guard와 cleanup test를 둔다.
- **의존 브랜치**: #13 미merge 상태에서 #15를 `devel`에 직접 게시하면 중복 diff가 생긴다. #13 merge 전에는 검증 후보만 게시하고 #15 PR은 만들지 않는다.

## 승인 요청 사항

- upstream 페이지 SVG와 preview DOM을 상속하고 Tauri는 전용 창·최종 인쇄 경계만 보충하는 방향
- `file:print-to-pdf`와 bundle font pipeline을 변경하지 않는 범위
- Task #13 exact SHA를 의존 base로 쓰고 #13 merge 전 #15 PR을 만들지 않는 예외
- 4개 Stage와 Windows x64 다운로드 후보까지 별도 단계 승인 없이 연속 진행하는 순서

작업지시자는 2026-08-08 같은 스레드에서 위 범위의 이슈 등록부터 다운로드 가능한 직접 검증 후보까지 별도 승인 없이 진행하도록 승인했다. 이에 수행계획 승인과 각 Stage 진입 승인을 해당 지시로 간주한다.

승인된 범위에 따라 `task_m010_15_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
