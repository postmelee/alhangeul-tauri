## 목적

같은 Windows PC에서 NSIS 설치는 썸네일에 실패하고 MSI 설치는 성공한 현상을
설치 범위·COM 실행 문맥·캐시·설치 순서별로 분리해 조사한다. 먼저 GitHub Actions의
깨끗한 Windows VM을 활용하고, hosted 환경에서 설명되지 않는 조건만 승인된
Windows 10/11 VM·VDI에서 보완한다. 물리 PC 확보를 시작 조건으로 두지 않는다.

등록 명령 성공, 처리기 선택, 직접 COM 생성, 실제 Shell bitmap 반환을 구분하고
지원 환경·제한·설치 대안을 근거로 정한다. 후속 #58의 선택 설치·앱 내 토글 설계에
필요한 등록·권한·복원 경계를 인계한다.

## 배경

- 사용자 보고 artifact: [run 34021920074 / artifact 9986364323](https://github.com/postmelee/alhangeul-tauri/actions/runs/34021920074/artifacts/9986364323).
  한글 2022가 설치된 PC에서 NSIS는 작은/큰 HWP 모두 실패했으나 제거 후 같은 빌드의

  Shell GetImage는 `0x80040154 / Bitmap=False`였다. JPG는 `0 / Bitmap=True`였다.
  DLL·worker 및 사용자별 COM 등록이 존재했고 `EnableLUA=0`, 관리자 권한이었다.
- 현재 NSIS는 64비트 HKCU, MSI는 64비트 HKLM에 처리기를 등록한다. MSI 전환은
  등록 범위 외에도 설치 경로·프로세스·캐시 상태를 바꾸므로 단일 원인은 미확정이다.
- [Microsoft COM 등록 규칙](https://learn.microsoft.com/en-us/windows/win32/sysinfo/hkey-classes-root-key)은
  UAC가 꺼진 관리자 실행의 사용자별 등록 제한을 설명한다. 그러나
  [GitHub Windows runner도 관리자 권한·UAC 비활성화](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#administrative-privileges)이며
  기존 CI는 성공했다. UAC 값만으로 원인을 확정하거나 NSIS를 일괄 차단하지 않는다.
- 현재 installer smoke는 같은 job에서 MSI → 제거 → NSIS 순서다. 선행 설치의
  등록·프로세스·캐시 영향은 가설로만 두고 NSIS-only clean job으로 분리한다.
  현재 Shell interop은 bitmap을 받아 해제하지만 호출자에게 HRESULT만 반환한다.
  성공 HRESULT와 non-null bitmap, 실제 새 추출을 별도로 검증할 필요가 있다.
- 시작 기준은 최신 `origin/devel`의 `c93ac8c58a796a45227f764f37b7aaffaa81899e`다.
  메인 worktree의 `local/task19`는 건드리지 않고 `.claude/worktrees/task57`의
  `local/task57`에서 수행한다. #19의 미통합 변경은 본 작업 근거에 섞지 않는다.

## 설계 방향

1. **진단을 먼저 고정한다.** 파일 존재와 COM 등록 명령만으로 성공 처리하지 않는다.
   연결 조회·직접 COM·Shell 요청은 독립된 결과로 남기며 순서가 상태에 영향을 줄 수
   있으므로 깨끗한 프로세스와 요청 순서도 기록한다. 초기 진단은 registry를 변경하지 않는다.
2. **설치 방식별로 VM을 분리한다.** 동일 검증 bundle을 받아 각각 선택한 installer만
   실행한다. install 이전의 양 hive·프로세스 상태를 확인해 오염된 환경을 정상으로 삼지 않는다.
   기존 순차 설치는 원인 비교가 필요할 때만 별도 대조군으로 두고 기본 수용 gate로 쓰지 않는다.
3. **캐시와 실제 호출을 구분한다.** task 소유 fixture 복사본과 새 경로를 사용하고 원본은
   수정하지 않는다. 새 경로만으로 cold extraction을 단정하지 않고 cache/extraction API의
   제어·관측 방법을 구현계획에서 정한다. JPG 성공도 모든 Shell 구성요소의 정상 증명은 아니다.
4. **오류를 숨기지 않는다.** HRESULT, bitmap 유무와 크기 등 관측값을 함께 수집한다.
   expected negative 검사는 별도로 표시하고 실패·증거 누락을 retry로 성공 처리하지 않는다.
   타임아웃과 설치 형식별 유일한 artifact 이름을 두어 진단 누락·충돌을 방지한다.
5. **환경에 맞춘 해결을 승인받는다.** NSIS-only가 실패하면 MSI-only 및 기존 순차 결과와
   비교하고 최소 보정안을 제시한다. hosted에서 모두 성공하면 Windows client/session 차이를
   조사한다. 등록 모델 변경이나 새 권한 helper 도입은 Stage 3 진입 전 구체적 승인을 받는다.
6. **사용자·기존 프로그램의 소유권을 보존한다.** 공유 key 전체 삭제를 하지 않고 기존
   snapshot/조건부 복원 계약을 유지한다. 계정 종류·권한을 기록하되 개인 계정·문서 경로는
   비식별화한다. 실제 한컴이 없는 가짜 ProgID 검사를 한컴 호환성 수용으로 표현하지 않는다.
7. **기존 경계를 유지한다.** #35의 GUI E2E와 도구를 재사용하되 editor/print 자동화를
   복제하지 않는다. helper는 역할별로 나누고 파일 300 LOC·함수 50 LOC를 목표로 한다.
   기존 대형 workflow·WiX 템플릿은 제한된 orchestration 수정만 하며 전면 리팩터링하지 않는다.

### 비교 순서와 판정

공개 작은 HWP·큰 HWP·HWPX와 JPG, 64비트 STA·동일 크기·timeout·probe 순서·파일 해시를
고정한다. 각 관측은 새 probe process와 task 소유 문서 복사본을 사용하고 최초 Shell 요청을
직접 COM/캐시 warming보다 먼저 수행한다. 강제 추출 결과를 별도로 기록한다. A→B→A 복원
관측과 독립 clean job 대조가 일치해야 조건의 영향을 지지한다. 한 번 성공한 retry만 골라 쓰지 않는다.

| 비교 | 고정 조건 / 바꿀 조건 | 판단과 한계 |
|---|---|---|
| C0 NSIS 원상태 | MSI 선행 없는 VM, 검증한 NSIS bytes·HKCU·기본 경로 | 기존 실패 기준선. 실패 미재현이면 개입하지 않고 image/환경 차이를 먼저 보고 |
| C1 실행 문맥 | 같은 SID·profile·session·설치 경로·등록을 유지하고 실제 정상 로그인 token과 승격 token 비교 | 문맥에 따른 차이. caller/가능한 Shell host token을 각각 관측. 다른 계정이나 단순 integrity 하향은 같은 실험 아님 |
| C2 경로 | C0 문맥·HKCU·DLL/worker bytes 유지, task 전용 관리자 쓰기 보호 디렉터리로 payload 복사하고 소유 InprocServer32 경로만 변경 후 복원 | 경로/ACL 묶음의 영향. 두 인자를 개별 원인으로 단정하지 않음. 복사본 옆 worker 의존 경로 확인 |
| C3 COM 등록 범위 | C2의 같은 보호 경로·bytes·caller 유지, 해당 Alhangeul CLSID의 필요한 COM 등록만 HKLM에 임시 추가 후 원상복원 | machine-visible COM 등록의 영향. HKCU 연결/ShellEx·UserChoice는 그대로. 전체 NSIS all-user 지원 성공은 아님 |
| C4 MSI 대조 | 별도 clean VM에 같은 출처 MSI 일반 설치 | 알려진 대안과 환경 유효성 재확인. NSIS와 차이를 hive 하나로 설명하지 않음 |

C1은 가능한 문맥만 실행한다. runner의 linked token/실제 사용자 세션을 안전하게 확보할 수
없으면 `context-unavailable`로 기록하고 정상 로그인 비교는 Windows 10/11 시험 VM 승인으로
넘긴다. 계정 생성·암호 수집·다른 사용자 token 탈취·UAC 전환·상시 서비스 설치는 포함하지 않는다.
C0/C2/C3는 동일 문맥의 경로·등록 실험이므로 C1 불가와 독립적으로 판단하되 전체 정상 사용자
수용으로 확대하지 않는다. 실행 가능성 확인 실패를 NSIS 제품 실패 또는 통과로 혼동하지 않는다.
