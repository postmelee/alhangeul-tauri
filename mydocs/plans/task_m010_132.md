## 설계 방향

- 기본 NSIS HKCU·MSI HKLM64 경계를 유지한 채 관측한다. registry 등록이 보인다는 사실과
  Shell surrogate에서 같은 COM class를 활성화할 수 있다는 사실을 구분한다.
- Microsoft의 [per-user COM override 설명](https://devblogs.microsoft.com/oldnewthing/20190801-00/?p=102745)은
  elevated 실행에서 HKCU 등록을 사용하지 않는 보안 경계를 설명한다. 이는 조사 가설의 근거이며
  본 제품의 root cause 확정은 아니다. 직접 COM 성공과 Shell 실패 차이를 별도로 입증해야 한다.
- 기존 probe를 우선 재사용하되 token 비교만으로 수행 가능한 안전한 관측 경로를 분리한다.
  기존 context experiment는 HKLM overlay 등을 함께 수행하므로 그대로 dispatch하지 않는다.
- hosted elevated 환경만 보고 일반 Explorer 실패를 단정하거나, 일반 사용자 성공만으로
  기존 elevated 실패를 해결됐다고 바꾸지 않는다. 지원 범위 변경이 필요하면 원인 증거와
  구체적인 설계를 제출하고 별도 승인받는다.
- 수정은 Windows 경계에 한정한다. shared core/CI 영향이 생기면 검증 profile을 확대한다.
- 새 파일 300 LOC, 함수 50 LOC, 매개변수 5개 기준을 지킨다. 기존 큰 파일은 역할별 helper로
  좁혀 수정하며 예외가 필요하면 구현계획서에 이유와 범위를 기록한다.

## 검증 계획

### 단계별 검증

- Stage 1: 기존 evidence/source/hash readback, Windows PS probe parsing/격리 회귀,
  `pnpm run test:automation`, `pnpm run check:product-boundary`, 필요 시 `profile=fast`.
  Windows baseline은 검증된 기존 artifact bytes를 우선 재사용한다. 공개 installer는
  별도 release hash 검증을 하며 ordinary artifact와 혼동하지 않는다.
- Stage 2: 위 검사와 Windows handler 관련 Rust test/clippy, probe/등록 회귀;
  제품 변경은 `profile=windows-package`. harness-only면 exact 입력이 있는 `installer`.
  새 workflow/shared/build 변경은 `CI_VALIDATION.md` 기준 `full`로 확대한다.
- Stage 3: Windows 지원 VM의 일반 사용자 Explorer 및 elevated 관측을 구분한다.
  hosted에서 interactive/linked token을 확보하지 못하면 미실행으로 남기고 필요한 Windows
  환경을 구체적으로 요청한다. 가능한 API 검사는 계속 진행한다.
- Stage 4: `pnpm run check:product-boundary`, 링크/결과 일치, `git diff --check`, PR 필수 fast.
  upstream/Studio/shared 영향이 있으면 `pnpm run test:upstream`, `pnpm run test:studio`,
  `pnpm run build:studio`를 추가한다. 통과한 동일 입력 검사는 근거 없이 반복하지 않는다.

### 통합 검증

- 수정 전 재현과 수정 후 기능 성공은 installer·DLL·worker hash, source/support SHA,
  fixture hash, OS/token/session, mode, HRESULT, bitmap 크기/내용 및 실행 로그로 결속한다.
- small/large HWP와 HWPX 공개 fixture에서 Shell 및 force-extract 성공, 실제 첫 페이지
  이미지의 내용/크기, JPG 대조군을 확인한다. 기존 캐시 성공만으로 신규 생성 통과를 주장하지 않는다.
- NSIS 생명주기와 MSI 일반 회귀, 타사 연결 보존·제거 이후 소유 등록 정리를 확인한다.
- `thumbnailStatus=not-accepted`나 bitmap 부재를 diagnostic contract 성공으로 대체하지 않는다.
- Rust desktop/Tauri/native/설치/Explorer는 Windows/Linux 지원 환경에서만 실행한다.
  이 Mac에서는 허용된 all-host 검사만 수행한다.
- private/generated 검증 산출물은 T7가 실제 연결된 상태에서 지정 output에 둔다.
  새 worktree 사용 전 storage routing을 적용하며 원본 #126 증거는 읽기 전용으로 보존한다.
- 최종 커밋 뒤 `git status --short`가 빈 출력이고 `git diff --check`가 통과해야 한다.

## 리스크

- **보안 경계**: elevated Shell이 HKCU COM을 허용하지 않는 환경이면 단순 등록 누락 수정과
  다르다. 격리/UAC를 약화해 통과시키지 않으며 제품 설치 범위 변경은 별도 설계 승인 대상이다.
- **현장 환경 부족**: hosted runner의 Explorer/token 제약을 정상 사용자 환경으로 오인할 수 있다.
  actual Explorer 수용 환경이 없으면 자동 결과만으로 완료하지 않는다.
- **캐시 오판**: 새 fixture 복사/고유 경로와 force-extract로 확인하며 전역 캐시 삭제는 하지 않는다.
- **회귀**: updater 후 DLL 경로/등록, MSI, 타사 연결 복원을 별도 확인한다.
- **이전 실험 재개 혼동**: #57 context experiment의 HKLM/보호 경로 개입은 본 계획 기본 범위 밖이다.

## 2026-11-11 지원 정책 선택 확정

작업지시자가 “사용자별 NSIS 유지, 관리자 환경은 MSI 사용”을 선택했다.
Stage 2의 시스템 NSIS 전환안 A는 채택하지 않는다. 현재 설치 형식과 제품 권한 범위를 보존한다.
이 결정은 관리자 NSIS 실패가 고쳐졌다는 의미가 아니다. 이슈의 완료 범위는 다음과 같이 정렬한다.

- 일반 사용자 NSIS와 관리자 MSI의 실제 HWP/HWPX 썸네일 생성 및 lifecycle을 검증한다.
- 관리자 NSIS 결과는 지원 제한 관측으로 분리하며 기능 수용에 포함하지 않는다.
- 실패를 허용하는 diagnostic contract와 지원 환경의 필수 bitmap gate를 명시적으로 분리한다.
- 사용자 안내는 NSIS의 일반 사용자 용도와 MSI의 관리자 환경 용도를 구체적으로 설명한다.
- renderer/worker 제품 코드를 근거 없이 변경하거나 새 버그 수정이 있었다고 주장하지 않는다.
- PR 생성 전 보고를 유지한다. 같은 버전 재배포는 최종 변경과 실제 배포 필요성을 기준으로 별도 정리한다.

Stage 2는 위 지원 matrix를 검증하는 fail-closed 판정과 공개 MSI 대조,
Stage 3은 설치/재설치/제거 및 실제 bitmap/Explorer 범위 확인,
Stage 4는 기존 승인 문서와 최종 보고로 구체화한다.

## 2026-11-12 Stage 3 보완안 — Windows 10/11 Explorer 화면 자동 검증

상태: **계획 초안 · 구현/runner 등록/비공개 저장소 생성 전 승인 대상**. 작업지시자의 계획 작성 요청에 따라 기존 #132의 Explorer 수용 절차를 구체화한다. 앞선 승인 이력과 완료된 Stage 2는 유지한다. 작업지시자가 직접 화면 검증할 수 있다고 한 경로도 유효하며, 자동화 환경 준비 전 이를 완료로 간주하지 않는다.

### 목적과 현재 증거

Windows 10/11 x64의 실제 로그인 세션에서 Explorer가 HWP/HWPX 첫 페이지를 표시하는지 자동 판정하고, 실패 화면과 설치 생명주기 증거를 보존한다. 기존 [full run 43102583324](https://github.com/postmelee/alhangeul-tauri/actions/runs/43102583324)는 API bitmap·설치·재설치·제거를 통과했지만 화면 관측은 `interactive-shell-owner-mismatch`로 미실행이다. 현재 캡처 helper는 성공해도 `captured-awaiting-review`이며 자동 시각 판정은 구현되어 있지 않다.

초기 제품 입력 후보는 source `a2796fc0fd93002ccdcf1e5c313701525b1668c6`, artifact `13896135792`, NSIS SHA256 `1d439358949785485c28a8a4815d76490cd37d65523abbbd37aa88c6918c220b`다. 실행 때 만료·출처·digest를 다시 확인하며 만료되면 임의 최신 파일로 대체하지 않는다. 이 일반 빌드 결과를 후속 서명 릴리즈 파일의 검증 결과로 전용하지 않는다.

### 구성과 실행 경계

- 공개 제품 저장소에서 기존 hosted 빌드를 유지하고, 검증할 source/run/artifact/installer hash를 고정한다. 테스트 PC에서 Rust/Tauri를 다시 빌드하지 않는다.
- **비공개 검증 제어 저장소**(제안명 `postmelee/alhangeul-ui-validation`, 아직 생성하지 않음)에만 repository-level self-hosted runner를 등록한다. 공개 저장소에 상시 runner를 직접 연결하지 않는다. GitHub는 공개 저장소의 fork PR을 통한 self-hosted 환경 침해를 경고한다. [공식 runner 등록 안내](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)
- 제어 저장소는 소유자 수동 `workflow_dispatch`부터 시작한다. 기본 브랜치의 검토된 workflow와 허용 목록의 harness SHA만 실행하며 임의 ref/명령/다운로드 URL 입력을 받지 않는다. PR·fork·`pull_request_target` 자동 실행은 연결하지 않는다. runner label은 배정 용도이며 접근 통제 수단으로 취급하지 않는다.
- label은 `self-hosted, Windows, X64, alhangeul-ui, win10` 또는 `win11`; 매 실행 OS edition/build/architecture를 실제 조회해 label과 대조한다. VM 한 대당 runner 하나, GUI job 하나만 실행하며 OS별 concurrency로 중복을 직렬화한다.
- 기본 job token은 필요한 읽기 권한만 부여하고 checkout credential을 보존하지 않는다. 타 저장소 artifact 접근은 인증 필요 여부를 확인하고, 필요하면 제품 저장소 Actions 읽기 전용·만료 설정된 자격 증명만 사용한다. 제어 저장소의 기본 token으로 타 저장소 접근이 된다고 가정하지 않는다. runner에는 서명·배포·릴리즈 쓰기 자격 증명을 두지 않는다.
- 기존 `windows-thumbnail-user-context.ps1`의 `github-hosted` 전용 가드를 유지한다. 계정/프로필 생성·삭제를 수행하는 해당 wrapper를 self-hosted에서 재사용하지 않고, 미리 준비한 테스트 계정과 소유 작업 폴더만 다루는 별도 실행기를 만든다.

### 자동 시각 판정과 실패 처리

- fixture는 공개 파일과 고정 hash만 사용하고 실행/단계마다 새 이름·경로로 복사한다. 기존 Shell force-extract 증거와 결합하고 전역 thumbnail cache는 지우지 않는다.
- Explorer 창 전체 PNG를 증거로 보존하되, 판정은 파일명과 UI Automation 항목 경계로 찾은 썸네일 영역을 대상으로 한다. UI 장식·선택 강조·시계 등을 제외하고 실제 페이지 내용은 보존한다.
- OS별 기준 이미지, 해상도/DPI/테마/폰트 및 fixture hash를 함께 버전 관리한다. 작은 픽셀 차이 허용 임계값은 정상 반복과 잘못된 이미지 대조 실험으로 정한다. 현 시점에서 임의 수치를 통과 기준으로 확정하지 않는다.
- 이미지가 안정될 때까지 상한 있는 polling을 사용한다. 창 열기/항목 검색/이미지 안정화 각 60초, 시나리오 20분을 초기 상한으로 제안하며 실제 측정 후 조정한다. 무한 대기나 자동 baseline 갱신은 하지 않는다.
- OS 업데이트로 기준이 바뀌면 실패/검토 필요로 남긴다. 첫 기준 이미지 승인과 기준 변경 검토에는 사람 판단이 필요하고, 이후 동일 환경의 회귀 판정은 자동화한다. 캡처 성공만으로 기능 성공을 기록하지 않는다.
- 결과는 API bitmap, Explorer visual, installer lifecycle, cleanup 상태를 분리한다. artifact 업로드 실패도 증거 미완료로 처리한다. 실패 시 원본/영역/차이 PNG·검사 JSON·sanitized 로그를 남기며 설치 파일·개인 데스크톱 전체·token은 업로드하지 않는다.
- exact source/harness SHA, run/attempt/artifact ID와 digest, NSIS/MSI/DLL/worker/fixture hash, OS build, token/session, 기준 이미지 버전 및 비교 점수를 manifest에 넣는다. 오래된 실행 결과를 새 후보 수용으로 사용하지 않는다.
- 종료 때 소유 창/자식 프로세스/작업 폴더만 정리한다. 전역 Explorer/dllhost 강제 종료, 무관한 사용자 계정 삭제, 테스트 외 파일 삭제는 금지한다. snapshot 복원 전 현재 job이 끝나 증거가 업로드됐는지 확인한다.

검증은 의미 있는 parser/hash/시각 오판 회귀와 Windows preflight·실제 GUI 실행을 포함한다. workflow/shared CI 변경의 필수 검사는 기존 `CI_VALIDATION.md` profile 기준을 따른다. 통과한 제품 artifact를 재사용할 수 있는 조건에서는 제품 빌드를 반복하지 않는다. 이 Mac에서 native Windows GUI/Rust/Tauri 검증을 수행하지 않으며, 로컬 생성 검증 파일이 필요해지면 T7 연결·routing 정책을 먼저 확인한다.

### 비용과 GitHub만으로 가능한 범위

2026-11-12 공식 문서 확인 기준이다. 현재 제품 저장소는 public이며, 계정의 실제 유료 plan/사용량/청구 설정은 확인하지 않았다.

| 항목 | 추가 과금 없는 구성과 조건 |
|---|---|
| runner 실행 | self-hosted 실행 자체는 무료. 공개 제품 저장소의 표준 hosted 빌드도 무료. 유료 larger runner는 사용하지 않는다. [Actions 과금](https://docs.github.com/en/billing/concepts/product-billing/github-actions) |
| 비공개 제어 저장소 | GitHub Free에서도 비공개 저장소 생성 가능. 유료 runner group/유료 보호 기능을 필수 조건으로 삼지 않고 소유자 전용 수동 실행으로 시작한다. [GitHub 요금제](https://docs.github.com/en/get-started/learning-about-github/githubs-plans) |
| screenshot artifact | 비공개 실행의 artifact는 저장 공간 한도 대상. Free 기준 500 MB가 다른 사용량과 공유되므로 잔여량을 먼저 확인한다. 설치 파일 재업로드/동영상/Actions cache는 제외하고 PNG/JSON만 7일 보관, 실행당 20 MB 이내를 초기 목표로 한다. 초과 시 보관량을 줄이거나 실행을 보류한다. [포함 사용량](https://docs.github.com/en/billing/reference/product-usage-included) |
| 과금 방지 | 무료 잔여량 확인과 해당 Actions 유료 사용의 중지 예산 설정을 함께 점검한다. 알림만 켠 예산은 차단이 아니며, 이미 발생한 저장 비용은 나중에 삭제해도 사라지지 않는다. 청구 설정은 사용자 승인 없이 바꾸지 않는다. [예산 설정](https://docs.github.com/en/billing/how-tos/set-up-budgets) |
| PC/VM/Windows | 기존 장비·사용 권한·저장 공간이 있으면 별도 클라우드 구매 없이 가능. 장비/Windows 사용 권한/전기/디스크/유료 가상화·ESU 등 환경별 비용은 GitHub가 제공하거나 부담하지 않는다. [self-hosted 책임 범위](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) |

따라서 **GitHub 추가 서비스 비용 없이 구성할 수 있지만, GitHub 기능만으로 Windows 10/11 x64 테스트 환경까지 무료 제공받을 수는 없다.** 기존 장비·OS 사용 권한과 계정 저장 한도를 확인하기 전에는 전체 비용 0원을 확정하지 않는다. 외부 유료 UI 테스트 서비스 없이 PowerShell/Windows API·이미지 비교 코드와 Actions를 조합하며, GitHub 자체가 Explorer 이미지 판정기를 제공하는 것은 아니다.

### 승인·착수 조건

이 보완안의 비공개 제어 저장소, 전용 Windows VM/로그인 세션, 기준 이미지 최초 검토, 위 matrix와 문서 위치를 검토한 뒤 구현을 시작한다. 현재 요청으로는 계획서만 작성하며 외부 저장소/runner/자격 증명/청구 설정을 생성·변경하지 않는다. 사용자 준비 사항은 Windows 두 환경 확보와 GitHub 설정 확인이며, 구현·도구 설치 절차와 workflow는 이 계획을 바탕으로 구체화한다. PR 생성 전 알림은 유지한다. 같은 v0.1.3 재릴리즈는 실제 수용 후 별도 배포안에서 서명된 최종 bytes 검증·tag/asset 변경·복구 절차를 확정한다.

## 2026-11-12 우선 실험 승인 — GitHub 무료 hosted 자원

작업지시자가 “GitHub 무료 자원으로 가능한 범위를 먼저 실험해줘”라고 지시했다. self-hosted 보완안은 대안 초안으로 유지하고, 먼저 Stage 3.1에서 무료 Windows Server 2022/2025의 동일 사용자·세션 Explorer 캡처와 Ubuntu 24.04의 KVM/VM 자원을 관측한다. 승인 범위는 공개 저장소의 수동 조사 workflow, 고정된 기존 artifact 재사용, 공개 fixture·합성 이미지, helper/회귀와 증거 기록이다. 유료 runner·외부 VM·비공개 저장소·self-hosted 등록·release 변경은 실행하지 않는다.

기존 UAC/등록 정책을 유지하고 runner/Shell token을 관측한다. high integrity의 MSI 화면을 일반 사용자 NSIS 또는 Windows 10/11 성공으로 바꾸지 않는다. 같은 세션 캡처와 MSI 첫 페이지를 확인하고, Linux의 KVM 실제 VM 생성 API·메모리/디스크를 검사한다. Windows 이미지 사용 권한·출처가 확인되지 않으면 무단 이미지 배포/활성화 우회 없이 그 조건을 남긴다. 조사 전용 workflow는 fast 계약과 실제 관측으로 검증하며 새 제품/full 수용을 주장하거나 공식 CI 계약을 바꾸지 않는다.
