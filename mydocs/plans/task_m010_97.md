## 목적

로컬 글꼴 사용 상태에서 반복되는 전체 글꼴 목록 생성·검색 비용을 줄이고 Windows/Linux의
문서 열기·스크롤·입력 응답성을 개선한다. 기존 글꼴 선택·대체·설정 유지 계약을 보존한 뒤
검증한 산출물로 Alhangeul v0.1.1을 배포하고 공개 다운로드 안내를 갱신한다.

## 배경

- Linux 사용자 성능 제보와 Windows에서 로컬 글꼴 사용 해제 후 빨라졌다는 작업지시자 관찰이 있다.
- v0.1.0의 `resolveLocalFont()`는 매 호출마다 catalog를 filter/map하고 모든 별칭을 정규화·검색한다.
  렌더링·측정 소비자가 같은 글꼴을 반복 조회하면 설치 글꼴 수에 비례하는 비용이 발생할 수 있다.
- 초기 분석의 Node 측정은 이전 `local/task69` 코드 기준이다. 실제 v0.1.0 및 최신 devel의
  소비 경로와 성능을 다시 확인하며 그 수치를 배포본 성능으로 재사용하지 않는다.
- #74는 사용 선택 지속·상태 통합·다국어 face 식별을 보정했다. 이 계약을 성능 개선 중 유지한다.
- WebKitWebProcess CPU 80%는 GPU 문제 확정 근거가 아니다. 글꼴 설정과 DMABUF 설정은 분리한다.
- 시작 기준: `origin/devel`의 `97550085a9334129062266dddb625798bcdc77e2`.
  기존 checkout의 미커밋 변경은 보존하고 별도 worktree의 `local/task97`에서 진행한다.
- 참고: #74, #69, `docs/architecture/LOCAL_FONTS.md`, `docs/operations/DESKTOP_RELEASE.md`,
  `docs/operations/CI_VALIDATION.md`. 현재 공개 버전은 v0.1.0, upstream은 v0.8.6이다.

### 포함

- 실제 배포 코드·최신 코드의 글꼴 조회와 렌더링 연결, catalog/provider 상태 변화 조사.
- 레코드·정규화 별칭 인덱스의 재사용과 반복 hit/miss 조회 최적화.
- 재감지, 설정 변경, 파일 읽기 실패·복구, 문서 변경, 늦은 비동기 결과에 대한 일관성.
- 동명 face, 정확한 PostScript/full name, 다국어 alias, 제한 글꼴 정책 회귀 검증.
- 함수 단위 성능 비교 및 Windows/Linux 설치본의 같은 문서 열기·스크롤·입력 비교.
- v0.1.1 제품 version, 릴리즈 노트, 패키지 생성·설치 검증, PR·릴리즈·다운로드 안내 갱신.
- Windows x64 NSIS/MSI, Linux x64 AppImage/DEB/RPM, Linux arm64 DEB의 기존 공개 범위 유지.

### 제외

- upstream pin 변경, third_party/rhwp 또는 generated WASM의 직접 수정.
- 글꼴 지원 형식·허용 root·라이선스 정책 확대, GPU 환경변수의 전 사용자 강제 적용.
- updater 신규 활성화, 서명 키 교체, Windows Authenticode 신규 도입.

- 다른 작업자의 변경 회수, force push, 기존 tag 이동, 관련 없는 CI 전면 개편.

## 설계 방향

- Alhangeul local-font leaf adapter 경계에서 해결한다. upstream 소비자와 API 호환성을 유지한다.
- catalog가 준비될 때 불변 레코드와 이름별 후보 인덱스를 구성한다. 일반 반복 조회에서는
  전체 목록 재생성·정규화·순회를 하지 않고 요청 이름과 해당 이름 후보만 확인한다.
- catalog generation, provider generation 및 읽기 불가 상태의 변화를 함께 조사한다.
  catalog generation이 같아도 파일 읽기 실패로 후보가 달라질 수 있으므로 generation만으로
  유효성을 가정하지 않는다. 후보 가용성 확인 또는 명시적 revision으로 stale 결과를 방지한다.
- 정확한 이름의 우선순위와 모호한 family를 임의 face로 선택하지 않는 동작을 유지한다.
  레코드 sourceKey와 CanvasKit bytes 재조회 간 식별자가 달라지지 않아야 한다.
- 필요하면 조회 인덱스를 독립 모듈로 분리한다. 신규 파일 300 LOC, 함수 50 LOC 권장 상한을
  지키며 불가피한 예외는 구현 전 계획 보정에 기록한다.
- 시간 기반 벤치마크와 결정적 회귀 테스트를 구분한다. CI의 절대 ms만으로 pass/fail을 정하지 않고
  반복 조회의 재구축·전체 순회 제거를 검증하며 실제 편집 성능은 별도 수용한다.
- 제품 변경 PR은 devel로, release PR은 devel에서 main으로 진행한다. 최종 제품 SHA와
  package hash를 고정하고 검증한 bytes를 공개한다. 게시 직전 임의 재빌드로 교체하지 않는다.
- Release read-back 뒤 site/release.json 갱신 PR과 Pages 배포를 수행한다. 기존 stable manifest
  갱신과 앱 내 updater 신규 활성화는 구분하고 현재 활성화 정책은 변경하지 않는다.

## 검증 계획

### 단계별 검증

- Stage 1: 가상 catalog 0/100/500/1000/5000개에서 반복 hit/miss, 다국어 alias와 모호한 face.
  warm-up 후 여러 번의 중앙값·환경을 기록한다. baseline 태그 및 source SHA를 함께 보존한다.
- Stage 2: focused Vitest, 실제 adapter/upstream 소비자 통합, 조회 중 읽기 실패·복구,
  사용 해제·재활성화, 재감지 및 늦은 async 결과. 필요 시 fast CI로 첫 원격 피드백을 얻는다.
- Stage 3: Windows x64 WebView2 및 Linux x64 WebKitGTK 설치본에서 공개 HWP/HWPX와
  지원 공개 글꼴로 로컬 글꼴 on/off 비교. 고정된 조작과 문서로 열기·입력·스크롤 지연과
  긴 작업·조회 호출을 관찰한다. 최초 감지와 이후 편집 지연을 분리한다.
  기존 Linux GUI harness를 우선 재사용하며 Windows 실제 GUI 수용 증거를 별도 확보한다.
  사용자 Wayland 장비에 접근할 수 없다면 이를 미검증으로 기록하고 X11 결과로 대체하지 않는다.
- Stage 4: 공유 제품 변경의 최종 후보는 profile=full. Windows x64 NSIS/MSI,
  Linux x64 AppImage/DEB/RPM 및 arm64 DEB의 기존 수용 경로로 설치·실행·저장·재열기를 확인한다.
  이전 run의 성공을 다른 SHA/bytes로 이전하지 않는다. 기존 알려진 설치 제한과 새 회귀를 구분한다.

## 리스크

- **추정 원인**: 조회 병목만으로 모든 지연이 설명되지 않을 수 있다. 실제 프로파일 결과로 범위를
  재판단하고 다른 renderer·GPU 수정이 필요하면 계획 보정 후 진행한다.
- **캐시 무효화**: catalog와 provider 실패 상태 수명이 다르다. 성공뿐 아니라 miss·실패·복구를 검증한다.
- **실제 표시 회귀**: 빠른 잘못된 face 선택은 개선이 아니다. 모호한 이름·정확한 이름 우선순위를 보존한다.
- **환경 가용성**: Windows/Linux GUI·arm64·Wayland 실측 환경의 가용성은 아직 확인하지 않았다.
  확보할 수 없는 필수 수용은 미완료로 보고하며 다른 환경 결과로 덮지 않는다.
- **릴리즈 기준 변경**: devel에 다른 작업이 합류하면 v0.1.0 대비 전체 diff와 최종 후보의 범위를 확인한다.
- **검증과 게시의 간격**: merge·version 수정이 제품 bytes를 바꾸면 후보를 다시 고정한다.
  기존 태그를 움직이거나 이미 게시한 asset을 조용히 교체하지 않는다.
- **공개 제한**: 기존 Authenticode·NSIS 썸네일·MSI 재부팅 등 알려진 제한은 재검증 결과에 따라 명시한다.
