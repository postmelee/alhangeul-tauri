## 단계 목적

새 암호화 키를 독립 백업에서 복구하고 공개 테스트 자료에 서명할 수 있는지 확인한다.
installer 서명·GitHub Secret 전환·제품 공개 검증은 이 결과에 포함하지 않는다.

## 산출물

| 파일 | 변경 요약 |

| 수행·구현계획서 | 실제 진행 상태 반영 |

## 본문 변경 정도 / 본문 무손실 여부

기존 계획과 과거 키 기록을 보존했다. 제품 공개키·Secret·기존 백업은 변경하지 않았다.
개인키·암호·실제 비밀 보관 경로를 문서에 기록하지 않는다.

## 검증 결과

기존 `scripts/updater/artifact-verifier.mjs`의 `verifyUpdaterSignature`와
`publicKeyFingerprint`를 Node에서 호출했다. 개인키 대신 공개 테스트 자료·서명·공개키만 읽었다.

- OK — 사용자가 생성, 암호 앱 저장, iCloud 백업 및 별도 내려받은 복구본 서명 절차 완료를 보고했다.
  원격 내려받기·암호 앱 조작은 사용자 확인이며 에이전트가 독립 관측한 것으로 주장하지 않는다.
- OK — 복구본 서명이 새 공개키로 검증됐다.
- OK — 동일 서명에 변경한 테스트 자료를 입력하면 검증이 거부됐다.
- OK — 복구본 공개키와 iCloud 백업 공개키의 fingerprint가 일치했다.
- OK — 새 fingerprint가 현재 제품 공개키와 다르다.
- 새 공개 fingerprint: `9f86f804067eff359cd32707137dfaaea8710450985dda86b0392da5db63b8f8`.
- 공개 테스트 자료 SHA-256: `bfcc0e1a7302111687a90afb7a9882f5a85ec5f2167374577b437cf5c94cbfc0`.
- OK — 원본·iCloud 백업 보존 및 시험용 복구 파일 두 개 정리 안내에 사용자가 완료를 확인했다.
  휴지통 이동 안내에 대한 확인이며 영구 삭제·완전 소거로 해석하지 않는다.
- 한계 — 복구 당시 파일 권한은 독립 확인하지 못했다. 생성 절차는 `umask 077` 및
  키 파일 `chmod 600`을 사용했다. 정리 확인으로 임시본 보유 종료를 기록한다.
- OK — 공개 자료만 이용해 서명·변조 거부·fingerprint·테스트 자료 hash를 재검증했다.
- OK — 문서만 변경했으며 비밀 자료는 추적 대상에 없다. `git diff --check` 통과.

## 잔여 위험

- 암호와 백업이 같은 Apple 계정에 의존한다. 계정 복구 책임은 사용자에게 있다.
- 공개 서명 검증은 임시 개인키 파일의 과거 권한이나 완전 소거를 증명하지 않는다.
- 새 키로 CI installer 서명은 아직 수행하지 않았다.

## 다음 단계 영향

- 원본·iCloud 백업은 보존한다. 공개 테스트 자료·서명·공개키는 다음 단계 대조를 위해 유지한다.
- Stage 2 수용 후 별도 승인으로 앱 공개키·계약 변경을 진행한다.
- GitHub Secret 전환과 원격 CI는 기존 B/C 승인 경계를 유지한다.

## 승인 요청

- Secret 변경·원격 push/CI는 별도 실행 승인을 유지한다.
